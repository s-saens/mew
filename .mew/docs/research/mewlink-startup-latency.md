# Mewlink initial display and reconnection latency

This document records research and measurements for `feat/mewlink-fast-connect`. [Remote Access](../development/remote-access.md) owns the current implementation contract, and [Central Deployment](../operations/remote-central.md) owns the rollout procedure. The production figures below predate the fixes; isolated measurements must not be interpreted as production performance.

## Goals and measurement boundaries

The target is no more than 500ms from the start of address navigation until the actual Mew screen opens. Measurements distinguish password input before authentication from the display of actual menus, the explorer, and an example file with a saved login. Waiting screens and connection status text do not count as success, and login-screen results alone do not establish that the workspace target has been met. Document editing readiness, external mobile networks, and recovery after sleep also require separate verification.

Production observations used a fresh Chromium context with no saved authentication. We distinguished the first visit from subsequent visits in the same tab and collected only WebSocket signal types, relative timestamps, and resource transfer sizes. We did not record passwords, sessions, tickets, SDP, or ICE contents. We did not build, deploy, or restart the production server.

The primary metric in subsequent isolated measurements runs from `performance.timeOrigin` of Chrome's top-level document to the first rAF after the actual login input is inserted. Earlier values calculated by subtracting Node's navigation-command timestamp from the browser timestamp are kept separate for comparison. The Node−Chrome offset estimated using minimum-RTT CDP round trips stayed within approximately ±0.8ms across repeated measurements. Thus, clock differences do not explain the stage differences of tens of milliseconds below, but waiting between browser transmission and Node receipt must not be interpreted as serial execution of browser code. rAF is the next display opportunity, not a measurement of completed pixel painting.

In two separate observations, the time from challenge receipt to connect transmission was 2–8ms, and from connect transmission to ticket receipt was 413–474ms. Local Ed25519 signing and verification CPU costs alone cannot explain this difference; round trips involving the central service and host are the main investigation targets. Under Cloudflare's [DO location contract](https://developers.cloudflare.com/durable-objects/reference/data-location/), existing objects do not automatically relocate after creation, and location hints apply only at initial creation. Connecting to a new object by changing only its name can lose previous revocation state, so simple replacement is not used as a performance fix.

The `apac-ne` hint added on 2026-06-19 does not relocate existing objects either. It is a candidate for initial placement of new objects concentrated in Korea and Japan, but does not guarantee the location or improved performance of current production objects. [Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2026-06-19-apac-ne-apac-se-location-hints/).

### Lower bound on network round trips

The new host preparation path still requires a fresh WSS upgrade, challenge, and connect. If the browser↔DO round trip is `R_BD` and the DO↔host round trip is `R_DH`, the answer cannot arrive faster than approximately `2 × R_BD + R_DH + 호스트 처리`. HTTP, TLS, code preparation, direct ICE, and actual UI rendering are separate, with some overlapping this interval.

The first response to a separate production heartbeat took approximately 150–210ms. If this represents the browser↔DO round trip and the previous HTML TTFB of approximately 210ms remains unchanged, the time from startup is 510–630ms even with the host round trip and UI taken as 0. However, production figures after the HTML and D1 optimizations and the DO↔host RTT have not yet been measured, so we do not conclude whether 500ms is possible in production. The browser's Cloudflare edge at the time was HKG, and the actual DO location could not be confirmed.

### Read-only verification of production location

We later queried D1 information and [DO Analytics](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/) using an existing account's read permissions. D1 was `APAC`, and read replication was disabled. The anonymous bootstrap on the public connection path was closed after receiving only the challenge; no offer or key proof was sent. Combining the device ID from this response with the Analytics `name` filter corresponding to the current `getByName(instance.id)` showed a single `SJC` group for calls to this Mewlink object during 2026-10-23 17:00–23:50 UTC. Account and object identifiers and credentials were not retained in the research materials.

This provided evidence that signaling for the actual target was placed in SJC in the US, separately from the earlier HKG edge observation. D1's APAC designation does not indicate a city or SQL execution time, and this aggregate does not substitute for individual handshake round-trip times. A single anonymous fresh WSS connection took 873ms to reach the challenge, but this includes DNS, TLS, HTTP, D1, and DO, so it is not used as the cost of a single SJC round trip. Device registration, member permissions, and production deployment were not changed.

### Boundaries for relocating an existing signaling object

Relocating an existing DO to a nearby region requires a separate migration design that preserves the namespace and authorization data. The source snapshot and subsequent changes must be transferred to the target, and the target must be activated as the writer only after the source's durable fence is confirmed. Both writers must never be allowed simultaneously during the transition, and revocation records, single-use consumption records, and retries after failure must be preserved. The source DO remains as a boundary that rejects old requests or directs them to the new authorization state. Changes that merely add a new location hint or delete data were not implemented.

Reading the current implementation showed that active browsers' nonce, challenge, consumption state, and connection generation also reside in WebSocket attachments. Migrating only the disconnected recovery table or reusing the existing host termination function loses this state. Safe migration requires confirming the durable fence and lease, explicitly representing attachment state and draining in-flight requests, transferring revocation and consumption changes after the snapshot, verified import, an atomic D1 routing switch, and fresh host and browser proofs. The routing table and epoch do not currently exist, and all callers, including online status, listing, and revocation, must change together. Returning after the new target is activated also requires a reverse migration with a higher epoch. Neither the implementation nor the performance of migration without downtime has been verified.

A smaller v1 would explicitly terminate existing connections, then transfer only authority and revocation tombstones after establishing a durable source fence and confirming the latest actual validity limits of tickets, leases, prepare, admission, and recovery, along with native dispatcher termination. Even if the current policy is 60 seconds, input acceptance margins, clock tolerance, and in-flight issuance prevent promising completion in a fixed 60 seconds. The target must not be opened if evidence of expiration or a host drain ACK is insufficient. Revocations must also be preserved after the snapshot through deny deltas and a seal, and the existing five route calls and the HTML cap's epoch must switch together. This is an alternative that is not implemented and introduces a maintenance window; it is not used as a workaround that changes only the object ID.

## Isolated end-to-end connection

`mewlink/test/p2p-startup.browser.test.ts` connects distinct HTTPS origins, actual Miniflare Workers/D1/DO, a native RTC host, and Chromium. It uses only temporary data folders and an example owner. The already installed `dist/` is read only, while `MEW_STARTUP_BENCH_SOURCE=1` compiles the current main and authentication entry points into an in-memory fixture, replacing only Workspace and port preview. This fixture compilation is not a production app build.

An installed-dist run midway through the investigation took 925ms on the first visit and 646/638ms on subsequent visits. Approximately 809KB of static fonts were retransferred even on subsequent visits. After adding font CSS and fonts to the existing SHA-256-verified cache, subsequent transfer size fell from 810,707B to approximately 1,416B. Display times were 631/626ms, so this transfer reduction alone did not achieve the 500ms target.

Intermediate results from the current main fixture were 883ms for the first visit, 624/599ms for subsequent visits, and approximately 1,385B of subsequent host response bodies. `/api/auth/me` was requested only once. Approximately 230–245ms remained for ICE/DTLS connection after the answer, while the authentication lookup itself took approximately 3ms. These measurements use source under modification and a local network; they do not substitute for final verification results.

Comparing native state logs with actual breakpoints in the Node inspector showed that the remaining approximately 250ms was in the ICE stage, while DTLS and SCTP together took approximately 3ms. Experiments that changed only candidate priority and advertisement order showed no consistent improvement and were not adopted. An experiment that gathered ICE in a standby helper first, then automatically rolled back to respond to the actual offer, produced subsequent display times of 338/275ms and a first-visit time of 619ms for the installed UI. A separate actual RTC fixture showed an answer at approximately 8ms and channel opening at approximately 64ms. These intermediate values must not be presented as final performance until unused socket lifetime, single use, cancellation, and integration verification are complete.

### CPU contention from the next standby helper

We separated the first connection from initialization of the next standby helper by using a host that had already been online for at least 1.5 seconds and a fresh Chromium instance. ICE for the helper serving the actual connection completed 1.52–1.59 seconds before navigation in every sample. We alternated the existing fixture with a fixture that delayed only native initialization of the second and later helpers by 800ms.

| Condition | Three first visits (ms) | Median |
| --- | --- | ---: |
| Initialize next helper immediately | 581 / 582 / 565 | 581 |
| Delay next helper initialization by 800ms | 503 / 466 / 534 | 503 |

The paired reductions were 78/116/31ms, and the next helper's initial CPU usage was approximately 82–101ms. The host's browser proof verification, dispatcher preparation, and response took approximately 1–2ms. However, even under the delayed condition, one sample still had 110ms between browser transmission and native receipt, so this contention alone does not explain all first-connection variation.

We then applied a 800ms creation delay in the product source and verified it five times with a fresh host and fresh Chromium. First visits took 559/541/558/600/580ms, the median of ten subsequent visits was 522.5ms, and the median of five fresh RTC recoveries was 815ms. This introduced a regression: a subsequent visit or recovery immediately after the first display had no standby helper and had to wait for a new process. We did not adopt this delay and returned to immediate replenishment. Evidence of initial CPU contention is distinct from whether scheduling at a particular time improves performance.

## Low-level, compression, and architectural alternatives

| Candidate | Verified evidence and assessment |
| --- | --- |
| Prepare native helpers, certificates, and ICE in advance | Completing initialization alone in advance reduced channel opening from 250–351ms to 162–275ms; a separate measurement including ICE preparation was approximately 64ms. Signing of the actual offer, DTLS, and a separate process for each connection are retained. |
| Provision single-use host proofs in advance | An implementation that reduces the host prepare→ready→central ticket round trip is under verification. Short expiration, process generation, single-use consumption on both sides, current authorization, and final ticket checks must be retained. |
| Batch revalidation of static resources | The current index response incorporates a list of SHA-256 hashes for cached paths to reduce additional per-resource round trips. Stored bodies are hashed again, and scope is limited to the connection generation, 1 second, and a single use. |
| gzip→Brotli | Compared the installed main JS of 578,956B on the same CPU. gzip produced 181,601B in approximately 8.5ms, while Brotli quality 4 produced 180,695B in approximately 6.4ms. The size difference for this file was approximately 0.5%, so this was not adopted as a primary means of reducing latency. |
| Native library replacement and address handling | Isolated syscall tracing identified interface and address lookup costs during remote description processing. Production libc and network settings were not replaced; these costs are investigated separately from actual ICE/DTLS waits. |
| Reduce native thread pool size | [libdatachannel 0.24.5](https://raw.githubusercontent.com/paullouisageneau/libdatachannel/v0.24.5/src/impl/init.cpp) creates its pool based on CPU count and provides a C++ configuration function. The current [node-datachannel 0.33.4 binding](https://raw.githubusercontent.com/murat-dogan/node-datachannel/v0.33.4/src/cpp/rtc-wrapper.cpp) does not expose it. In an isolated comparison that added `SetThreadPoolSize(4)` only to a wrapper based on the fixed OpenSSL 3.5 version and reused the original archive read-only, the median initial creation time for ten fresh children per condition was 118.723→118.416ms. Threads were 23→15, CPU time was 9.544→8.898ms, and RSS was similar. All exited normally, but there was no evidence of latency improvement, so this was not adopted. Full P2P, load, and platform verification and changes to installed binaries were not performed. |
| WebTransport | The [W3C contract](https://www.w3.org/TR/webtransport/) provides certificate SHA-256 verification, but client identity must be verified separately. It requires a new implementation covering NAT traversal, UDP reachability, and browser compatibility, so it is not treated as an immediate replacement for existing WebRTC. |
| Issue HTML nonces in advance | The current challenge is carried in the same initial response interval as the 101 response. Since `onopen` also occurs after handshake completion, learning the nonce earlier from HTML does not reduce required round trips. [WebSockets standard](https://websockets.spec.whatwg.org/#feedback-from-the-protocol). This was not adopted because there was no evidence of benefit to justify the added complexity of nonce binding, expiration, and compatibility. |
| Forward the offer starting with the Upgrade request | This is a follow-up architecture that could overlap browser→DO→host preparation with the handshake. It requires verification of browser WebSocket API request-body constraints, separate POST costs, atomicity of single-use proof preparation/socket binding/consumption, and offer substitution, key substitution, and revocation checks. It is not included in this implementation. |
| Persistent reverse tunnel and TURN | These can improve NAT accessibility but do not automatically eliminate central signaling round trips. A reverse tunnel requires separate end-to-end encryption that prevents the relay from seeing plaintext, along with host key binding. TURN is distinguished as an accessibility alternative that retains the current DTLS. |
| End-to-end encrypted WSS relay | This can avoid PC initialization, but the final ticket and proof currently bound to the SDP fingerprint must be bound to the new channel. Even existing protocols such as [Noise XX](https://noiseprotocol.org/noise.html) still require verification of a non-extractable browser signer and the precise implementation/audit scope. Even in an optimistic model where both WSS connections are already open and authorization overlaps, the authentication ACK and first read take approximately 2R and 3R respectively, so if the end-to-end RTT R through the relay is at least 167ms, the time exceeds 500ms even before the UI. This is not a measurement of actual SJC R, and plaintext relays, 0-RTT writes, and races between two dispatchers are not adopted. |
| Fixed connect HTML that does not wait for D1 | The current HTML handles lookup and rate limiting in one batch, and WSS with a signed cap skips D1. Simply removing the HTML lookup leaves WSS without an instance requiring two sequential queries, lookup→rate, and late device key preparation. A policy decision is also needed on whether to treat fixed public bytes like the existing ASSETS exception; retaining the existing global HTTP300 counting for HTML-only/HEAD prevents eliminating D1 from the critical path. Shared caching of cap responses is not used as a workaround. |

We do not reduce network reachability or omit certificate, key possession proof, single-use nonce, or authorization revocation checks. The static UI cache is not expanded into a document, account, or session cache.

We also considered downloading public UI assets early during connection negotiation. The minimal approach stores only the main, authentication, and runtime JS from a fixed public release as bounded, unverified candidates, while retaining all checks against per-file SHA values in the current authenticated P2P index response, body rehashing, instance, generation, 1-second validity, and single use. This boundary does not require a new host JWT or signing endpoint; a CDN changes only the source of the bytes. It does not increase pre-authentication Workspace requests or place HTML, APIs, sessions, or user files on the CDN. Candidate storage must also be serialized within the existing limits of 64 entries, 32MiB, and 8MiB per file, and headers, decoded bodies, and gzip ETags must be normalized. Compiling downloaded code in advance is a separate architectural change because a [per-document module map](https://html.spec.whatwg.org/multipage/webappapis.html#module-map) cannot later be transferred to the UI iframe. It requires the same final document, individual integrity checks for all static children, confirmation by the current host, and document disposal on mismatch; a single preload or root SRI cannot substitute for these conditions.

We later compared one fetch-only pair using a temporary public static path on the same app origin. The original `connect-src 'self'` remained unchanged, and we neither added this release path to the product Worker nor deployed assets. With Node 24, the installed SDK, the full UI source, and CSS/fonts held fixed, first menu/tree/edit readiness was 733/817/1,020→686/770/968ms, subsequent readiness was 333/412/500→333/407/503ms, and fresh RTC recovery was 139→147ms. The final two conditions each had 1 pass and 0 skip, and eight helpers exited normally. A name-selection error during preparation and a separate preliminary baseline run were not combined with this pair.

The three candidates were downloaded and stored 308–345ms after navigation began and were used only in branches that passed the existing live-host batch verification at 526/543/573ms. There were 0 App pre-requests and subsequent CDN requests. Initial UI startup→menu was 221→184ms, but total time to the first menu exceeded 500ms; native startup variation, the absence of final Vite preload, and the limitations of a single pair still apply. P2P static requests were 45→42, JS requests were 39→36, and host static bodies were 2,187,277→1,981,112B. The separate public download adds 663,534B of decoded raw bodies, so this is not described as a reduction in total network transfer. Verification with a separate dump of raw host headers and negative tests for gzip, cancellation, and malicious catalogs were not performed, and this was not adopted in the product.

### Execution boundaries when compiling in advance in the same document

Three conditions were checked in a separate static Chromium/ServiceWorker fixture. Entry and static-child evaluations and API calls during preload were 0. Even when the SW subsequently rejected new fetches with 403, an import in the same document evaluated the existing module record once without additional fetches. Thus, a design that assumes current-host verification of the existing cache automatically reruns at execution time does not hold. Under the condition that explicitly detected a SHA mismatch in a separate fresh body and discarded the document, entry evaluations were 0; creating a new document through navigation required fresh module fetches and evaluations. On Node 24, 4 tests including the parent checks passed, with 0 skipped. These results do not verify actual Mew/P2P activation gates or performance.

Applying this requires a new client activation gate that binds the fixed bytes actually used for compilation and the current host's confirmation to the exact document and connection generation. The existing 304/200 fallback in `fetchRemoteUiResource()` cannot be mistaken for the batch's 1-second, single-use consumption, so strict batch-hit provenance must also be distinguished. The document's client ID, token, instance, attempt, index version, auth revision, and validity period must be rechecked after every asynchronous boundary, and cancellation or mismatch before activation must end in disposal of the entire frame. Actual module evaluation is separate work after activation commit, so removing a script alone does not guarantee 0 evaluations; the existing initial authentication, scope, and App import gates must be retained. Even without changing the host protocol, this is a new security contract and has not yet been adopted in the product.

A run with subsequent static stream checks added produced 5 pass and 0 skip, including the parent checks. ### Synchronous OS lookups in the native helper

An intermittent pause of approximately 150ms before the host received the authentication message was investigated using Node inspector CPU profiles, conditional breakpoints, and event-loop delay. In one reproduction, the browser sent authentication at 473ms and the host received it at 630ms; in between, `os.networkInterfaces()` ran synchronously for 185ms at 393–578ms. The call increased user CPU time by 0ms and system CPU time by approximately 12.4ms, with a maximum event-loop delay of approximately 196ms. This is judged to be OS address lookup blocking the event loop, rather than being explained by computation alone.

This lookup is used when Linux NAT path preparation checks the local address of the actual selected path. After the wait before starting mapping was reduced from 2 seconds to 100ms, it overlapped the initial RTC phase. A change to asynchronous lookup is being verified without removing address/path validation or NAT reachability. The per-connection breakpoint resumed in approximately 0.4ms, and the profiler, debug connection, and temporary fixture processes are to be cleaned up. This single reproduction does not establish a common cause across all platforms or all first-connection variation.

In one actual RTC check after the asynchronous fix, the Linux synchronous call occurred 0 times, and authentication transmission to host receipt took 3ms. A separate event-loop stall remains, so this is not described as eliminating all latency.

Additional NAPI and CPU profile instrumentation showed `addRemoteCandidate()` blocking synchronously for 117ms and 145ms. The user/system CPU increase for each call was smaller than wall time, and the same helper's longest event-loop stall overlapped the native call stack. A conditional breakpoint checked only the call name, time, and CPU before resuming. Separate candidate-type checks also reproduced 150ms with numeric IPv4/UDP/srflx candidates, so this cannot be treated as an mDNS-name-only issue.

In the version-specific source, [libdatachannel's Simple resolve](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.5/src/impl/peerconnection.cpp#L1090-L1121), [candidate resolution](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.5/src/candidate.cpp#L139-L158), and the subsequent [libjuice candidate resolution](https://github.com/paullouisageneau/libjuice/blob/3c40a3545b6b1b62c7adee7f8f2bd58aa290afd6/src/ice.c#L143-L205) synchronously call `getaddrinfo()` with `AI_ADDRCONFIG` even for numeric addresses. In a quiet, separate C probe, numeric-only lookups of fixed documentation IPv4/IPv6 addresses took approximately 0.00017–0.024ms; adding `AI_ADDRCONFIG` to the same lookup took approximately 0.667–10.109ms. This difference provides evidence of address-lookup cost but does not prove the cause of the entire 150ms during connection. Native internal lock waits and other factors require further investigation. Installed binaries were not modified, and DNS, IPv6, and TCP candidates were not excluded.

Separate baseline and modified binaries were built from pinned node-datachannel 0.33.4, libdatachannel 0.24.5, and the original submodule sources. Both binaries used the same tools, dependencies, and feature settings; the modification consists of two conditions that exclude `AI_ADDRCONFIG` **only in Simple mode** in libdatachannel and libjuice. Existing `AI_NUMERICHOST`, libjuice's `AI_NUMERICSERV`, Lookup mode, parsing, candidate order, signatures, and DTLS checks were retained. No custom address parser, asynchronous NAPI, or candidate removal was added. Because prefiltering by whether an address family can use numeric candidates changes, equivalent semantics across all platforms are not claimed.

In the default environment, 44 comparisons covering IPv4/IPv6, mapped addresses, zones, UDP/TCP, invalid addresses/ports, service names, Simple hostname/mDNS, and Lookup localhost had identical success status, address families, ports, and parsing errors. Total time in this environment was 445.28→25.39ms. In one actual P2P comparison pair of the two binaries built with the same tools, synchronous calls for numeric IPv4 candidates took 158.832→0.102ms, and mDNS Simple checks took 25.742→0.139ms. The first login display in that pair was 606→513ms, subsequent visits were 283/262→297/255ms, and recovery was 129→128ms.

The actual parent and child ran Node 24.16.0, and all 20 helpers shut down cleanly. ### Return events when the connection appears alive

After actual authentication and screen display, only the test-owned RTC helper was paused with `SIGSTOP`. With the parent process and WSS kept running, online·pageshow·visible events were sent. There were three WSS lease responses, but RTC remained connected and became `disconnected` only after about 5,945ms. Immediately issuing `SIGCONT` then returned the same peer to connected at about 5,965ms. This is not the recovery time for a new connection that completed a new ticket and authentication, nor was it an actual Wi-Fi transition.

This sample provides evidence that waiting for RTC's own disconnection detection after a return event can take substantial additional time. We discarded the initial output's interpretation of “no detection for 7 seconds,” where polling missed a briefly displayed overlay, and corrected it using persistent DOM marks and the actual peer sequence. The three owned helpers on Node 24 exited normally, and there were no write requests. A proposal to check the current RTC data path in the foreground with a limited read request must first be validated for contention involving congestion, stream limits, cancellation, and current authentication checks; it has not yet been added to the product.

A separate prototype sent one favicon HEAD within the existing request quota only on visible·online return, and canceled its determination during actual authentication checks, busy requests, backpressure, or generation or session changes. The final determination was at 1,500ms and simple observation at 500ms; it neither authorizes authentication nor retransmits writes. All 28 regression checks using a fake clock and actual stream slots, along with type checks, passed, but both actual native tests failed at the new-authentication recovery assertion. Normal HEAD requests took 3–4ms, but diagnostics under the paused condition showed an app request after 95ms, causing the conservative guard to cancel; the run ended after about 6,480ms with native detection and the same peer returning. The three owned helpers in each run exited normally, and product and installed assets were unchanged. This prototype did not achieve 1,500ms recovery and remains unadopted, without relaxing the conditions to ignore intervening requests.

ICE restart while retaining the same DTLS·DataChannel was also reviewed in source only. The current native API has no restart, and the polyfill method throws a not-implemented exception. The retained libjuice source rejects changes to existing remote ICE credentials and changes to local credentials after gathering, and strings in the installed Linux binary are consistent with this path. The fact that [restart is possible under the standard](https://w3c.github.io/webrtc-pc/#dom-rtcpeerconnection-restartice) is distinct from support in the current SDK. Existing signal-resume also reattaches WSS with the same SDP, keys, and lease; it is not renegotiation. A supporting backend and separate nonce·SDP hash·restart epoch·current permission validation are required, and the same helper paused with SIGSTOP cannot process a restart offer either, so we do not consider this a change that immediately resolves the roughly 6 seconds in this test. No product modifications, SDK replacement, or runtime experiments were performed.

### Official font subset comparison — not adopted

Unlike the roughly 809KB on the anonymous login screen, the actual Workspace's first display above required the full Regular font of 438,540B and did not fetch Bold. We compared the official WOFF2 subset sources for IBM Plex Sans KR 1.1.0 under 400/700 and `font-display: swap` conditions in a separate temporary fixture. The unions of character coverage were identical for the full and subset versions, and the 83 distinct visible Sans characters in the actual Workspace required only 7 Regular files totaling 72,156B. However, the complete subset CSS is 104,345B (gzip 22,004B), and it also increases the number of small font requests. This character count is an observation from a temporary example screen and must not be used to estimate sizes for all user documents.

The same source graph and actual authentication and tab switching were retained, but the subset version evicted JS from the 64-entry cache. The subsequent Workspace visit fetched 27,956B of fonts and 3 JS files again, while the same subsequent visit with the full version retransmitted no static bodies, fonts, or JS. After pressure from sequential requests for 188 subset resources, the cache stayed within its limits of 64 entries, 64 revalidation paths, and 4,419B of encoded query, but the next UI fetched 59 JS files totaling about 1.31MB again. Per-resource 304 responses and current host SHA checks after the 1-second validation lifetime expired were retained. Staying within cache limits and preserving repeat-visit performance are separate matters.

All 16 full-version control samples matched, but pixels differed in 8 subset samples at the same weight and size, and NFD Korean text also changed width. Coverage alone cannot guarantee character composition or rendering equivalence, so we did not adopt it in the product. A hybrid proposal using only 14 subsets selected from the example also missed one subset needed by the actual screen; the estimated total would be 501,660B if it fetched the full version as well, and no browser run was performed. Installed fonts, CSS, dependencies, and production assets were unchanged.
