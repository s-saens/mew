Central Mewlink accounts manage device registration, listing, deletion, and optional external identity proofs. Public device addresses initiate WebRTC connections without central login; users log in on the installed mew login screen with **a local email and password or a Mewlink account that has completed owner approval and self-linking**. Central identities and local users are separate; email, address, or device registrant status does not grant work permissions. [ADR 0208](../history/decisions/0208-mewlink-approved-login-identities.md). Implementation and isolated validation of the new authentication path are distinct from actual production application; the user must redeploy the central service and update the local installation. Checks of existing production logins by provider and measurements on external Android/LTE networks, sleep, and network switching remain outstanding.

On 2026-10-10, the user confirmed use of the actual mew UI and agent chat through the public username/device address, then reported repeated disconnections on desktop and mobile. Isolated load tests using actual RTC identified and fixed paths involving an IPC count limit for small messages and treating native send-wait returns as failures. Socket closure, callback exceptions, transmission ordering, and races when closing the central tab were also reproduced and fixed. The checks below do not establish a single cause of the reported symptoms or replace actual deployment and mobile network-switching validation. Browser-view resource 503 is handled separately from these connection stability checks.

## Domain migration and device dashboard

The device address is `https://mew.run/{username}/{device}`, and the management dashboard is `https://mew.run/{username}`. The dashboard shows the device list only to its owner logged in to the central service. Another account's dashboard returns 404; when logged out, the login screen is displayed without requesting the device list. `/` and the former `/dashboard` redirect to the user's own address after login. Starting a connection at a public device address does not require central login.

Command port buttons append `/<port>` to the public device address rather than the app frame's origin. `previewBaseUrl` passed by the parent and launcher, error handling for older central versions, and preview domain readiness follow the [port preview contract](port-preview.md#mewlink). Central changes are applied separately from host app updates.

The internal execution origin is `https://app.mew.run`. It is separated from the management screen on a different origin within the same site to reduce mobile browser cross-site storage restrictions while preserving central cookie and API isolation. Screen addresses on the former `mew.saens.kr` redirect to the new domain, but registration, persistent WSS, signing keys, and device IDs are retained. The central service allows only configured previous origins, and validates the host proof audience and ticket issuer against the origin of the host actually connected to. New browsers validate ticket issuers only against the current and previous origin list allowed by central configuration, while retaining validation of the same signing key and instance audience. Launch does not require new RPC methods on existing Durable Objects. The issuer of approved local Mewlink identities remains the corresponding host's origin, and the identity namespace for direct email accounts is also fixed to its previous value to prevent creation of a different account with the same email.

When retaining previous provider callbacks, OAuth is handled at `OAUTH_ORIGIN`, and a new management session is issued after consuming a single-use proof valid for 60 seconds and bound to a browser verification cookie on the new management origin. Requests that fail origin, cookie, or expiration validation do not create a session. This route is not provided on the app origin. [Domain migration decision](../decisions/0005-mewlink-domain-and-private-dashboard.md).

## Public file and folder links

A public link appends `/share/f/{id}` or `/share/d/{id}` to `https://mew.run/{username}/{device}`. The central worker preserves that typed share path through the connection parent, app launcher, and `mew:context` handoff. The installed app selects its standalone public editor after remote transport initialization, without opening the workspace or login UI. Direct localhost and custom-domain links select the same editor from their pathname.

The host dispatcher permits only the exact `/api/public-shares/{f|d}/{id}` capability endpoints before local login. Metadata, tree, file, and raw reads and existing-file content updates are authorized by the [public capability service](access-control.md#public-capability-links). Management routes, other work APIs, and work WebSockets still require local authentication. Invalid IDs do not retain a public connection. A validated capability supplies a live revalidation callback for connection lifetime; disabling publication or losing creator permissions removes that anonymous authorization. Authenticated session revocation remains unchanged.

`publicShareUrl` uses the validated public device base forwarded through `previewBaseUrl`; an invalid remote base fails instead of copying the internal app origin. Public raw responses forward CSP, Referrer-Policy, X-Content-Type-Options, and X-Frame-Options across the data channel.

The central source is maintained in the excluded `mewlink/` directory and is applied separately from the host repository commit. Host tests and isolated launcher checks do not establish deployment. The user must apply both host and central changes and verify a copied link from another browser before relying on Mewlink publication. The host must remain awake, online, and reachable through the direct connection.

## Connection information display

The device connection screen shows the public access address first, followed by the connected Mewlink account's `@username`, device name, direct connection readiness, and links to manage the user's own account and devices. The Mewlink registration account is distinguished from the local mew account used for access. Online status indicates central signaling status and does not guarantee a successful direct connection from an external network. Registration, pending registration, address lookup failure, setup required, and deregistration confirmation are handled on the same screen.

The host does not construct public addresses from immutable internal account IDs. It sends an unauthenticated `HEAD` request to the existing public device path to check the central username redirect. Only addresses pointing to the same public origin and device name, with no query, fragment, or user credentials, are displayed or copied. Previous `mew.saens.kr` registrations are checked at `mew.run` without changing registration keys or account mappings. Once the username is confirmed, the management link points to that user's path. If lookup fails, an error and refresh action are provided instead of exposing an internal-ID address, and the management link points to the public root.

Lookup results are reused within the process for 60 seconds; central reconnection and explicit refresh trigger a new check. Requests use a 5-second timeout and coalesce duplicate lookups. Late results arriving after deregistration or replacement are discarded. Only the display username, device name, and address are added to the status API; central cookies, email, internal account IDs, and keys are not provided. No central service changes or redeployment are required.

Validation uses address and origin checks in `server/remote-access-address.test.ts`; status queries, caching, retries, and key preservation in `server/remote-access-registration-network.test.ts`; and address copying, account display, error recovery, deregistration, and desktop/mobile display in `server/remote-access-ui.test.ts`. These are isolated checks using mock central responses and are distinct from validation with live service accounts and external-network access.

## Architecture and identity

`mewlink/src/worker.ts` is the Cloudflare central entry point. It is managed with its own package.json in a directory excluded from the parent Git and npm workspace. Workers + Static Assets deploy only the login, device selection, and connection frontend together; D1 handles central management accounts, registrations, management sessions, and single-use requests; per-device Durable Objects handle persistent WSS, signaling, and revocation. The central service does not load local API, workspace, terminal, or agent modules, or the parent mew `dist/`. The central `/api` has no work routers. OAuth integrates directly with Google, GitHub, Apple, and optional email OIDC, without Supabase.

The address bar shows `mew.run/{user}/{device}`. The new launcher identifies the target device through WebSocket bootstrap and starts the connection without central login. `authMode: local` and the random subject are connection context, not a local account or role. Single-use nonces, tickets, browser keys, and resume tokens are handled only in the central parent; the internal app origin `app.mew.run/launch/{임시 ID}` receives only public configuration for the exact frame and transport stripped of credentials. Central cookies for device registration and management use `__Host-`, Secure, and HttpOnly, and are not sent to the app origin. Central authentication and account APIs are blocked on the app host. After connection, the actual mew UI is fetched from A and runs in an internal iframe. Both hosts are deployed to the same Worker.

`server/remote-ui.ts` serves the installed A's `dist/` only for GET/HEAD requests from a dispatcher that has verified the key and connection proof. It does not allow direct HTTP, arbitrary files, ports, or development servers, and uses real-path checks to reject external symlinks, dotfiles, and traversal. Files are limited to 32 MiB and the index to 512 KiB. It checks `mew-p2p-bootstrap=1` in the built index to reject older UIs before execution, and selects remote bootstrap through the `mew-p2p-app` meta injected into the response. `src/main.tsx` starts downloading the lightweight authentication entry point and checking the parent MessagePort in parallel, but renders **after** establishing transport and account/instance storage scope. It does not fetch the workspace App before login and password changes are complete, and reuses the initial authentication state. Detailed responsibilities follow [browser startup](architecture.md#initial-browser-startup). Ordinary project paths on A do not select remote mode.

The Service Worker maps `/__mew_ui/{임시 ID}/...` to `/api/remote-ui/file?path=...` and redirects absolute static URLs to the same prefix. JS `import.meta.url`, dynamic imports, and worker resources remain on the same connection. Even after a worker restart, it looks only for the exact same `/launch/{임시 ID}` window and does not substitute another tab. App requests use MessagePort → the verified DataChannel of the central-origin parent; native URL requests use worker → the same parent transport. Actual app code receives neither the central session nor launch proofs.

A's `server/remote-access-agent.ts` checks a registration request initiated by the local owner and valid for 5 minutes. It verifies proof of possession of the Ed25519 key generated by A and the centrally signed receipt, then stores the immutable instance ID, central account ID, device name, and key. The production server entry point, `server/serve.ts`, connects to the central service over WSS only when a registration exists. `npm start`, `npm run serve`, and `./mew start` use this entry point. The Vite plugin for `npm run dev` does not create a Mewlink agent or register the `/api/remote-access` management API, so it does not connect or reconnect to the central service or register devices even when a saved registration exists. Running development and production servers together does not let the development server take over the existing device's central connection. The production server's exponential backoff is capped at 30 seconds plus jitter, and restarts use the saved key.

A central identity is **provider ID + verified issuer + immutable subject**. GitHub uses a numeric user ID under a fixed issuer. Matching emails, display names, or subjects from different providers are not merged. Changing login providers or replacing an email OIDC issuer creates a separate account. A UI for linking accounts across providers is not yet available.

A retains its existing email, password, roles, and server-side sessions, and links approved external identities as separate login methods. The existing `accounts` mapping from initial registration is preserved for configuration-file compatibility but is not used to authorize new device access. The previous local and central member APIs continue to return 410, and central membership does not create work permissions. New approvals use the local access request API and owner management screen below.

The transport opens after validation of the connection ticket and proof of browser key possession. Before login, only `GET/HEAD /api/remote-ui`, `/api/remote-ui/file`, `GET /api/auth/me`, `/api/auth/mewlink`, `POST /api/auth/login|logout|change-password`, and `/api/auth/mewlink/request|login` are available. Even files exposed to ordinary guests are blocked over unauthenticated P2P, and all work WS connections are rejected. Accounts logged in with temporary passwords may perform work only after changing their passwords. Approved external authentication logs in independently while leaving the password-change requirement intact in password storage.

Local authentication reuses the existing `createAuthRouter`, scrypt, and login failure limits. Only centrally signed `clientIp` is used for IP limits; app Cookie, role, and authentication headers are not trusted. Local sessions are applied to requests and WS through server-side context bound to the connection, with password changes, account deletion, expiration, and permission revocation checked on every request and by timers. Account switching and logout first clean up previous requests and WS connections.

The trusted launcher on the central origin stores or removes `x-mew-session` from login, password change, logout, and browser trust responses in per-device storage, then removes it from headers sent to the app origin. WebRTC, browser keys, and resume tokens are handled on the central origin; the launcher on the app origin receives only MessagePort transport stripped of credentials. Sessions on subsequent visits resume only through the first transport authentication message. Actual app storage is partitioned by the local email from `/api/auth/me` and the instance ID, and the app frame restarts on account switching. Follows the [browser storage contract](browser-storage.md).

A's `<DATA_DIR>/remote-access.json` atomically stores version 1, the server key, the pinned central public key, and account mappings. Private keys use file permissions restricted to the OS user. Damaged configuration is not overwritten with new keys. Central key and DB locations and backups follow the [installation contract](../operations/remote-central.md).

## Opening device connection settings

The owner manages device registration, connection status, access address copying, and deregistration through **Mewlink** in the header hamburger menu. `RemoteAccessModal` follows the shared `DialogFrame` behavior for closing with Esc, back navigation, or an outside press, and for restoring focus. Account management retains only Mewlink identity access approval and revocation, without displaying device connection settings. Registration and deregistration controls remain hidden during remote access.

## Keeping browser login and revoking access

After logging in with a local password or an approved Mewlink account, selecting **Stay signed in on this browser → Remember** on the central parent screen trusts the current browser. Here, a browser means a specific browser and profile on a device; all browsers are not grouped as one device. Temporary passwords must be changed first. The app bridge rejects `/api/auth/remote-device` requests, so the installed app cannot bypass consent in the central parent. [ADR 0015](../decisions/0015-trusted-browser-access.md).

`POST /api/auth/remote-device` accepts `{ label }` over the currently authenticated P2P connection. It binds the session to the host-verified local account, `authenticationMethod`, password credentials or the approved link's `credentialId`, and browser public key fingerprint. Trusted sessions expire after **90 days of inactivity**, and their expiration is renewed immediately on resume. Valid session checks on open connections also renew expiration at most once a day to maintain connections in active use. Resumption requires proof of possession of the same key, and the bearer session from before trust was established is discarded. Password changes, approved link revocation, account deletion, and current permissions are revalidated on every request. A token alone cannot be used to resume with a different key, and password login is not automatically replaced with external login.

The central launcher stores non-extractable Ed25519 keys **per host instance** in IndexedDB on the central origin. Tabs for the same host share a key, while different hosts use separate keys to reduce visit correlation. If storage is unavailable, it uses a non-extractable in-memory key and cannot preserve that key for the next visit. Only trusted session tokens are stored in per-device localStorage on the central origin; new sessions are first placed in sessionStorage, and previous persistent entries are removed. A session is promoted to localStorage only after `/api/auth/me` confirms its trusted status or the central parent's remember request succeeds. Existing 30-day local tokens retain compatible resumption. Keys and tokens are not passed to the app iframe, and passwords are not stored. With consent, approved external logins can also issue trusted sessions bound to the current approved link. These sessions can resume after the central cookie expires if the host's approved link and browser key remain valid. Storage locations and removal conditions follow the [browser storage contract](browser-storage.md#storage-scope-for-remote-local-account-connections).

The host sends `{ type: 'trusted-browser', connection, label }` over the central WSS only for connections that have completed local authentication and consented to trust. The central service uses the connection's public key fingerprint as `browserId` and stores its name, initial registration time, and most recent trust confirmation time in the per-device registry in D1 `0005_browser_access.sql`. Revoked rows are neither deleted nor reactivated. Even if revocation overlaps key verification or registration, a terminated connection is not reopened.

| Path/action | Contract |
| --- | --- |
| `GET /central/instances/:id/browsers` | Only the central device owner can retrieve `{ id, label, createdAt, lastSeen, revoked, connected }[]`. Times are epoch ms, and `connected` indicates a valid connection state in the DO |
| `DELETE /central/instances/:id/browsers/:browserId` | Only the owner can revoke access. Persist the revocation record first, send `access-revoked` to all tabs with the same device and key, then close the connections and forward `end` to the host |
| Dashboard: **Manage Connected Browsers → Revoke Access** | Revoke a specific browser through the API above. Connections from other browsers and to other hosts remain active |
| Device: **Unregister** | Discard the entire host registration and terminate all connections. This is a separate action from revoking a specific browser |

Logout and explicit revocation remove saved resumption tokens and stop automatic connections. `access-revoked` and explicit authentication rejection also stop automatic retries. The browser's key remains to preserve its revocation identity; keys and tokens for other hosts are untouched. Deleting the IndexedDB key and authenticating again with a new key using a password or approved external account can register a new browser, so browser revocation does not revoke the authentication method itself. A lost device or compromised authentication method also requires changing the corresponding password or revoking the external link.

## Static Asset Compression and Revalidation Caching

### Separating Caches for the Central Public Launcher and Installed Host Code

Under [ADR 0050](../decisions/0050-mewlink-startup-preparation.md), only successful GET/HEAD responses for the central service's `/launcher/<이름>-<8자리 빌드 해시>.js/css` allow a browser-only cache of 1 day. This requires status 200, a JS/CSS MIME type matching the extension, and a strong ETag; it is not allowed with `Set-Cookie`, personalized `Vary`, Range, Authorization, a query, or upstream `no-store`. The header is `private, max-age=86400, immutable, no-transform`, and CSP and origin isolation remain in place. When new HTML points to a different hashed URL, the browser fetches the new code.

HTML, connection token paths, public configuration/keys, Service Workers, APIs, non-hashed compatibility files, and errors remain `no-store`. This HTTP cache applies only to non-personalized central public code. Installed host code must pass the per-device SHA-256 and current P2P revalidation described below. Authentication results, documents, and sessions are not cached, and saved code is not used to enter the app after a disconnection or permission error.

Add `Link: <https://app.mew.run>; rel=preconnect` only to connect GET responses with status 200 HTML for the public production pair `https://mew.run`→`https://app.mew.run`. The request origin must also match the central configuration; do not add it for other production origins, roles, HEAD requests, or errors. Do not inherit Link from ASSETS, and do not include device paths, instances, admission, queries, or cookies in the hint. Omit `crossorigin` to match the actual iframe's credential mode, while retaining final CSP, `no-referrer`, authorization, and limit checks. When [Cloudflare Early Hints](https://developers.cloudflare.com/cache/advanced-configuration/early-hints/) is enabled and the cache is ready, a TLS connection may start before the HTML arrives, but 103 issuance, reuse, or reduced production timing is not guaranteed. Do not use preload, which sends resource requests before the final Referrer-Policy.

The connect HTML runs static bootstrap code before CSS and external scripts and fetches the connection controller and JOSE verification chunks together via `modulepreload`. The Worker adds only the body's SHA-256 hash to CSP when the trusted ASSETS HTML contains exactly one `script[data-mewlink-prime="v1"]` as a direct child of head and its standard marker and static body match. It does not allow `unsafe-inline` and passes the hash through an internal Response WeakMap. Dynamic device and admission metadata is provided earlier, outside the code, and the response explicitly specifies UTF-8. Invalid markers and older Worker/HTML versions use the existing external entry point.

The preliminary code prepares the same-origin browser bootstrap WSS and a per-device non-extractable Ed25519 key. Through a version-checked, single-use shared slot in the same window, it hands the socket off exactly once to the controller with the same URL and subprotocol. Before handoff, incoming data is limited to 8 messages, 64 KiB in UTF-8, and 10 seconds. Page departure, configuration mismatches, or exceeded limits trigger cleanup, and callbacks in unknown slots are not executed. The existing controller validates the nonce, final ticket, device answer, and proof of key ownership.

The inline code and external ESM also share the key preparation promise once for the same instance. Unused slots are removed after 10 seconds or on pagehide, and the actual non-extractable Ed25519 key, native promise, version, and instance are checked. Forged objects or preparation failures fall back to the existing key generation path. IDB's atomic add and re-query of the winner among simultaneous first tabs remain in place, and connections do not use a candidate key before storage completes. Once the key is ready, public JWK export runs in parallel with the SDP offer, and connect is sent only when both results are ready. Late completion after cancellation cannot reopen the connection.

### Host UI Compression and Revalidation

Vite's `base: './'` makes HTML assets, dynamic modulepreload, CSS, and worker URLs relative so the installed app runs both at the root and under a temporary P2P prefix. Because preload and the actual import use the same URL, this avoids fetching the same module again after redirecting `/assets/...` to a prefixed URL. Absolute asset paths from older builds remain compatible through the Service Worker's existing redirects. [Vite relative base](https://vite.dev/config/shared-options.html#base) and [modulepreload paths](https://vite.dev/config/build-options.html#build-modulepreload).

On browsers that support `DecompressionStream`, the Service Worker requests `encoding=gzip` only for GET requests for UI files without Range. A sends HTML, JS, CSS, JSON, SVG, and text that pass the existing path, realpath, size, and bootstrap checks as gzip streams. The dispatcher forwards `Content-Encoding` only for UI responses, and the worker decompresses the stream and provides the browser with a response stripped of compression encoding and length headers. The P2P receive window, cancellation, and backpressure apply to the same stream. HEAD, Range, images, and woff2 use the existing raw responses.

Because negotiation is optional, older servers ignore the query and send raw files, while older workers and unsupported browsers do not request compression. Task APIs and document bodies are not treated as compressed assets or stored in CacheStorage.

The resource worker waits up to 30 seconds for response headers. For static UI bodies, if no chunk or completion signal arrives within 30 seconds after the consumer requests more data through `pull`, it cancels the upstream request through the same MessagePort and ends the read with an error. When a chunk arrives, the timer is cleared and restarts on the next `pull`, so the total duration of an active download is not limited to 30 seconds. This UI body limit does not apply during backpressure when the consumer stops reading, or to long-lived bodies such as SSE from general APIs. Completion, errors, cancellation, and responses without bodies clean up timers and ports. `server/remote-resource-worker.test.ts` uses a virtual clock to verify stalls, progress, backpressure, long-lived APIs, and cleanup; `server/remote-ui-resource-browser.test.ts` handles actual compression, cache, and dynamic import checks.

Under [ADR 0018](../decisions/0018-mewlink-startup-revalidation.md), the internal launcher's `remote-resources.ts` stores non-Range GET responses for JS, MJS, CSS, fonts, and Wasm under `/assets/` and CSS, WOFF, WOFF2, TTF, and OTF under `/fonts/` in the `mew-remote-ui-v1` CacheStorage cache. Scripts and JSON under `/fonts/` are excluded. Keys include the instance ID verified by the current parent and the resource path, allowing code for the same host to be found even when the launch token changes. Accounts, documents, authentication tokens, HTML, images, APIs, HEAD, and Range are excluded from this cache. Limits are 8 MiB per resource after decompression and, across the entire app origin, 64 entries, 32 MiB, and 7 days since last storage; the oldest entries are removed first. An existing body verified by the current host is stored again and its timestamp updated only after 24 hours have passed since its last storage, avoiding rewriting the same large body to CacheStorage on every consecutive visit. Storage failures use the existing P2P download path. HTTP responses retain `no-store`, and only explicitly managed copies of static assets are stored separately. [Cache API lifetime and distinction from the HTTP cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache).

After the existing path, realpath, and size checks, A creates a strong ETag from the file content's SHA-256, distinguishing raw and gzip representations. The launcher rehashes the stored body, then sends `If-None-Match` over the currently authenticated P2P connection. It reuses the decompressed body only if A's 304 and ETag match. It does not trust the stored ETag alone, even if another app on the same origin tampers with the cache; mismatches, expiration, and older servers cause a fresh body to be fetched. An invalid 304 triggers an unconditional retry. Disconnections, 403, and 503 do not fall back to the cache, and the current worker reapplies the response CSP. The first download continues streaming without waiting for cache storage. The server reuses hashes when the file identifier, size, and modification/change times match, retaining at most 256 entries.

On subsequent visits, the current connection's `/index.html` GET optionally includes up to 64 cached paths within an encoded query of 6 KiB. If preparing the optional cache list takes more than 25 ms, the launcher requests index first and uses the existing per-resource revalidation. The host hashes files that pass the existing realpath, type, and 8 MiB checks in batches of up to 8, and returns the current raw SHA-256 ETags or `null` in the same order in `x-mew-ui-revisions`. The HTML body is not stored.

The launcher rehashes the stored body and skips the additional round trip only if it matches that list. The list is bound to the same instance, the open transport's `resourceGeneration`, and a maximum of 1 second after the response, and is used only once per resource. Suspension, termination, or a new index request invalidates previous verification, and late responses cannot overwrite a newer list. Missing, expired, or mismatched lists and older versions use the existing per-resource 304 revalidation. Cache fallback is not allowed for disconnections or permission errors.

This change takes effect after the user updates local mew and the central service and opens the page again. First visits, code changes, and environments with storage restrictions require downloads, and current connection authentication and host verification remain in place on reconnection.

## Preparing the App Bridge During Connection Negotiation

If the central connect HTML includes all public central/app origin metadata and the central origin matches the current page, `connection-frame.ts` prepares a hidden app bridge iframe with a new temporary token alongside WebSocket bootstrap. Older HTML without metadata prepares it after bootstrap as before; partially missing metadata or invalid origins end in an error. No device ID, authentication information, or MessagePort is passed at this stage.

The existing connection code takes over the iframe only if the central/app origins confirmed by bootstrap match the prepared values. Only ready messages with the exact iframe, origin, and token are accepted. Public device context is passed after bootstrap, and the transport port after `ready && connected`. The host's `/__mew_ui/` screen and task APIs are requested only after the existing authenticated P2P connection is ready. Browser key and saved session checks, ticket verification, revocation, leases, and same-account verification during recovery remain in place.

Failures, cancellation, duplicate starts, page departure, and configuration mismatches clean up the prepared iframe, listeners, timers, and unfinished bootstrap. The saved instance hint is used only as a lookup hint; if the actual device differs, the previous prepared connection is closed and preparation restarts in the correct identity mode. The early iframe itself has no device ID and therefore has no connection authorization until it takes over the newly confirmed context. [ADR 0050](../decisions/0050-mewlink-startup-preparation.md).

## Approved Mewlink Account Login

**Log In with Mewlink** on the login screen passes only the action through the designated app MessagePort. The internal launch frame and central parent verify the exact port and frame, and the parent navigates to the current device's `?login=mewlink` path. Central OAuth and email login return to this path. App-provided URLs are not used as navigation targets, and central cookies, launch tokens, and local session tokens are not passed to the app.

Connections with a central session optionally include a signed `{ issuer, subject, displayName, provider, username }` identity in the ticket. `issuer` is the central origin, and `subject` is the immutable central account ID. The connection's random subject differs from the local user ID. The identity and session hash from WebSocket bootstrap are bound to that socket's attachment, and the same session and account are checked during connect, ticket creation, renewal, and alarm handling. Older HTTP launch retains the existing signature, actual session hash, and single-use consumption checks. A trusts the identity in a signed ticket only after verifying it against the pinned central key and origin. Display information in HTTP bodies, headers, or prepare messages is not proof of identity.

Unapproved users click **Request Access**. Requests store only the verified transport identity; email or role input does not create users or permissions. When the owner checks the identity, provider, and username under **Account Management → Mewlink Account Access** and clicks **Approve**, a passwordless member is registered immediately and appears in the approved list. Roles are changed in account management. After approval, the waiting screen checks the status and logs in; subsequent new connections connect directly using the same approved identity. Central device registration alone does not grant local permissions; approval or self-service linking is required.

Existing email users link their own accounts under **Settings → Account → Link Mewlink Account**. This requires both the verified central identity from the same live P2P connection and a password login session, and any temporary password must have been changed. Existing local permissions allow linking without separate access approval. While logged in externally, switch through **Log In with an Existing Email Account** and link in a new app screen scoped to the account. [Self-service linking decision](../decisions/0007-mewlink-self-service-linking.md).

The linking target is fixed to the user of the current password session. Identity, account ID, and role in the body are not used as proof or as the linking target. `previousAccountId` is the comparison value for the previous link confirmed on screen; if the actual link has changed, the request is rejected with 409. Retrying for the same target returns the existing link. Moving another link issues a new link ID, revokes previous external sessions and tasks, and clears related access requests. After moving the link, a previous account with no remaining password or other Mewlink identity is deleted in the same account directory save. The previous account's saved sessions, trusted browsers, Git credentials, and feature and file permissions across all workspaces are also revoked. Previous accounts with a remaining password or another Mewlink identity are retained, and merges that would remove the last owner are rejected with 409. The target account's role, password, personal settings, and current email login session are retained. The previous account's project files, personal settings, and work records are preserved and are not automatically transferred to the target account.

A P2P account merge request keeps only that request active during synchronous permission cleanup, then immediately rebinds it to current permissions and sends a success response. Other in-flight requests and connections for the previous account follow the existing permission revalidation and revocation rules. [Merge decision](../decisions/0041-mewlink-merged-account-removal.md).

| Path | Boundaries and behavior |
| --- | --- |
| `GET /api/auth/mewlink` | Verified connection identity and unavailable/unlinked/pending/denied/approved status. unavailable over ordinary HTTP |
| `POST /api/auth/mewlink/request` | Requests use only the transport identity. Deduplication, up to 256 pending requests, up to 256 processing history entries, a 7-day lifetime, and a 15-minute restriction on resubmission after denial |
| `POST /api/auth/mewlink/login` | Select the current approved link. Switch the request generation and terminate previous tasks without issuing a password session |
| `POST /api/auth/mewlink/link` | Links the verified transport identity to the user's own current password account. Not logged in or no identity: 401; external login or temporary password: 403; conflict with a previous link: 409 |
| `GET /api/admin/mewlink` | Only the owner can view request and link lists |
| `POST /api/admin/mewlink/requests/:id/approve` | Owner approval. The UI creates a new member with an empty body. The compatibility API retains the existing accountId, display name, and member/manager selection. Reject re-execution of processed or expired requests |
| `POST /api/admin/mewlink/requests/:id/deny` | Owner denial of a request |
| `DELETE /api/admin/mewlink/links/:id` | Owner revocation of external authentication. Local passwords and personal settings are preserved |

Processing a request immediately frees its pending slot. Only the most recent 256 processing history entries are retained, and the 15-minute restriction on resubmission after denial applies only to retained history. If more requests than that are processed in a short period and an old denial record is removed, that identity can request again but cannot gain permissions without approval.

`users.json` v2 stores `accounts`, `passwordCredentials`, `mewlinkIdentities`, and `mewlinkRequests` in the same atomic file. User creation and the approved link are saved together so a failed approval does not leave an unlinked user. Existing v1 data is migrated on the first account save, preserving existing email-based internal IDs, sessions, permissions, and personal data. New external-only users use `account_…` IDs without fabricated emails or passwords. The compatibility API's `email` is an internal user ID, and `accountId` is also provided. Contact/profile information and login methods are separate. The CLI's `role` and `remove` also accept internal IDs, while `add` and `reset` are for email login accounts.

`server/remote-authentication.ts` manages the login method selected for a connection. External authentication is bound to the local account and approved link ID at that time and revalidated on every request. Reapproval after unlinking or deletion does not restore the previous link's permissions. Approval alone does not silently switch accounts on an existing waiting connection; a login action performs the switch. External authentication does not automatically replace an expired or logged-out local password session. `hasPassword` and `authenticationMethod` from `/api/auth/me` distinguish settings forms for passwordless accounts and external logout. Saving a profile preserves the actual password record.

When resuming a saved local password session or an explicitly issued trusted session, the launcher omits the central identity through `identity: false` and connects independently of central login. The host continues verifying the original approved link even for trusted external sessions. Explicit Mewlink login does not send saved local sessions. A transport that includes an identity ends the connection when the central session ends. Even if that connection switched to a password, the local password session itself is not revoked and resumes independently on the next connection. External logout clears the local selection, and the parent ends the central session before returning to the same device's login screen.

Applying these changes requires both **the user's local mew update and Mewlink redeployment**. Agents do not perform production builds, deployments, or restarts. Central source retains the existing policy excluding it from public Git, so it is kept in a separate private backup.

## Usernames and Device Addresses

Users set a username the first time they log in to the central service, then change it through account settings (`/account`) in the header. Usernames are 3–30 characters using English letters, digits, and hyphens; they must start and end with a letter or digit, and consecutive hyphens and reserved service path words are not allowed. Leading and trailing whitespace is removed, names are stored in lowercase, and they are unique across the central service regardless of case. OAuth display names or provider usernames are not automatically claimed.

The current device address is `https://mew.run/<username>/<device-name>`. D1 `0002_usernames.sql` adds a nullable `username` to existing accounts and preserves name ownership history in a separate table. Claiming a name and changing the current name execute atomically in a D1 batch so only one account obtains the name among concurrent requests. Previously used names remain owned by the same account and cannot be claimed by another account. Previous names, uppercase addresses, and existing internal ID addresses redirect to the current username address with 307. Existing addresses for accounts without a username remain in place until one is set.

Central internal account IDs, provider identities, administrative sessions, and device owners use the existing immutable IDs. Task permissions and browser storage scopes use local accounts and instance IDs. Usernames are address aliases; changing a name does not transfer permissions or storage scopes. A central internal ID identifies a management account and is neither device usage permission nor a local login account. Internal ID-based device addresses saved by local mew also redirect centrally to the current username address, so re-registration is unnecessary.

`PUT /central/account` requires the central origin and a login session, returning 400 for an invalid name and 409 for a name already owned by another account. Account APIs remain blocked on internal app origins. To apply this for users, deploy the central frontend, Worker, and D1 migrations together with `npm --prefix mewlink run deploy`. There is no need to build or restart local mew solely for this change.

`mewlink/test/username.test.ts` verifies concurrent claims, case handling, reserved words, change history, session/owner preservation, origin checks, and redirects from previous addresses. `mewlink/test/p2p.browser.test.ts` checks initial setup, recovery from duplicate-name errors, changes, actual P2P UI access through new and previous addresses, and mobile widths. The user performs the actual central deployment.

## Direct Email Login

The central login screen provides an email input form when the Cloudflare `EMAIL` binding and a valid `EMAIL_FROM` are available. The sequence is enter email → send code → verify code → set a username on first use → return to the original device registration or connection path. The form is hidden when configuration is absent, and existing Google, GitHub, Apple, and optional email OIDC remain independent. [Sending configuration and deployment](../operations/email-login.md), [ADR 0206](../history/decisions/0206-mewlink-email-code-login.md).

`POST /central/email/start` validates the central origin and the email in a size-limited body, then issues a per-browser, host-only Secure, HttpOnly `__Host-mew_email` cookie. The 6-digit code is generated using cryptographically secure randomness and is valid for 10 minutes. D1 `email_logins` stores a challenge hash and a code hash bound to the raw challenge, without storing the plaintext code. The request changes to `ready` only after sending succeeds and is deleted on failure. A new request from the same browser deletes the previous challenge.

`POST /central/email/verify` requires both the cookie and the code. It atomically increments the verification attempt count in D1 and allows at most 5 attempts. After a fixed-length, timing-safe hash comparison, it consumes successful requests with an atomic DELETE to prevent reuse and concurrent successes. Accounts and central sessions are created only after consumption, retaining the existing session cookie security attributes. Sending is limited to 10 requests per IP per minute and 1 request per normalized email per minute; verification is limited to 30 requests per IP per minute. Codes, cookies, and email bodies are not logged. Expired requests are removed by the existing hourly cleanup.

Email addresses are trimmed of leading and trailing whitespace, and the entire ASCII address is normalized to lowercase. The local part is limited to 64 characters and the full address to 254 characters; provider-specific aliases such as dots and plus signs are not merged. Direct email identities are looked up using the `email-code:<central-origin>` namespace and verified normalized address, and continue using the account's immutable ID. They are not automatically merged with OAuth/OIDC or local mew accounts displaying the same email. Verifying ownership of the authentication email does not grant new device management or local task permissions.

Email sending failures end with 502, rate limit violations with 429, invalid codes or cookies with 401, and expiration, attempt limit violations, or already-used codes with 410. The UI preserves input and errors, provides actions to request another code and change the email address, and prevents duplicate actions during the resend wait and verification. It cleans up the countdown on refresh and navigation. After initial name setup, it returns to the original central path after safely validating it. Email tests use mock sending; actual email delivery, domain activation, and central deployment require user confirmation.

The central frontend uses the mew symbol, IBM Plex Sans KR, and purple accents. The device list displays the name, online/offline status, and address in the same row, and offers unregistration only to the owner. Successful copying is indicated by a check icon and status announcement. Unregistration is confirmed within the row; Cancel or Esc closes it and returns focus to the original button. Mouse and keyboard interactions share DOM tooltips, and touch interactions do not show hover tooltips.

An empty list explains how to register from account settings in local mew. The connection screen at a device address shows only the process of opening mew, using **a full-screen gradient and centered indicator**, without the central header, account menu, device address card, or list link. The initial HTML provides the same screen. It displays `mew에 연결 중` while connecting and `mew를 여는 중` when the transport is ready, and transitions only after receiving the app's ready signal. Temporary reconnections preserve the existing app and drafts.

The background is a single CSS radial gradient layer that follows the OS light/dark theme and animates only transform and opacity. It does not download images, videos, canvas assets, or additional animation libraries. Reduced motion settings use a static background and indicator, and animations stop in hidden tabs. The connection screen uses system fonts. The central regular and bold font files, totaling approximately 809 KB, are unnecessary for connection, so font CSS is registered only when opening central login, registration, or management screens through `shell()`. Fonts in the actual mew app follow the existing app contract. [CSS animation rendering guidelines](https://web.dev/articles/animations-guide).

`bootstrapRemoteConnection()` opens WSS using the device path or instance ID while preparing the SDP offer and ICE. It verifies the instance, app origin, allowed issuer, and central public key from the same-origin challenge, so it does not make separate HTTP launch or `/central/key` requests. Once the verified instance's browser key and resume session are ready, it sends connect once with the socket nonce, offer, and public key. Cancellation during preparation closes the socket, peer, and pending waits, and late preparation cannot reopen a terminated connection. The older `connectRemote()` HTTP launch and central key lookup remain as a compatibility path. This path is used only for transport failures before bootstrap context is available, not for invalid context, access denial, or revocation. ICE candidates are sent under the same WSS ordering and authorization conditions below, and key, signature, issuer, audience, time, and browser/device proof validation remain in place.

The host pre-supplies the host authentication epoch and up to 8 single-use challenge/generation entries with a lifetime of 60 seconds over the authenticated persistent WSS. It changes the epoch for each new host proof. The central service stores them in `mew_signal_preparations` SQLite and atomically consumes them before sending prepare and the final ticket, skipping the host ready round trip. Consumption records remain until expiration to prevent reuse after hibernation or duplicate supply. The host also consumes each entry in the same authentication epoch only once and rejects tampering, reuse, and expiration. This list does not authorize connections or replace checks of current device and browser permissions. If unsupported, exhausted, or the remaining lifetime is 2 seconds or less, it uses the [existing ready path](../decisions/0028-mewlink-websocket-bootstrap.md).

Session resumption, the operation dispatcher, and authentication-complete responses are not allowed until the final ticket and browser key proof have been verified. Data arriving earlier is held in `remoteTicketInbox` within the existing limits of 32 KiB per frame, 512 KiB total, and 4096 pending entries. Termination or expiration releases pending waits and cleans up helpers, and late ticket, signature, or process callbacks are discarded. Answers and candidates arriving during signing also remain ordered after the ticket and are not sent after revocation or host replacement.

After verifying the new challenge and sending connect, the browser sends ICE candidates over the same WSS while waiting for the ticket. The central service processes messages from the same socket in order, forwards candidates only to the approved `state.connection`, and retains current identity, revocation, and lifetime checks. Before the ticket, candidates are limited to 127 to stay within the central queue limit of 128 entries, including connect. Candidates are not sent during cancellation, signaling interruption, or recovery authentication waits; queued candidates are forwarded only after verified reattachment.

A registered host pre-initializes native components, certificates, and ICE in at most one separate standby RTC helper with no account, registration key, session, or remote offer. Prepared SDP and candidates are not sent externally. The warmup negotiated channel ID 1022 is closed before the actual offer, and upstream automatic rollback produces a normal answer. One JS wrapper reference for the closed native channel is retained until `rtc.cleanup()`. This prevents GC from collecting the wrapper remaining in the SDK's global list first and causing a crash or hang during shutdown; the native channel is already closed and keeps no additional sockets open. Unused UDP sockets are replaced every 30 seconds within the same `55000–55031` range, and central WSS reconnection also replaces the standby helper. When an actual connection takes over a helper, the next helper is prepared immediately if a slot is available. Router mapping starts only after actual prepare. The maximum of 8 active connections and a separate process per connection are maintained, and used helpers are not returned for use by other connections. No unnecessary standby helper is created while 8 connections remain active or the central connection is down. Preparation errors do not trigger immediate infinite creation retries; takeover, registration changes, unregistration, and shutdown clean up creation retries and standby helpers.

NAT mapping preparation starts after 100 ms for an actual connection and is canceled if the connection is established first. Linux route and address checks use the [shared asynchronous lookup](remote-desktop-connectivity.md#automatic-nat-preparation-for-active-connections) to avoid blocking the RTC callback event loop. Terminated active and standby helpers are first sent close and are discarded with SIGKILL if they do not exit within 4 seconds. A normal exit cancels the forced termination timer, and stalled native cleanup is not repeatedly awaited using the same SIGTERM. NAT leases, current permissions, and process isolation per connection are maintained.

The internal launcher verifies the role HTML's `mewlink-central-origin` and `mewlink-app-origin` metadata and the instance information from the exact parent frame, then starts Service Worker registration and activation during P2P preparation. Only older HTML lacking both metadata entries queries `/config`; partial metadata or an invalid origin is treated as an error. HTML does not contain nonces, tickets, browser keys, or sessions. The instance of the final MessagePort must also match before use. On the initial connection, `/api/auth/me` overlaps with app resource preparation, and no duplicate `/api/remote-ui` request is made because index performs the same bootstrap check. The resource bridge forwards index's 403, 404, and 409 as launcher errors. Transport to an existing app undergoing recovery is reopened only after verifying the same account and authentication method.

The authentication state verified on the launcher's current connection is passed once through `initialAuth`. With a new launcher that negotiates `authStatusPending`, index and app code wait for the same `/api/auth/me` result even if they arrive first, avoiding duplicate requests. Older launchers fall back to the existing query, while invalid state or termination ends with an error. Reconnection and account switching discard the previous pending state and verify the same account and authentication method on the current connection. Authentication results are not persistently cached. Downloading the app's route-specific authentication entry point also starts in parallel with MessagePort and storage scope preparation, and actual rendering occurs after scope verification.

If a saved session and previous device path hint exist, `identity=0` is selected from bootstrap to omit central identity. The saved association between the public address and instance is only a hint; if the response instance differs, the prepared socket is closed and the process restarts in the actual device's identity mode. That session or browser key is not sent to another device. Explicit Mewlink login does not use saved sessions. Automatic recovery also uses a new bootstrap, and the existing app resumes after the same account and authentication method are verified.

Existing simulated-time checks confirmed that overlapping 180 ms of local preparation with 200 ms of signaling wait resulted in 200 ms until connect was sent. This is not a measurement of production improvement and does not guarantee live-service latency including network activity, ICE negotiation, and local app downloads. The changes require application to the user's local app and redeployment of the Mewlink central service.

Offline states and request failures show specific errors on the same full-screen view and offer reconnection or navigation to the device list. Internal launcher failure reasons are sent through the bound relay port before the termination notification so that generic cleanup messages do not overwrite specific errors. The internal connection frame ready signal, screen resource preparation, and app ready signal each have a 15-second limit to prevent indefinite loading at a stalled stage. These connection frontend changes take effect through the user's **Mewlink central redeployment**. The agent does not run production builds or deployments.

## External WSL access and UDP inbound traffic

Mewlink's native WebRTC helper uses only UDP `55000–55031`. Even if STUN obtains external candidates, a phone on another network may be unable to connect if inbound traffic on those ports is blocked. In WSL mirrored mode, check the Hyper-V firewall's WSL inbound policy separately from Windows Defender. Open only the required UDP range without changing the overall default inbound policy to allow. [Microsoft WSL networking](https://learn.microsoft.com/windows/wsl/networking#mirrored-mode-networking).

When the owner clicks **Mewlink → Register Device** locally, `remote-access-network.ts` starts network preparation before registration. Already registered devices run the same procedure through **Prepare Connection** while preserving the device ID and key. Server startup, status queries, and connections from external phones do not open Windows approval dialogs. Status queries are read-only and reused for 30 seconds. `POST /api/remote-access/prepare-network` is available only to the local owner and is not allowed through the P2P operation dispatcher.

The fixed `remote-access-network.ps1` prepares only the inbound UDP range for WSL Hyper-V or the Node program running on Windows. If administrator privileges are required, it requests Windows UAC once and coalesces concurrent requests. Cancellation, explicit blocking, same-name conflicts, and management policy restrictions are shown as preparation failures, and existing rules are not overwritten. The WSL rule is a port range applied to the entire WSL VM, not a per-program rule. Linux, macOS, and environments where Hyper-V policy cannot be inspected retain `unknown` and allow registration, but are not shown as prepared.

For WSL installations requiring manual recovery, a range rule can be added in administrator PowerShell as shown below.

```powershell
New-NetFirewallHyperVRule -PolicyStore PersistentStore -Name 'Mewlink-ICE-UDP-55000-55031' -DisplayName 'Mewlink ICE UDP 55000-55031' -Direction Inbound -VMCreatorId '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -Protocol UDP -LocalPorts '55000-55031' -Action Allow -Enabled True
```

If a rule with the same name already exists, check its range, direction, and allow status without creating a duplicate. If management policy blocks local rules or regular Defender rules impose additional blocking, those policies must also be checked. Router NAT and external-network UDP restrictions are separate conditions, and firewall rules alone do not guarantee connectivity on every network. When revoking, delete only the rule with the same name.

In source installations, `remote-access-rtc.mjs` is read in a separate process for each new connection. Changes limited to the helper's port and candidate handling apply to the next connection. Changes to the parent registration API, settings UI, or network preparation apply after the user updates, builds, and restarts locally. CLI executables require distribution of a new executable. Anonymous mobile browser connections on the same PC and checks of host UDP candidate ports are distinguished from actual external LTE verification.

### Router preparation and direct connection diagnostics

The helper immediately exchanges existing WebRTC host and STUN candidates. If no connection is established within 100 ms, it tries the existing `nativeConnectivity` PCP → NAT-PMP → UPnP sequence when the actual host UDP socket matches the OS-selected default route. It requests a 120-second lease for that UDP port from a supported router and adds the successful public candidate. Leases are renewed at half the returned lifetime, and only mappings it owns are deleted when the connection ends. Unnecessary discovery is canceled if a direct connection is already established. The channel and peer close immediately, and mapping cleanup waits at most 3.5 seconds.

`RemoteStatus.network` is the OS preparation status, and `connectivity` contains the latest helper's candidate gathering status, counts of host/srflx/public IPv4/global IPv6 candidates, and mapping status. Diagnostics do not include addresses, ports, or authentication values. `online` indicates the central signaling connection and does not mean an external phone has connected successfully. OS rule preparation and synthetic NAT checks are also not evidence of external-network success.

Operation data continues to be transmitted directly through WebRTC DataChannel. HTTPS, WSS, or TURN data relays are not added. Direct connections may fail if the router does not support mapping or multiple NAT layers or external UDP blocking remain. [Automatic preparation decision](../decisions/0006-mewlink-direct-network-preparation.md).

## Windows Chrome connection to WSL on the same PC

Only on WSL kernels, `server/remote-access-rtc.mjs` uses `remote-access-ice.ts` to add a `127.0.0.1` candidate with the same socket port and mid as the IPv4 UDP host candidate. The loopback candidate is sent only once even if other interfaces advertise the same socket. Normal host and STUN candidates and authenticated ticket and key validation are maintained. Loopback addresses are not created from TCP, IPv6, srflx, relay, or mDNS candidates, and no separate relay socket or HTTP path is opened.

In WSL mirrored mode, ICE checks sent to normal Windows and Linux interface addresses may receive no response even on the same PC. On 2026-10-09, a failure using only existing candidates was reproduced with actual Windows Chrome 155 and an isolated native helper on WSL2 mirrored mode (check packet responses: 0), and candidate pair selection and DTLS/DataChannel opening were confirmed after adding loopback candidates. Chrome experimental settings, Windows firewall, and WSL settings were not changed. This result does not guarantee success in other WSL network modes or on external networks. [Microsoft WSL networking](https://learn.microsoft.com/windows/wsl/networking).

Because a new helper is created on connection, even a running server reads the modified helper file starting with the next connection. Changes limited to this candidate handling do not require central redeployment or an app bundle rebuild. Create a new connection through **Reconnect** on the failed device page or by refreshing the page.

## Central signaling authorization state

Each device's Durable Object stores its device public key, browser trust list, and revocation records in its own SQLite. On first access, it imports the existing D1 device and browser lists once, and does not treat import failures as an empty list or completed initialization. Subsequent hibernation also restores SQLite and WebSocket attachments to use the same state. `shared/remote-signaling-state.ts` provides the shared implementation, and the private `mewlink/src/signaling.ts` handles the central connection. [ADR 0025](../decisions/0025-mewlink-signaling-authority.md).

Device and browser state is not reread from D1 for each SDP ready, answer, or ICE candidate. Local password, saved session, and anonymous connections make 0 D1 queries for these messages. Central session queries and request limits remain for connections containing an external Mewlink identity. New WebSocket bootstrap consumes the socket attachment's nonce once instead of performing D1 launch INSERT/DELETE operations, while issuance and single-use consumption for older HTTP launch remain in D1. Prepare/ready, signatures, leases, and direct P2P transmission are maintained.

Browser revocation and device disposal through the management API are first persisted in DO SQLite, then the target connections are terminated before D1 is updated. If the D1 update fails, the API returns a failure but does not roll back the DO revocation. The latest revocations are checked at new admission and after long-running token verification or signing, and late-arriving initial D1 lists or trust registrations cannot undo revocation. Browser management lists read DO state.

Lease renewals and the 10-second alarm monotonically merge device and browser revocations from D1 and revalidate central sessions. D1 active values do not reverse DO revocations. Revocations made by directly modifying D1 outside the management API take effect at the next renewal or alarm. Backups and rollback to older versions must consider both DO and D1 state, following the procedure in the [central deployment document](../operations/remote-central.md#preserving-and-restoring-signaling-authorization-state).

## Connection authentication and revocation

### Single-use rate limit proof prepared in HTML

Currently, GET requests for public device HTML check and consume the HTTP limit and IP launch, device launch, and IP browser signal limits in a single D1 batch. `instance_rate_keys` in `0006_instance_rate_keys.sql` links the original instance to the existing SHA-256 rate limit key, so existing counters, limits, and check order do not change. Keys are prepared during new registration and authenticated host startup; if missing from an existing row, the existing lookup path establishes the association before backfilling it. A connection is not allowed if a different key is stored. HEAD requests, redirects from old names, nonexistent devices, and disposed devices do not consume bootstrap limits in advance.

Successful GET requests provide a signed admission with a 10-second lifetime in HTML metadata. This proves rate limit consumption bound to the device, current path, origin, IP, and single-use jti; it does not grant device or account access. The browser sends it only on the first bootstrap and does not reuse it for reconnection. The WebSocket subprotocol proposes the fixed `mew-admission-v1` and `mew-admission.<증명>`, and only the fixed value is selected in the response. The proof is not included in URLs, referrers, app context, Service Worker, or logs.

The Worker removes externally supplied `X-Mew-Admission` and passes only signature-verified values to the DO. The DO rechecks the current device, owner, name, IP, origin, and expiration, then atomically consumes the jti in `mew_signal_admissions` SQLite before opening WSS. Consumption records are retained until expiration and limited to 128 entries. Reuse or forgery does not create a new socket. The new socket's nonce, browser key ownership, and final ticket checks are still performed.

The valid admission path skips D1 queries and rate limit writes for WSS. Missing or expired admission or an IP change falls back to existing D1 rate limit checks. In that case, the count reserved in HTML is not refunded. Older HTML and direct HTTP launch use the existing path. Mixing new HTML with an older launcher or version mismatches during rollout may conservatively consume additional counts, so the Worker, role-specific HTML, and hashed chunks are applied together. Forgery or explicit rejection is not bypassed through the client's older authentication path.

1. A signs the central nonce with the server key on every WSS connection. The central service verifies the registered public key and instance ID.
2. B opens `/central/signal?role=browser&bootstrap=1` WSS using the device path or instance ID. The central service checks the origin, registered device, IP, and device request limits. The DO binds the nonce, random subject, and optional central identity to that socket and sends a challenge. The session is an empty string for anonymous or identity-omitted connections.
3. B sends that socket's nonce, SDP offer, and Ed25519 public key. The central service consumes the nonce once and checks current device and browser revocations. When A creates a challenge/generation and sends ready, the central service signs a 60-second ticket for the instance, connection, browser key, SDP fingerprint, and trusted CF connection IP. Older versions obtain an existing HTTP launch, verify its signature, target, and session binding, and atomically consume it once.
4. A starts RTC preparation after ready and separately completes final ticket validation of the pinned central key, issuer, audience, algorithm, expiration, connection, negotiation, authentication mode, and IP. The answer fingerprint is signed with the server key, and B verifies it using A's registered key confirmed by the central service. The DO's host FIFO forwards answers and candidates after sending the ticket.
5. In the channel's first message, B presents the exact ticket and proof of browser key ownership. A local session for reconnection is accepted only from `session` in this message, and a trusted session must also match the saved public key fingerprint. An invalid session leads to the login screen without operation permissions. Challenge/generation values are not reused.
6. Before login, limited UI, authentication, and access request APIs are used. A local password or explicitly approved external identity applies the existing account's feature and file permissions. Central login and logout do not create or revoke local password sessions. Transports containing an identity also check the central session lifetime.

The browser's central connection proof and device answer verification, and the server and central service's `verifyRemoteToken`, use the shared `REMOTE_TOKEN_CLOCK_TOLERANCE` to allow **2 seconds** of clock skew. The tolerance missing from browser verification was aligned with the server, while the `iat` maximum age of 60 seconds and expiration, signature, issuer, and audience validation remain in place. If a future `iat` exceeds the allowed range, guidance to automatically synchronize the date and time on the connecting device and mew host is shown instead of a raw JWT error. The current time is not changed to the token's issuance time, and time validation is not skipped. Applying this fix to the central launcher requires the user to redeploy Mewlink; actual device clock skew and production application are checked separately.

Active connection leases last at most **60 seconds**, and B's renewal interval is **20 seconds**. A does not apply renewals before transport key proof is complete. Central logout terminates connections containing an identity while preserving identity-omitted local password connections and saved password sessions. Previous central member revocation is not a basis for new local permissions. Disposing of device registration terminates open signaling connections and A's connections. A revalidates the selected authentication method, current account, and lease on every request and at 1-second intervals. During central disconnection, only connections that negotiated reattachment remain within their existing lease; all others close immediately. A's policy change events also trigger validation. Existing WS and desktop per-feature permission revalidation and input leases are used together.

After the existing 10-second alarm check, the central DO sends a `renew` request specifying the connection ID to browsers that sent `serverRenewal: true`. The browser responds immediately only on the same connection where key proof is complete, allowing renewal even if the 20-second timer is delayed. Sending the request alone does not extend the lease, and responses are also subject to device, identity, and expiration checks. This request is not sent to older browsers, and new browsers connected to an older central service continue using the 20-second timer. Browser suspension or authenticated WSS disconnection does not extend the current lease, and negotiated reattachment also occurs only within the validity period below. Application requires the user to redeploy the Mewlink central service. Isolated validation checks the delayed-timer path and does not establish the cause of actual repeated disconnections or replace phone power-saving or external-network verification.

Browser RTC allows up to **5 seconds** for recovery from a transient `disconnected`. If it recovers in **less than 1 second**, it keeps the same transport without a recovery indicator or duplicate `connected` notification. If it persists for 1 second or longer, it indicates recovery status; if it has not recovered after 5 seconds, it switches to a new connection. The native helper's own cleanup limit remains separate at **15 seconds**. Repeated state events do not extend the deadline. On returning to `connected`, it preserves the same transport, app iframe, and input drafts and requests renewal. Recovery and termination both cancel all indicator and termination timers. `failed`·`closed`, actual DataChannel closure, and parent termination immediately clean up the transport. Authenticated WSS is cleaned up immediately if reattachment was not negotiated or if closure is normal, access is denied, or authorization is revoked. The existing 60-second lease expiration takes precedence even while waiting for recovery, and expired authorization is never restored. When the browser becomes visible again or receives `pageshow`·`online`, it immediately requests renewal of the existing session. Writes and commands are not replayed; per-request authorization checks, the central 10-second alarm, and the 20-second renewal interval remain in place. Decisions and verification scope follow [ADR 0081](../decisions/0081-mewlink-transient-recovery.md) and the [work record](../work/mewlink-transient-recovery.md). The basis for treating `disconnected` as a state that can recover naturally follows the [WebRTC state contract](https://www.w3.org/TR/webrtc/#dom-rtcicetransportstate).

### Reattaching the same RTC after a brief signaling interruption

When opening central WSS, the host limits the handshake to 30 seconds. On an open socket, it sends the existing JSON heartbeat every 20 seconds and checks for the matching JSON response from central before placing it in the asynchronous message processing queue. It waits 5 seconds for a response using monotonic time, retransmits once, and, if there is still no response after another 5 seconds, calls `terminate()` to run the existing abnormal closure and reconnection handling. It sends no duplicate heartbeats while waiting. While the event loop is running, disconnection detection takes approximately 30 seconds at worst; even if the first deadline runs late after sleep, it allows 5 seconds for rechecking. Successful transmission or the initial `pong` alone does not establish that the connection is alive, and send errors trigger the same termination. Timers and listeners are cleaned up when the socket closes. This check does not extend authorization or the lease. [Initial investigation](../work/mewlink-host-heartbeat.md) · [Follow-up policy and verification](../work/mewlink-efficient-recovery.md).

Under [ADR 0033](../decisions/0033-mewlink-signaling-resume.md), connections that negotiate `signalResume` in all of the central challenge, host nonce signature, browser request, and signed ticket preserve RTC and ongoing work during a transient WSS disconnection. Normal closure (code 1000), explicit denial, revocation, logout, and expiration do not use this recovery. Older versions retain the existing full reconnection behavior.

The browser signs the new socket's single-use nonce with its existing key, and central rechecks the same session's instance, origin, connection, generation, SDP fingerprint, key fingerprint, subject, optional identity, and revocation status. Reattachment restores only the existing lease. Expiration is calculated using the renewal request ID, the monotonic request start time, and central's remaining time minus a 1-second margin, so clock differences, network delays, and retries themselves do not extend the allowed time.

The DO retains up to 8 disconnected browser states in the `mew_signal_recovery` SQLite table and cleans them up based on the existing expiration time, alarms, new connections, and revocation. Open sockets are restored from attachments. A new host WSS signs the nonce and the list of authenticated connections it actually holds with the registration key; central compares these against current connections and retained state and resends only existing leases. After awaiting the host identity lookup, it rechecks the current host, browser, and stored state. An unprepared new host process does not revive previous peers. Browser waiting slots for reattachment and host authentication slots remain available even with 8 active peers.

Isolated Workers tests checked nonce, key, generation, and device mismatches, reuse, revocation, logout, expiration, hibernation, host replacement, and browser reattachment races. Stability tests with actual Workers, native RTC, and Chromium confirmed that HTTP succeeded in the same iframe and RTC without creating a new prepare when the browser and host WSS connections were disconnected separately. Uninterrupted operation is not guaranteed for forced termination in which the platform loses all socket state without a close callback. Reattachment failure or lease expiration leads to the full reconnection described below.

After final connection termination, sleep, or a network change, the central launcher automatically reconnects using a new WebSocket bootstrap, the same browser key, and the stored session. A new HTTP launch is used only in the compatibility path for older versions. The first retry after an ordinary failure starts immediately; repeated failures use a delay starting at 250 ms and capped at **30 seconds**, with jitter. On receiving an explicit `offline`, it waits using the presence mechanism below before creating a new RTC. The base intervals for this wait are 2·5·10·30 seconds, capped at 30 seconds including jitter. During full recovery, a hidden tab or an offline internet connection cancels timers and ongoing preparation and lookups; recovery resumes once on online, pageshow, or return to visible. Renewal and central reattachment for a live RTC remain allowed. Resuming does not itself extend the lease. Browser RTC disconnected waits up to 5 seconds for natural recovery before switching to a new connection, separately from the host helper's own 15-second cleanup limit. The existing app iframe and unsaved input are preserved, and the transport is replaced after verifying the same local account and authentication method through the new connection's `/api/auth/me`. If the instance, central/app origin, or previewDomain changes, the new prepared connection and existing iframe are cleaned up, automatic recovery stops, and the user is prompted to refresh. Existing app state is also not reused if the account or authentication method changes. In-flight requests on the terminated connection are canceled, and saves and commands are not automatically replayed. The DOM browser view and Mewpet conversations reopen read subscriptions without resending previous input. Explicit revocation, authentication denial, and logout clear stored tokens and stop retries. Remote desktop's separate video/input peer remains subject to manual reconnection. Reauthentication is required after 90 days of inactivity, a password change, or revocation of an approved connection; actual connection persistence while a phone sleeps and successful recovery over external networks are not guaranteed.

`GET /central/presence?instance=<기기 ID>` provides only `{ online: boolean }` without login. It is allowed only from the current and previous central origins and rejected from app origins. It checks ID format, registration, and revocation and is limited to 60 requests per minute per IP. Exceeding the limit returns 429 and `Retry-After: 60`; deleted or revoked devices return 404 and `code: instance-not-found`. It does not cache, forward central credentials, look up management sessions, issue launches, or prepare RTC. Lookups incur costs for rate-limit recording, device lookup, and DO state checks. This round trip is not added to normal initial connections, and an ordinary 404 from an older central version falls back to the existing full reconnection.

Recovery authentication through `/api/auth/me` is limited to 10 seconds from request start through completion of the JSON body; requests from previous generations and late responses are discarded. If initial authentication has not yet completed, the first recovered state becomes the baseline. If the previously verified account or authentication method changes, or an explicit 401·403 is received, the session is cleared and the user is prompted to log in again. Compatibility HTTP launches for older central versions and presence lookups also apply a 10-second limit through body completion and support cancellation. [ADR 0086](../decisions/0086-mewlink-recovery-efficiency.md).

If a destination tab closes during an asynchronous authorization check in the central DO, only that tab's send failure is cleaned up. This error is not escalated into an authentication failure for the host that sent the message. Actual host termination and authorization revocation close all dependent connections as before.

Central launches are limited to 30 per minute per IP and 60 per minute per device; signaling connections also have limits on IP frequency, pending connections per device, and total connections.

The existing bootstrap in [ADR 0048](../decisions/0048-mewlink-bootstrap-rate-batch.md) performs the IP launch 30, device launch 60, and IP browser signal 30 limit checks in a single D1 `batch()` after device lookup. Currently, valid HTML admission skips this duplicate call; without admission, a valid instance and path hint allow the device lookup to be included in the same batch. Each UPSERT checks in SQL whether the preceding counter exceeded its limit, preserving the order, 60-second window, shared existing counters, and behavior of not incrementing later counters after rejection. If one statement fails, the entire batch is rolled back and the connection is denied. Older HTTP launches and ordinary host/browser signal paths use the existing checks.

Role hints and subsequent key proof separate browser and host waiting slots and reserve capacity for host handshakes. Browser signaling is allowed only from central origins and rejected from app origins. Locally unauthenticated connections last at most 5 minutes, and central renew does not extend this deadline. Connection, work queue, body, and frame size limits retain the transport contract below.

Local account revocation is handled through existing local account, session, and permission changes. Local deregistration closes work and removes keys, then invalidates the central registration using a server signature. If central does not respond, an error instructs the user to delete the remaining registration from the dashboard. Retroactive revocation of downloaded materials or OS tasks already started follows existing permission boundaries.

`remote-access-dispatch.ts` binds a verified session lookup function to an in-memory duplex socket and runs the existing HTTP parser, Express router, and WS upgrade. Local session or permission revocation terminates the affected previous work and WS connections while retaining a restricted login transport. No additional messages are sent even if a Blob read completes or the next split chunk becomes ready after the socket closes.

## Protocol and resource lifetimes

The protocol version is **1** in `shared/remote-access.ts`. It is checked in the central challenge and A's authentication-complete message, and incompatible connections are rejected. The server name is fixed after initial registration; changing it requires deletion and reregistration. Production verification of version-specific updates and automatic key rotation remains pending.

| Limit | Current value |
| --- | --- |
| Single JSON frame / binary chunk | 32 KiB / 12 KiB (size before base64 encoding) |
| Extended HTTP/WS receive window | Initially 8 chunks / 96 KiB after negotiation; up to 256 chunks / 3 MiB after consumption. Unnegotiated HTTP retains 1–8 chunks; WS retains the existing send method |
| RTC send queue | Wait at 512 KiB or above; terminate if no progress is possible for 10 seconds |
| A's per-connection native IPC receive queue | UTF-8 total of 512 KiB including the frame being processed; at most 4096 queued items. Processes authentication and frames in FIFO order and removes unprocessed items on termination |
| A's pending native IPC send ACKs | At most 64 per connection, with at most 512 total across A's 8 connections. Terminates the affected connection if no response arrives within 10 seconds |
| Concurrent HTTP/WS work | After separation is negotiated, 16 each and 32 total per channel. Unnegotiated peers share 16 slots |
| Admission queue when concurrent work exceeds the limit | At most 64 per transport instance, with a 30-second wait. The same caps apply to the actual channel's shared app/resource queue |
| Concurrent browser connections | 8 per A |
| HTTP upload / single WS message and queue | At most 25 MiB each. Lower limits in existing APIs also apply |
| A's total in-flight HTTP bodies and WS assembly/send data | 64 MiB. Not a RAM limit for the entire OS process |
| Signaling message / pending processing / ICE count | 96 KiB / 128 per connection / 256 total in both directions per app connection |
| No initial HTTP response or upload progress | 30 seconds. After the response, streams end through cancellation or channel/authentication lifetime limits |

The browser queues new work when slots are full and first sends it when a slot becomes available. Requests from the app MessagePort and launcher/resource requests share admission on the actual DataChannel. After confirming `flowControl.separateStreams: true` in the response or socket open, HTTP and WS slots are separated into 16 each. FIFO order is maintained within each type, while blocked WS queues do not prevent use of free HTTP slots. Older versions and connections before negotiation retain the existing shared 16-slot FIFO. HTTP holds a slot until the response body completes; WS holds it until the connection closes. Cancellation, closure, or channel termination while waiting removes unsent work; queue limits and timeouts end in errors. The server cleans up completed work before sending the termination frame, and the browser returns a slot after sending the cancellation frame. Write requests are not automatically retransmitted.

The `request`, chunks, `end`, `cancel`, and credit for the same work forwarded through MessagePort enter a per-request send FIFO. Termination and cancellation do not overtake chunks waiting on RTC backpressure. Cancellation before admission immediately discards the unsent body; work already started sends preceding frames and cancellation in order before returning the slot. Late credit for completed work is discarded.

Even if `sendMessage()` in `node-datachannel` 0.33.4 returns `false`, accepting the frame into the RTC queue without an exception counts as a successful send. The helper sends only once and returns an RTC acceptance ACK, then applies the existing 512 KiB and 10-second backpressure limits to the queue. It does not retransmit the same frame. The return value is not an ACK that the remote app has completed the work. This is based on the installed version's [SCTP send implementation in libdatachannel v0.24.5](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.5/src/impl/sctptransport.cpp#L340-L359) and actual native load tests. Closed channels and actual send exceptions terminate the connection.

Pending native ACKs are counted per connection so normal transfers from multiple browsers do not consume one another's limits. Exactly 64 are allowed; the 65th send is rejected on that connection. Pending waits are cleaned up on termination, and late ACKs cannot affect a connection recreated with the same ID. Host regression tests verified three browsers each waiting for ACKs for 16 HTTP operations and 16 WS operations, as well as limit overflow, termination, and recreation of a single connection.

This change must be applied to both the local app/server and the central connection frontend. From the repository root, the user runs `npm run build` followed by `./mew restart` to apply the local version, updates central with `npm --prefix mewlink run deploy`, then refreshes the public device page. The agent does not build, restart, or deploy the running instance.

The existing optional fields `request.responseWindow` and `response.responseWindow` in version 1 retain 1–8 chunks. Older servers without these fields use the 1-chunk credit method; requests from older clients without the fields receive no initial credit. New peers use the consumption-based extension below. Entire files are not accumulated in a Blob for delivery, and download size follows the existing file API and stream. Large WS messages are split and reconstructed using sequence numbers. Early HTTP 403 responses and chunks arriving after cancellation are discarded without interrupting other work. Writes and commands are not automatically retransmitted; if results are lost, an error prompts the user to check before retrying. All streams, virtual sockets, and RTC child processes are cleaned up on termination, and child helpers terminate if no parent heartbeat arrives for 10 seconds.

### Consumption-based HTTP/WebSocket receive control

The `flowControl: { version: 1, maxWindow: 256, separateStreams: true }` from [ADR 0032](../decisions/0032-mewlink-consumer-flow-control.md) is included in HTTP requests and socket opens and used only when the same capability is confirmed in the response or `open`. `maxWindow` ranges from 8 to 256, and `separateStreams` is optional. Unnegotiated peers use the existing HTTP receive window and WS transmission, without batched credit.

New hosts also initially send only 8 chunks. The final consumer's `RemoteReceiveWindow` adjusts the window within a maximum of 3 MiB by accounting for request round-trip time, chunk processing cost, credit not yet received, and unread bytes. HTTP expands only after the actual reader consumes data, sending only the initial 96 KiB for unread responses. WS accounts for processing cost after chunk validation, decoding, assembly, and message dispatch. Credit is deferred to the next task and returned per consumption batch, giving the UI and small messages opportunities to run. The bridge's `forward` only passes through the final consumer's credit and adds no receive acknowledgment of its own.

Negotiated `credit.count` returns 1–256 credits in a single frame. The server's `RemoteSendWindow` rejects credit above the cap and releases waits on cancellation, socket closure, or permission revocation. The browser also rejects chunks beyond the window and discards scheduled returns for closed windows. Single-message, upload, RTC send, and server byte budgets remain in place. Base64 format is retained, prioritizing native conversion and using simple iterative conversion in unsupported browsers.

In the 2026-10-20 isolated mixed-load test with native RTC, Chromium, and both MessagePort endpoints, small WS latency p95 was 3 ms, small HTTP latency was 5.9 ms, and the maximum display frame interval was 16.8 ms while receiving 22.5 MB over WS. In a separate simulation of 100 ms round-trip latency, 4 MiB HTTP decreased from 4.48 seconds with the existing receive window to 0.55 seconds with the expanded window. Tests also covered 4× CPU slowdown, unread responses, slow readers, 16 persistent WS connections alongside HTTP, older versions, cancellation, and permission revocation. These figures are results from that isolated run, not total loading times on actual user devices or external networks.

`@mew/ui/browser-storage-scope` includes the local email and instance ID in localStorage and IndexedDB names. It separates files, tabs, drafts, and agent history by local account and A, replacing open IndexedDB connections when the scope changes. The existing origin-wide budget and retention period for regenerable localStorage caches apply across multiple A instances. Connection termination cleans up regenerable bodies, transcripts, and transfer history in the current scope while **preserving unsent drafts, PDF annotations, open tabs, and settings**. It follows the [browser storage contract](browser-storage.md). It does not replace global fetch, WebSocket, or localStorage.
