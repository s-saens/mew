## Ownership and storage

- Git connections are scoped by Mew email, provider ID, and host. They are not migrated from existing `gh` authentication, environment tokens, or SSH keys. Accounts remain disconnected until their first connection, after which connections persist across server restarts and Mew logins.
- The provider contract in `server/git-providers.ts` owns device authorization initiation, polling, token refresh, account verification, host/repository path validation, and the Git authentication username. The initial implementation is github.com. GitLab and Enterprise are not yet registered and require adding providers and their UI/authentication flows.
- `GitConnections` uses SHA-256 filenames derived from the user, provider, and host in `MEW_DATA_DIR/git-connections/`. Access and refresh tokens, expiration times, and authors are encrypted with AES-256-GCM, with the ownership key bound into the AAD. Directory permissions are 0700; key files and atomically written files use 0600. The key and ciphertext must be backed up together. This does not isolate secrets from users with OS file access permissions.
- Tokens and device codes are not included in APIs, browser storage, remote URLs, Git argv, or AI input. Only the user authorization code is returned for the user’s own login operation. API responses are no-store.
- Disconnecting removes the corresponding Mew connection. GitHub web sessions, other Mew users, and OS gh authentication are retained. Provider-side authorization is revoked in GitHub’s Authorized OAuth Apps.
- Account deletion through either the UI or CLI removes Git connections for registered providers. OAuth operations capture the account creation timestamp at startup and compare it with the current account on asynchronous responses, status queries, and restarts. Tokens from previous operations are not stored for deleted accounts or accounts re-registered with the same email. Retention of personal settings is distinct from retention of external credentials.

## API and login

- `GET /api/git-connections/github`: Returns configuration availability, the user’s own connected account, and the user’s own login operation.
- `POST` on the same path: Starts the OAuth device flow or resumes the user’s own in-progress operation. Different accounts can proceed concurrently. Uses the built-in public Client ID by default, replacing it if `MEW_GITHUB_CLIENT_ID` contains a non-whitespace value. Token requests follow the provider’s interval, slow_down, and expiration rules.
- `DELETE` on the same path: Removes the connection and in-progress operation. Tokens arriving late are not stored, even if cancellation occurs just before completion.
- `POST /:id/stop`: Cancels the user’s own operation. `POST /:id/browser`: Opens the fixed GitHub authorization URL in the [login virtual screen](login-desktop.md). Uses the same git or filesWrite permission as connection operations.
- The connection API requires login and the git or filesWrite capability. As a personal integration setting, it does not require access to all repository files. Existing project and capability permission checks for actual Git APIs remain in place. The old `/api/git/github-auth` path is a compatibility path that retains the existing Git capability and full-project access checks.
- The external GitHub authorization link can be used without separate browser permission. The login screen inside the panel requires Chrome, Xvfb, FFmpeg, and Python input handling on Linux/WSL; gh is not required.
- When disconnected or expired (including authorization revocation confirmed by GitHub for remote operations), explicit operations return HTTP 428 `git-auth-required` before making changes. The UI opens the shared login dialog and retries the originally serialized request exactly once after success. It does not continue after cancellation or logout. Retry headers contain the URI-encoded Mew owner and workspace, which the server compares against current values. General failures are not automatically rerun.
- Login operations exist only in memory and must be restarted after a server restart. Expired access tokens are automatically replaced using refresh tokens when querying account status or checking the connection for a Git operation. Concurrent refreshes for the same account, provider, and host within the server are coalesced, and the connection ID is retained. If a connection is disconnected or reconnected during refresh, a late response does not overwrite it. Login is required again if the refresh token is absent, expired, or revoked. Existing stored connections have no refresh token, so users must log in again once after this change is applied. Temporary network or provider failures return HTTP 503 without removing the stored connection. Refreshing tokens issued through Device flow uses only the public Client ID ([GitHub’s official refresh contract](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#refreshing-an-access-token-with-a-refresh-token)).

## Git execution boundaries

- The requesting user’s author information is passed per execution for regular, per-file, and AI commits and for cherry-pick/revert committers. The ID and login returned by GitHub are used to construct the private address `ID+login@users.noreply.github.com`. Shared `user.name` and `user.email` settings are not modified. When cherry-picking an existing commit, the original author is retained according to Git rules.
- The explicit environment allowlist for `simple-git` 4 includes only server-defined author and committer names/emails and the temporary `GIT_INDEX_FILE` for AI commits. Per-account write environments remove inherited `GIT_*`, editor, pager, and authentication token variables before adding identity information, and do not disable safeguards for command execution, configuration includes, or abbreviated options. The remote authentication path separately adds a server-owned credential socket and fixed configuration path to this environment and runs through the existing `execFile` path.
- Existing incidental commits for file creation, copying, moving, deletion, uploading, and replacement are created only when the account is connected. If disconnected or using an unsupported remote, the file operation proceeds and the commit is skipped. Explicit commits during file saves and history restoration check the connection before writing. Per-file commits do not include other staged files.
- Title bar branch creation and switching (`GET/POST /api/git/branches`) are local operations that check the Git capability, access to all project files, and the workspace in POST requests. They do not require a GitHub connection or remote lookup. Only actual local, remote, and tag refs from `for-each-ref` are allowed as a base; commit hashes are validated separately. `switch` runs without forced switching or stash. Selecting a remote branch directly creates a tracking local branch; creating a differently named branch with a specified base does not automatically set an upstream. Duplicate Pull/Push and branch operations on the same repository are blocked.
- Account selection follows the branch’s upstream remote → origin → sole remote order. Local repositories without a remote use the GitHub connection. Ambiguity among multiple remotes requires configuration.
- Pull/Push checks the registered provider and host of the actual fetch/push URL. GitHub SSH addresses are normalized to HTTPS at execution time without changing stored remotes. Arbitrary hosts, local paths, embedded credentials, multiple push URLs, and repository URL rewriting are rejected.
- Sending `Accept: application/x-ndjson` to `POST /api/git/remote` streams `progress`, `complete`, and `error` events starting when Git actually runs. Authentication, workspace, and remote validation failures return existing HTTP statuses before the stream starts, including 428 when login is required. Git runs with `--progress` and `LC_ALL=C`, and only phase, percentage, and object counters are extracted from stderr. Raw logs, URLs, and credentials are not transmitted. `complete` is sent only after Git exits successfully; 100% transfer does not mean remote success. Client disconnection neither reruns nor forcibly stops Git. Regular JSON responses remain supported.
- Credentials are passed only through a temporary Unix socket and credential helper for the command. The helper accepts only the exact HTTPS host and repository path. OS helpers, global/system configuration, additional authentication headers, cookies, interactive prompts, and HTTP redirects are not used. The socket is removed on exit. This path targets the supported operating systems Linux, macOS, and WSL.
- AI task files receive only the Mew owner and connection ID, provider, and host. The current connection ID is checked at execution start and immediately before each commit, and work does not continue with a disconnected or replaced connection. Tokens are not placed in AI prompts or input.json.
- General agents fix author and committer environment variables to the Mew account logged in for the start request. If a GitHub connection exists, they use its name and private email; otherwise, they use the Mew profile name and login email. Existing author and date environment variables from the server and runtime are overwritten or removed, and shared Git settings and tokens are neither changed nor passed along. Detached supervisors and ACP children inherit this information and retain the initial account across reconnections and process recreation. This does not apply retroactively to already-running supervisors, so start in a new tab. Internal execution without an account retains the existing environment.
- Regular terminals, cloning into external folders, and agent remote authentication use the existing OS execution environment. Account selection in the app is not a shell sandbox, and working trees are not cloned per user. Commit signing and hooks follow existing Git settings.
