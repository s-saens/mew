## Connection path

Uses direct DTLS-SRTP and DataChannel connections between an external phone and the login host. Mew HTTPS/WebSocket handles only authentication, approval, and negotiation; it does not add TURN or server-side video relaying. Installation file readiness is distinct from a successful external phone connection. Success in Chrome on the same PC is not reported as external-network verification.

The default STUN servers are Google `stun:stun.l.google.com:19302` and Cloudflare `stun:stun.cloudflare.com:3478`. Browsers use the full list. Because libdatachannel/libjuice selects one STUN server per agent, the native host configures one at a time and performs bounded retries with the next server on failure before any input channel opens or after a 12-second discovery delay. The maximum is 3 distinct servers; the default configuration makes 2 attempts. An empty ICE list does not query STUN. [libdatachannel implementation](https://github.com/paullouisageneau/libdatachannel/blob/v0.24.5/src/impl/icetransport.cpp) · [Cloudflare public STUN](https://developers.cloudflare.com/realtime/turn/faq/).

Each negotiation includes `negotiation` 0–2. The parent's authenticated WebSocket and current session ID are retained, and only the transport agent is recreated. The previous peer and input channels are closed and temporary mappings cleaned up before a new offer is sent. The browser, server, and host all ignore previous answers/candidates. Each native attempt retains strong references to the motion/control channel wrappers and explicitly closes them on termination. This prevents the shared lifetime bug where receive-only channels were prematurely destroyed by JS GC, closing SCTP. If the peer fails before the first input connection, the browser retains the WebSocket and waits for the next offer or the 20-second timeout. Asynchronous video statistics also apply only to the corresponding peer and negotiation generation. Sessions whose input channels have already opened do not retry this way. Capture frames, GPU devices, and encoders are not restarted; a keyframe is requested when the new track opens.

## Automatic NAT preparation for active connections

`native-connectivity.mjs` observes the ports of actual ICE host UDP candidates. If a direct connection is established within 2 seconds, it does not change the router. After that, it attempts PCP → NAT-PMP → UPnP IGD using only private IPv4 candidates on the same interface as the OS-selected route. On Windows, the login host directly queries the kernel-selected IPv4 gateway and source through `GetBestRoute2` in the system `iphlpapi.dll`. This removes PowerShell/CIM startup process delays and the 2.5-second timeout and does not substitute WSL's virtual default gateway. Linux locates `iproute2` by absolute path in the standard `/usr/sbin`, `/sbin`, `/usr/bin`, and `/bin` directories and uses the selected interface and preferred source from `ip -j -4 route get 1.1.1.1`. Mac uses the IPv4 gateway and interface from `/sbin/route -n get -inet 1.1.1.1`. This fixed address is used only for a local kernel route lookup; no packets are sent. It does not use default-route list order or the first NIC, or bypass VPN/policy routes through an arbitrary physical LAN router. Gateway, mapping target, and protocol cannot be specified through GUI or HTTP input. [Windows route API](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2) · [Linux route lookup](https://github.com/iproute2/iproute2/blob/main/man/man8/ip-route.8.in) · [Apple route contract](https://github.com/apple-oss-distributions/network_cmds/blob/main/route.tproj/route.8).

On Linux, actual address ownership is queried asynchronously for each selected interface with `ip -j -4 address show dev <dev>`. The returned interface, IPv4 address, and preferred source are cross-checked, excluding loopback and host scope. Each query retains a 2.5-second timeout, a 16KiB output limit, and an AbortSignal; it does not query all NICs or fall back to synchronous `os.networkInterfaces()` after failure. This is a shared fix to avoid the event-loop stalls identified in the [Mewlink initial connection investigation](../research/mewlink-startup-latency.md). Mac interface checks retain the existing implementation, and this Linux verification is not treated as a Mac measurement.

PCP/NAT-PMP exchanges use only a UDP 5351 socket connected to the OS default gateway. Response opcodes, internal ports, and the PCP nonce are checked. PCP does not use the third-party address option. A successful public external IPv4 address and port are passed as an srflx candidate for the original ICE socket. The mapping and peer UDP sockets are separate, and the mapping targets the observed media ICE port, not the control socket. [PCP](https://www.rfc-editor.org/rfc/rfc6887.html) · [NAT-PMP](https://www.rfc-editor.org/rfc/rfc6886.html).

UPnP SSDP sends discovery requests on the selected interface with TTL 1. It accepts responses only from that interface's default gateway IPv4 address, and description and control URLs use only HTTP at the same IP. It rejects redirects, URLs with credentials, external hostnames, and DTDs/entities; responses must be no larger than 64 KiB, and each request must complete within its time limit. It only retrieves the external address and queries, creates, or deletes specific UDP mappings for fixed WANIP/WANPPP services. Creation requires confirming that no mapping exists, and renewal or deletion requires matching the internal address, port, and random ownership token. It does not replace or delete another app's mappings. [IGD service contract](https://upnp.org/specs/gw/UPnP-gw-WANIPConnection-v2-Service.pdf).

A lease of 120 seconds is requested, and only responses of 1–300 seconds are accepted. UPnP also checks the lease actually queried. Permanent or excessively long mappings are rejected and cleaned up, with no retry in permanent mode. Active mappings are renewed halfway through the lease; renewal is canceled and mappings deleted on termination, approval revocation, or negotiation replacement. If cleanup fails or the process is forcibly terminated, the accepted lease expires within at most 5 minutes. Reuse is allowed only after a stop ACK confirms capture has stopped and network cleanup is complete; hosts that do not ACK within 3.5 seconds are discarded. Cleanup failure does not extend the lifetime of screen/input approval.

Idle hosts do not create STUN agents, NAT discovery, mappings, or renewal timers. Router automation can be disabled with `MEW_DESKTOP_AUTO_NAT=0`. This setting is independent of STUN. Route lookup failure is diagnosed as `route-unavailable`, and the absence of a private IPv4 router route matching the candidate as `no-router`. These conditions do not block direct IPv6 connections or STUN and are not hidden as installation success.

On parent termination or SIGTERM, input and connection approvals are revoked first, then native capture and NAT cleanup are given up to 3.5 seconds. On completion, the race timer is removed so it does not delay a quick exit. OS adapters, the parent channel, and RTC are released after the worker exits. POSIX parents forcibly terminate only after 4 seconds following SIGTERM. The Windows login supervisor's parent-termination guarantee is maintained separately.

## Windows firewall preparation

`prepare-windows-network.ps1` prepares only UDP reception for the installed `runtime/node.exe`. It derives the managed rule name from a hash of the executable's canonical path and allows only that program across all Windows network profiles. It does not change TCP, other apps, global firewall settings, or permanent router rules. Without administrator privileges, it requests OS UAC using the fixed installation script and target path. The user grants approval in Windows.

Existing explicit app blocks and conflicting rules with the same name are preserved, and preparation stops. UAC denial, organizational policy, and query failures are shown as separate warnings, and `MEW_NETWORK_READY` is not emitted. The helper-file installation marker indicates only file, binding, and GPU module status. Network preparation failures do not delete installed files or automatically repeat OS approval prompts. Users can request network preparation again with the same `desktop-setup`. Development agents do not run this installation procedure against an actual firewall.

Read-only diagnostics distinguish explicit blocking from the absence of an allow rule and pass that distinction to failure guidance. An app allow rule alone does not guarantee that organizational policies or other filters have also been lifted. [Microsoft firewall rules](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule).

## Mac/Linux network permissions

Mac/Linux use the same native code for STUN retries, temporary NAT mappings, encrypted video/input, and shutdown lifetime handling. Successful preparation of a Windows UDP rule is not shown as POSIX network approval.

The Mac app's own Info.plist includes `NSLocalNetworkUsageDescription`. macOS 15 and later may require Local Network permission for local UDP and router access, separately from Screen Recording, Accessibility, and firewall inbound permissions. The approval target varies with the responsible app determined by the OS and the execution environment, with exceptions for cases such as Terminal/SSH child processes. User denials, the TCC DB, and global network settings are not changed. [Apple local network contract](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

`network-support.mjs` uses the fixed `socketfilterfw` executable on Mac to read only global/block-all/app status and pass it to failure recovery guidance. On Linux, readable fixed UFW settings and `firewall-cmd --state` are used to provide guidance on the active firewall's inbound UDP policy. It does not run `sudo`, use administrator helpers, allow ports globally, or change existing rules. Active UFW/firewalld status alone is not taken as proof that packets are actually blocked. Insufficient permissions, missing tools, and query failures are treated as unknown and do not block host startup. Diagnostics run in parallel with video preparation, and query output, personal paths, and rule lists are not saved to files. If Linux firewall inbound policy blocks the connection, the operator must authorize it under that policy.

## Errors and verification scope

`network-status` reports only candidate counts (host/srflx/public IPv4/IPv6), whether discovery is complete, and automatic mapping status. Addresses, SDP, ICE credentials, and screen contents are not written to files. The browser distinguishes address discovery failure, connection path failure, and video decode failure after the path/input is ready. Mapping success alone is not shown as a successful external internet connection. Connection notifications and completion are shown only when both input channels and video decoding are ready.

Checks:

- `remote-desktop-connectivity.test.ts`: Tests PCP/NAT-PMP responses, nonce/port checks, and renewal/deletion over real isolated UDP; UPnP ownership, permanent lease rejection, and external URL blocking over isolated HTTP; cancellation of late mappings; and STUN agent replacement and isolation of stale negotiations. Also simulates the Windows native route ABI, errors/cancellation, and Mac/Linux selected IPv4 interfaces, multiple NICs, service PATH, preferred source, VPN/IPv6-only/missing routes, and read-only firewall diagnostics.
- `remote-desktop-nat-webrtc.test.ts`: Uses real libdatachannel, Chromium, and OS route lookups on Windows or opt-in Mac/Linux, and removes internal host candidates and address candidates from SDP. Establishes encrypted connections and successfully delivers synthetic input twice using srflx candidates forwarded only through a test-only UDP NAT, then deletes each mapping. Checks channel wrapper lifetimes by forcing native Node GC twice during an active connection and then delivering new synthetic input. Preserves each originating socket across multiple browser interfaces. Does not modify real routers, firewalls, screens, or keyboards. POSIX opt-in specifies `MEW_DESKTOP_TEST_NATIVE_HELPER` for the isolated helper and requires a real private IPv4 route. Being able to run this fixture on Mac does not mean execution on a real Mac has been verified.
- `remote-desktop-network-install.test.ts`: Simulates rule and UAC functions in Windows PowerShell to check preservation of blocks/conflicts, reuse of valid rules, fixed program/UDP scope, and approval cancellation. Does not perform actual administrator approval or firewall changes.
- `remote-desktop.test.ts`·`remote-desktop-readiness.test.ts`: Checks authenticated negotiation replacement, blocking of previous answers/candidates, browser retry waiting after failure, isolation of late video statistics from previous peers, and connection notifications for the new screen.
- Retains the existing resident, direct transfer, notification, installation, and browser checks.
- `remote-desktop-shutdown.test.ts`: Checks the sequence of waiting for NAT/capture cleanup that takes longer than the previous 500ms before releasing RTC, the timeout for unresponsive cleanup, and closure of the parent channel even when the OS adapter fails.

Removing only the channel-owning reference in the isolated helper reproduced input connection loss after GC, confirming the regression check's detection scope. Linux ran as a Linux process in WSL and does not substitute for verification on a physical Linux GPU or the external internet.

Actual first display, reconnection, sleep/lock, and approval revocation on LTE/5G phones and home routers must be checked after the user applies the changes. Do not label this isolated NAT check as verification on a real carrier network. Automatic direct connections can also fail with unsupported routers, CGNAT, or complete UDP blocking. Manual port mapping is not the default usage procedure. Adding a separate relay is outside the scope of this work.
