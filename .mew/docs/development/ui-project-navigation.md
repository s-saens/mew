## Sticky Ancestor Rows in the File Explorer Tree

`TreeHeader` in `FileTree.tsx` keeps expanded-folder and parent-Documents rows sticky within their child lists. Rows are 1.75rem high, stack by ancestry, leave at the list end, and stop sticking when collapsed. Restored at the user's renewed request after temporary removal on 2026-10-06.

The list's existing 2px top spacing is subtracted from the sticky position through `--tree-sticky-inset`. Sticky rows connect without gaps from the top of the scroll area so content underneath does not show through. Files, documents, and MOCs reserve `scroll-margin-top` equal to the ancestor row heights so the tab position indicator is not obscured. Compact trees inherit the outer scroll area's adjustment.

Each folder and document node uses `isolate` to create a stacking context. Its sticky row covers its child list with an opaque surface, while outer ancestor guide lines appear continuously in front of descendant nodes. Guide lines retain their existing 2px left position and 14px hierarchy spacing and do not intercept pointer input. Existing selection, hover, focus, opening, collapsing, menus, and dragging are preserved.

`server/sidebar-sticky-ui.test.ts` validates coordinates and gap-free alignment of three levels of sticky rows in PC/mobile file and document trees, hierarchy-line pixels in captures of both themes, release at each child list's end, collapsing, file clicks, and tab position indicators.

## File explorer touch menus and moving items

Selected file, folder, Documents document, and subproject rows in the file explorer use a `bg-surface-raised` background, without adding a theme-colored border or ring to the selected state.

`useTreeTouchGesture` distinguishes touch from mouse input by the actual pointer type. When touch starts, it disables native `draggable` on that item and prevents the browser's early `dragstart` and `contextmenu` from preempting the long-press menu. Pressing the mouse again restores native dragging.

- Starting at 500ms, highlight the pressed row with `bg-surface-raised` and keep it highlighted while the menu is open. Clear the temporary highlight when the menu closes or touch is canceled, without changing the existing active file.
- Prepare to move starting at 350ms, the same as tabs and Dock, so dragging can begin without an additional wait after the browser's long-press feedback. After preparation, movement of at least 12px immediately enters move mode and highlights the original item and filename preview. Releasing after holding still for at least 500ms opens the item menu. Holding still alone does not move a file.
- Movement of at least 12px before move mode cancels the long press and preserves default scrolling. During a move, a non-passive touch listener blocks scrolling, and the list scrolls automatically at its edges.
- Touch dragging shares the existing `dragstart`, `dragover`, `drop`, and `dragend` handling and path MIME type. Synthetic clicks after a menu or move are ignored, but the next intentional tap is accepted immediately. Touch cancellation, multitouch, Esc, loss of focus, screen hiding, and unmounting clear timers, previews, and the scroll-saving lock.

Verification: `server/sidebar-touch-ui.test.ts` uses actual touch events in isolated Chromium to check taps, menus, moves, holding still, cancellation, scrolling, external drop targets, subsequent click blocking, and returning to mouse input on the same device. On 2026-10-04, immediate movement after a 400ms hold and menu opening after a long stationary hold were confirmed. This does not replace vibration verification on physical iOS and Android devices.

## File explorer top create buttons

`useSidebarCreate` remembers the last selected directory and tree scope in the file explorer separately from the editor's active document. A folder uses its own path; a file uses its parent path. It distinguishes the root from Documents and clears the selection and pending requests when the working root changes. Subprojects also select their own paths as creation targets, like regular folders. Only the adjacent arrow switches projects. The top `SidebarCreateButtons` sends file and folder creation requests to only the selected scope and is hidden from guests.

Documents follows the [parent and child document contract](document-pages.md). Selecting a representative file uses its parent document as the creation target; selecting a standalone Markdown document uses it as the target for creating its first child. The document view has a single top button, **New Document**, and the row's **+** uses the same name-entry flow. Clicking a name selects it; double-click or Enter opens its body in the current tab. Ctrl/Cmd+click toggles selection, and Ctrl/Cmd+Enter opens a separate tab, following the [explorer selection contract](../features/projects-files-search/file-folder-exploration-and-operations.md#selection-opening-and-context-menus). The arrow only changes the child list, and the representative file is hidden from that list.

Creation shares the existing inline name entry, validation, and API in `FileTree.startCreate`. Clicking a button alone does not save a file with an arbitrary name. Collapsed Documents is expanded first, and received requests are consumed once and removed so that the input does not reappear when expanded again. File and folder creation in subprojects also shows inline input at the selected path in the current tree. Documents creation retains the Documents API scope.

## Subproject switching

Under [ADR 0004](../decisions/0004-subproject-folder-exploration.md), direct and nested subprojects appear as regular folder rows in `FileTree`. They follow their actual locations and normal sorting; clicking, touching, Enter, or Space on a folder toggles expansion. Opening, creating, and uploading files inside them, expansion, child-cache restoration, and file-location display work as for regular folders. Descendants under collapsed ancestors are not lazy-loaded. A project icon and a separate `SubprojectLink` arrow are displayed; only the arrow opens that folder as the active project. The arrow is disabled for anyone other than the owner, and file browsing and operation permissions follow existing rules.

`App.openSidebarProject` passes the current root and tree scope as `{ path, workspace }` to `POST /api/subprojects/open?project=<scope>`. The server checks the owner role, matching source root, actual subfolder, `.mew` directory, and file viewing permission, then calls the existing `switchWorkspace`. If the source root has changed, it returns 409; links, parent-directory escapes, and regular folders are rejected. Projects within Documents are also resolved using paths in that scope.

The response is applied through the existing `applyWorkspace` to restore the per-account project list and per-root UI. Only successful absolute paths are remembered, and duplicate paths are merged into one. A shared ref prevents duplicate switch requests. The `expandedSubprojects` storage field remains for compatibility when reading old state; new saves contain an empty array, and the old separate project section is not restored. Regular file-tree expansion state and the child-list cache are used, and the command menu on project rows remains hidden.

## Fast root project switching

Reduce waiting within the contracts for per-account active roots in [ADR 0200](../history/decisions/0200-mew-account-active-workspace.md), SPA switching in [ADR 0086](../history/decisions/0086-mew-root-project-spa-handoff-and-cache.md), and preserving agent work in [ADR 0092](../history/decisions/0092-mew-agent-survives-root-project-switch.md). Do not switch to inactive roots in advance to read actual folders or files.

**Switch state and selection.** While `switchingRootProject` is true, `ProjectLoadingOverlay` shows a central, translated accessible status without darkening or blocking screen input. Reduced motion disables rotation. Root/subproject entry shares this state; only the current operation clears it in `finally`. It ends on completion/failure unless session restoration continues. Do not restore removed tab-bar status text without a user request.

| Selection during a regular root switch | Behavior |
| --- | --- |
| Different pending target | Start the new POST immediately; abort the obsolete POST and unapplied agent preparation |
| Same pending target | No-op |
| Currently displayed root while another is pending | Send a POST: cancellation cannot undo a server-committed switch |

Request identity guards success, errors, and cleanup, preventing obsolete responses from replacing the latest screen or clearing its loading state. Mouse, touch, and Alt+number share this behavior. Retain subproject/worktree operation locks.

**Read ownership and prefetch.** UI metadata uses cache-owned abort signals:

- Selection cancels reads outside the displayed root and new target; replacement confirmation cancels the old root's remaining reads. Failed replacement still lets the displayed root restore. Remove a pending entry before aborting so immediate return starts a fresh read. Ignore canceled transports' late responses for cache warming and replacement-request removal.
- `App.openRootProject` starts absolute-root account UI and, when agents/terminals are used, agent-tab queries alongside the POST. Initial/expired UI reads reuse identical in-flight requests. `AgentPanel.preparedTabs` accepts only that switch's promise; occupancy refetches still read the server. Same-account switches from another connection, subproject entry, and initial display use existing queries. Other accounts cannot change this screen.
- Hover/focus on an inactive project row preloads per-account/absolute-root UI metadata, with at most 2 speculative queries. Actual selections are uncapped and share requests. Do not prefetch files, trees, or session occupancy. Permission changes reset cache/restoration generations, discard old-permission replies, and refetch.
- Registered-project selection preserves the path-list array, avoiding account-list saves. Within the logged-in App, reuse project icons through an LRU of 4 entries, 1MiB, and 60 seconds; clear on permission changes or icon saves. Preserve account/root boundaries and the shared icon canonical source.

**Snapshot limits.** `WorkspaceSnapshotCache` belongs only to a logged-in `EditorApp`: screen state allows 12 roots/1MiB; first-level trees allow 24 root/scope entries/1MiB. Snapshots last 60 seconds; entry/byte overflow evicts LRU entries, and large entries are not cached. Add no localStorage ledger or server cache. Permission changes clear both caches; account changes replace App.

**Applying state and preserving writes.**

- After server confirmation, apply cached UI/first-level trees immediately. Always reread the tree in the background; change-signal reads also update cache. Coalesce presence signals during the POST, then check the current root once. Sequence numbers reject older replies. Matching `path`, `projectPath`, and `docsPath` in POST/notification replies skip reinitialization; changed Documents paths clear/refetch tree cache. Before the initial root is known, avoid duplicate authenticated tree/project-list queries.
- Leaving before the 500ms save delay writes the snapshot to the **previous root**. Serialize account UI PUTs; do not send pending writes after account App disposal. Keep newer local snapshots over overlapping in-flight GETs.
- `useTabs` restores all panes/tab shells in one update without reusing previous-root tabs by name. Remove other API scopes, including old Documents, so they cannot save under the new root. Preserve account/root body-memory LRU and asynchronous IndexedDB reuse. Cached bodies appear read-only without a loading overlay; verify only active-tab permissions/version per pane and skip retransmission on a match. Block editing, collaboration seeding, and comment operations until verified; never display old-root bodies under new tabs. See [File Body Retrieval and Cache Restoration](file-loading.md).
- Apply tree, body, and document-rule replies only for the current switch generation, including A→B→A. Earlier generations cannot overwrite body/cache. Failed switches retain the current root and screen.

Validation: `workspace-snapshot-cache.test.ts` checks reuse, in-flight request coalescing, LRU/byte/expiration limits, retries after failure, and permission invalidation. `server/workspace-switch-ui.test.ts` loads the actual App, useTabs, FileTree, project selector, and docking into isolated Chromium and controls network responses to check that metadata requests start before POST completion, warm returns issue 0 additional UI GET requests, caches appear while tree/body refreshes are pending, duplicate notifications are handled, closing the last file tab is saved, Documents scopes are isolated, stale body responses are discarded, and switch failures are handled. Because this test substitutes other panels and editor renderers, its results must not be interpreted as measurements of total latency involving the actual server, large editors, and agent reconnection. `server/agent-command-ui.test.ts` separately checks normal initial queries and reuse of prepared queries in the actual AgentPanel.

On 2026-10-19, 6 cache tests and `server/workspace-switch-ui.test.ts` confirmed that no switch POST, file, tree, or agent occupancy requests occur before selection; prepared requests are reused; warm returns issue 0 additional UI/icon queries; late metadata is discarded after permission changes; and switching and panel restoration work. Total switching latency in production was not measured.


## Switching worktrees within the same project

[Decision 0068](../decisions/0068-project-worktree-context.md) separates the visible project from its file-operation root. In `GET/POST /api/workspace`, `path` is the physical root and `projectPath` the logical project; older responses without `projectPath` use `path`. The account ledger stores them as `activeWorkspace` and `activeProjectPath`, respectively.

- For normal project selection, `POST /api/workspace { path }` changes both roots to the target path and restores that project's saved screen. When moving to an existing worktree through Git branch selection, the request uses `{ path, worktree: true, workspace: <출발 실제 루트> }` and preserves `projectPath`. This operation does not add the worktree to the separate project list.
- The server checks owner/manager permissions, a matching source root, the Git top-level paths of the current and target folders, a shared Git common directory, and the target's registration in `git worktree list`. If the account's actual or logical root changes during asynchronous Git checks, it rejects the request with 409. If target validation fails, it preserves the current project and does not rename or move folders or force a Git switch.
- The project name, account UI ledger, docking and popup storage keys, mobile panel state, editor pane and tab structure, and `AgentPanel` identifier use `projectPath`. Within the same logical project, panels are not remounted and another project's layout is not restored. Files, Git, navigation, search, and body caches use `path` to query the target worktree again.
- When the working root changes within the same logical project, `useTabs` carries over open relative paths and the pane and tab structure, and removes previous bodies. It reloads target content and permissions starting with active tabs; inactive tabs follow the existing lazy-loading rules. Files missing from the target appear as read-only errors so that previous bodies are not saved as new files. External absolute-path files retain their existing external file scope.
- Before creating or switching branches, complete the autosave queue and in-flight saves, and save modified tabs, including external files opened by absolute path. Block new edits and autosaves during preparation, abort the switch if saving fails, and do not immediately retry failed saves automatically. If the optional `workspace` supplied with a file save request differs from the request's actual root, the server rejects it with 409. Late save and body responses from the previous root are not applied to a screen whose switch generation has changed.
- Existing agent and terminal tabs and running sessions retain their original cwd. The default cwd for new tabs is updated to the selected actual working root. Switch notifications for the same account and path isolation between accounts follow the existing contracts.

This switch uses an existing worktree without copying files, checking out, or swapping physical paths. The target tree, bodies, and permissions must be queried again, and total switching latency on the actual server requires separate measurement.

### Confirming and creating missing project paths

On ENOENT, `listEntries` checks `lstat` and `stat` toward the parent directories to find the nearest existing directory and the first missing name. `GET /api/fs/entries` returns 404 and `{code: "MISSING_DIRECTORY", missing: {path, existingPath, missingName}}` only for genuinely missing directories. Files, permission errors, and broken symbolic links are not classified as creation targets. The client distinguishes this response using `MissingDirectoryError`, without parsing error strings.

If the path the user navigates to does not exist, `LinkProjectDialog` displays a translated question and the full creation path in the shared `ConfirmDialog`. Cancel preserves the entered path, and the owner/manager-only `POST /api/fs/directory` `{path}` is called only after confirmation. The server checks the path again and creates intermediate folders with `mkdir({recursive: true})`. Already-created directories are treated as success, and files are not overwritten. After creation, it browses that location without automatically opening the project. Request sequence numbers are used to ignore query/creation results arriving after closure or navigation to another path, and navigation, closure, and duplicate execution are blocked during creation. An initial query failure for the default path does not automatically open a confirmation dialog.

Validation uses `server/fsBrowse.test.ts` for nested paths, queries without writes, races involving existing directories, and distinctions between files, permissions, and broken links; `server/access-policy.test.ts` for actual HTTP metadata and owner creation permissions; and `server/project-dialog-ui.test.ts` for creation confirmation, cancellation, retries after failure, and translations.

### Saving and detecting file browsing favorites

The shared `FileBrowserFavorites` sits below the title and above the address bar as its own collapsed dropdown. Because this is a composite list with separate navigation and removal buttons, it uses `FavoritesDropdown` within the same shared favorites component instead of the single-select `SelectField`. The list is portaled into the nearest `DialogFrame` to remain within the modal focus boundary, and its fixed position is adjusted upward or downward to fit the visual viewport. It scrolls within a maximum of 280px and supports Tab, arrow keys, Home/End navigation, Enter/Space activation, `useOverlayDismiss` Esc/back dismissal, and focus restoration. An outside press closes only the list and does not activate controls underneath. Add Current Folder and Refresh remain visible when collapsed. `GET /api/fs/favorites` returns `{ folders: [{path, name, kind, account?, provider?}] }`, combining the server OS's default folders with the signed-in account's changes. `PUT /api/fs/favorites` changes only one path using `{path, favorite: boolean}` and returns `{ok: true}`. Both APIs use `requireFeature('serverFiles')` and read and write only the requesting account. `/fs/cloud-storage` is allowed for owners and managers.

Storage uses the per-account `fileFavorites: {added, hidden}` in the existing `DATA_DIR/user-ui-state.json`. It is independent of the project root and does not overwrite other accounts' paths or existing tab and workspace screen values in the ledger. Per-path changes are read, modified, and saved atomically to preserve changes from concurrent windows adding different paths. Removing a default entry records it in `hidden` so the next detection does not restore it. The added and hidden lists each allow up to 200 entries; paths must be absolute and no longer than 4096 characters, and adding a path checks its real path, directory status, and accessibility. Deleted or disconnected paths can also be removed from favorites.

`server/file-favorites.ts` performs shallow checks of default home folders, macOS iCloud and File Provider folders, the WSL C drive, Windows profile default folders, and OneDrive folder backup locations. Shared cloud detection reuses `server/cloud-storage.ts` and deduplicates by real path. WSL is identified through environment variables or the Microsoft identifier in the Linux kernel, allowing detection even when running as a service. The browser OS is not used for detection. The current folder's favorite status is determined using `canonicalPath` from `/fs/entries`, so it is recognized as the same folder even when reached through a symbolic link. Users can directly add custom paths to folders accessible to the OS. Detection and save failures are separated from list errors, and existing favorites are preserved.

Validation checks macOS/WSL virtual directories and per-account storage in `server/file-favorites.test.ts`, feature permissions and account isolation in `server/access-policy.test.ts`, and shared favorites between the two dialogs, persistent removal of defaults, save failures, and mobile layout in `server/project-dialog-ui.test.ts`.
