## Mewlink local login

Device addresses connect without central login, but ordinary guest feature and file-sharing permissions do not apply before mew login. The exact public capability routes described below are a separate exception. The dispatcher allows only static UI, authentication, and Mewlink access request APIs and blocks work HTTP and WS traffic. Existing role, feature, file, and working-root permissions apply after verifying a local password session or an external identity authorized through owner approval or self-linking. Centrally registered accounts, addresses, and connection subjects are not local permissions. Temporary passwords, expiration, logout, account deletion, and role and file rule changes are checked even during active connections, and requests and WS connections using previous authentication are terminated. Password change requirements apply to password login and are not cleared by profile edits through external authentication. Transport details and session retention follow the [remote access contract](remote-access.md).

When the owner approves a verified identity request under **Account Management → Mewlink Account Access**, a member without a password is registered immediately. Existing email users can link their own account using a verified Mewlink identity from the same connection and a completed password login. This link creates no new account or permissions and uses the email account's existing permissions. Role, feature, and path permissions belong to the same local user ID. New external users have no permissions before approval, and their default role is member. Unlinking does not delete personal settings or the local password; it revokes only external login. External links are bound to the connection ID and user ID at approval so that reconnecting after unlinking or linking another user cannot revive existing sessions.

## Management UI and defaults

The shared modal header contains a title, account count, and add/close icons; the account creation form and permission guidance expand when needed. Clicking a profile photo opens an account control popup for changing roles or deleting accounts. Deletion requires confirmation within the popup and can be retried on failure.

The role in account creation, roles in account rows and photo popups, file path scopes, and per-path permissions use the shared `SelectField`. Selection supports keyboard and touch without native popups, and lists appear outside the table's scroll area. Fields are disabled while role or file permissions are being saved, and existing save-failure notices, refetching, and server permission checks are retained.

The owner's **Account Management → Feature Permissions** displays accounts as columns and roles and features as rows. Account headers in the feature and file permission tables display saved profile photos, or a person icon if no photo exists or loading fails. guest retains a group icon, and clicking a header shows the name and email. The owner-only `/api/admin/access` and feature permission save responses include per-account `avatarDataUrl`. Features are file viewing and editing, agents, terminal, remote desktop, localhost app access, Android, server file explorer, Git, databases, collaborative editing and comments, chat, system administration, and scheduled tasks. Roles provide defaults, and checkbox changes are per-account overrides. Resetting restores that role's defaults. The last owner cannot be demoted or deleted, and currently logged-in users cannot delete themselves. Owner-only administrative functions such as account and workspace management cannot be delegated through the feature table.

owner and manager can use all features by default. Both roles can also list, add, and switch projects, change icons, create folders and perform Git operations in the selection dialog, and switch subprojects and worktrees. Lists and active roots are saved per account, and these APIs are unavailable to member and guest. Account management, Documents settings/import/export, and the existing `/project` create, rename, and delete APIs are owner-only. This follows [decision 0070](../decisions/0070-manager-project-access.md). member can use file viewing and editing, databases, collaborative editing and comments, and chat. Only file viewing and editing can be configured for guest; all other features are limited to logged-in accounts. All are blocked while a temporary password remains unchanged. Terminal-based agents require both agent and terminal features.

Under **File and Folder Permissions**, select the workspace or Documents and browse or enter a relative path. Each account's rules are inherit, block, view, or edit, with the effective result displayed alongside them. The feature-level file viewing and editing toggles set the upper limit. The most specific file/folder rule takes precedence, and editing includes viewing. Without a rule, logged-in accounts are allowed and guest is blocked. The file explorer manages public capability links separately; it does not edit account or guest path rules.

## Public capability links

The [public sharing feature](../features/appearance-accounts-operations/accounts-roles-feature-permissions-and-guest-sharing.md#public-file-and-folder-links) and [ADR 0097](../decisions/0097-public-file-folder-links.md) define anonymous file/folder publication. `GET /api/public-shares`, `GET /api/public-shares/list`, and `PUT /api/public-shares` require owner/manager and current file permissions. They are scoped to the request's workspace. They neither set guest rules nor expose another workspace's records.

`/api/public-shares/{f|d}/{id}` and its `/tree`, `/file`, and `/raw` operations validate the random capability independently of the visitor's login. The API resolves each path inside the saved root, rejects traversal and symbolic links, and blocks secret files, denied segments, server data, and `.worktrees`. Target identity, the publishing account's original identity, management role, and current file permissions are checked again on every request. Moving or replacing a root cannot redirect an old link to unrelated data. Disabling publication deletes the record; publishing again uses a fresh ID.

Read-only capabilities reject writes. Editable capabilities can update existing text files only; they cannot create paths or run privileged operations. Saves require the current version tag and return 409 on stale writes, while the browser retains the draft. Raw responses use sandbox CSP and no-store, no-referrer, and nosniff headers. The remote dispatcher forwards these security headers too. Public pages avoid the normal workspace bootstrap and project/session subscriptions.

Public Mewlink admission allows only exact typed capability HTTP paths and their supported methods. A successfully validated public request renews an anonymous connection's access without granting ordinary work HTTP or WebSocket access. Revoking the record invalidates later requests and the public connection's retained authorization. Ordinary device addresses still require local login. See [the public connection contract](remote-access.md#public-file-and-folder-links).

## Storage and paths

The owner-only `DELETE /api/admin/users/:accountId` returns 404 for a nonexistent account and 400 for deletion of oneself or the last owner. Deletion removes passwords, regular and trusted browser sessions, Mewlink connections and approval requests, file rules across all workspaces, and per-account feature overrides, and notifies clients of access changes. It also removes Git connections for registered providers; ongoing GitHub login operations compare account creation timestamps to avoid saving tokens that arrive after deletion and re-registration. Personal settings, project files, and work records are preserved. Re-registering the same ID must not restore past sessions, permissions, or external Git credentials.

- `shared/access-policy.ts`: Feature list, role defaults, and shared types.
- `server/access-policy.ts`: Actual authorization decisions and atomic saving of `MEW_DATA_DIR/access-policy.json` (0600). Features are saved per account email/guest, and file rules per actual workspace root.
- `server/access-routes.ts`: Owner-only `/api/admin/access`, `/feature`, and `/path`. File change requests send the workspace identifier from when it was opened and are rejected with 409 if the root has changed.
- The existing `guest-access.json` is imported once into the current workspace when no new policy file exists. It is written along with the next permission save. The old `/api/guest-access` change API is 410.
- Documents, subprojects, root aliases, and symbolic links are evaluated by their actual paths, so restrictions cannot be bypassed through another alias. Paths outside the workspace and blocked paths are rejected. Recursive moves, copies, and deletions are rejected upon encountering a directory symbolic link to prevent scope escapes and cycles.

The general file boundary always rejects not only folders named `.data` but also the actual `DATA_DIR` and all descendants. This applies even when renamed through `MEW_DATA_DIR` or when the default XDG data folder is inside the workspace. File and folder symbolic links and descendant paths that do not yet exist are also checked using their actual parent paths. Neither owner nor explicit file allow rules can lift this block. These paths are also hidden from project lists, trees, and catalogs.

APIs requiring project-wide permissions, such as Git, DB, tasks, and feature lists, also require the current `serverFiles` permission if the data folder is included. This permission already allows access to OS files through the separate server file explorer and is enabled by default for owner and manager. Therefore, an existing `.data/` in the Mew repository does not cause a blanket block on these accounts' normal project work. Exceptions are not granted by role name alone; revoking `serverFiles` or restricting explicit file permissions still applies the corresponding checks. Data path blocking in general file APIs remains in effect.

## Server boundaries

The feature middleware and WS authorize in `server/reqAuth.ts` are the actual boundaries. Trees and searches return only permitted items, and raw content, downloads, PDFs, history, comments, table widths, and attachments also check file permissions. Folder moves, deletions, and copies check descendant block rules as well. Upload destinations are checked again after multipart parsing, and link propagation from document title changes applies only to editable files.

guest's `PUT /api/file` edits only the contents of existing files. It does not create nonexistent paths and opens file handles without a creation flag so that deletion between checking and writing does not result in file creation. `/api/raw`, `/api/asset`, and the server file explorer's `/api/fs/raw` block script execution with CSP sandbox to prevent user files such as HTML and SVG from executing with the privileges of the Mew origin.

Terminal, agent, collaborative editing, DB, presence, and live WebSockets compare the scheme, host, and port of the browser-sent `Origin` against the request origin. Different ports on the same host, subdomains, `null`, and invalid Origins are rejected. Compatibility is retained for non-browser clients without Origin; because browser WebSockets send Origin, this exception cannot allow pages from other origins to use cookie authentication. Mewlink, which uses the central origin, permits an exception only for a live P2P context verified and linked by the server, while retaining existing authentication, feature, and revocation checks. The same policy applies to production and development servers.

Attachment `/api/asset` cannot be viewed merely by knowing its UUID. View permission for the corresponding `.mew/assets/` file is required, and responses are not cached. When sharing a document with guest, attachment paths must also be allowed separately. Reading the frontmatter shared selection list (`/api/frontmatter-options`) requires project-wide view permission; adding or deleting requires login and project-wide edit permission. Features that return project-wide data, such as Git and DB management, are blocked if the project has partial file restrictions. DB also rechecks the project scope actually used by the router.

The login video screen checks the authentication operation's `agent` permission or the GitHub connection's `git`/`filesWrite` permissions. It does not require separate general browser permission.

File rules apply to the **mew file API**. Server control features such as agents, terminal, remote desktop, and server file explorer operate with OS permissions and are not sandboxed by file rules. Do not assume file rules can hide secrets from accounts allowed to use these features. This explanation is displayed in account management.

## External debugger

The [external DAP debugger](../features/terminals-agents-automation/external-dap-debugger.md) requires terminal feature permission for owner or manager and project-wide file read and edit permissions for the current project. Adapter installation and execution and debug targets operate with server OS permissions and are not sandboxed by file ACLs. Permissions are checked on every debugger HTTP request, and running sessions are revalidated on policy changes and every 5 seconds. Requests with mismatched accounts, projects, or sessions are not executed. Independent sessions, child connections, threads, and references for each pause revision are checked, and the same permissions apply to memory and value writes. Since the internal DOM browser was removed, analysis connections that select a general Mew browser tab are not provided. The external DAP debugger and analysis file import are retained.

The optional `mew-debugger` agent MCP requires the `agent` feature and per-account, per-project `agentBridge` activation in addition to debugger permissions. It rechecks every call, on policy changes, and every 5 seconds through a private Unix socket bound to the account and project, and closes connections when sharing is disabled, permissions are revoked, or the project changes. Commands require the exact session, connection, and pause revision and use the same allowlist as HTTP. Tool installation, arbitrary DAP/CDP, and other accounts' targets are not exposed.

## Permission changes during active connections

On save, `accessChanges` revalidates existing connections. Agent, terminal, collaborative editing, remote screen, and browser sockets disconnect unauthorized connections and also check input and output. DB subscriptions check feature and project access. Idle socket authentication is rechecked every 5 seconds. localhost preview tokens are bound to the original authentication session and current `portPreview` permission, and requests and open sockets are revalidated. Old `browser` overrides are read and migrated as `portPreview` and written under the new key on the next permission save.

presence sends a content-free `permissions` signal, and the client reloads `/auth/me`, the tree, and open file permissions. Unauthorized windows and files are closed, and files with only edit permission revoked become read-only. Content caches are discarded, and revalidation also occurs on reconnection. Data users have already downloaded and processes running on the server are not retroactively deleted or terminated.

## Verification

`server/access-policy.test.ts` verifies independent feature allowance and denial, account management permissions, guest migration, inheritance and explicit blocking, aliases and symbolic links, HTTP/search/collaboration permission revocation, the last owner, and workspace changes. `server/account-access-ui.test.ts` verifies saving, recovery after failure, restoration of role defaults, file rules, and desktop/mobile tables in the actual management components. Tests use temporary data directories.

`server/server-data-path.test.ts` checks that arbitrarily named data folders inside the workspace and file/folder aliases are blocked in general file GET/PUT, ACL, trees, and catalogs while safe sibling paths remain accessible. It also checks Git, task, and feature list access for accounts with server file permissions, permission revocation, and file rule enforcement. `server/websocket-origin.test.ts` checks rejection of different ports, schemes, and Origins for each WebSocket type, same-origin and non-browser compatibility, and the lifetime of verified P2P contexts. This security fixture prohibits PTY creation.

## Task panel

The object list `/api/task-list` requires login and view permission for the entire current root; writes also check full edit permission. The request root and account are checked against the current session so that requests made just before switching are not saved to another project or account. Accounts with read-only access can retrieve the list. This follows the [input and storage contract](task-list.md).

## Mewpet global skins

List and image reads in `/api/mewpet/skins` are public display data like built-in skins and are allowed for all roles. Adding, editing, and deleting are instance-wide changes and are owner-only. Global skins are not filtered by the active project's or Documents file ACLs. The server checks the actual image format, size, frame count, and manifest and rejects paths outside the folder and symbolic links. Uploads are limited to 4 MiB per image, 24 MiB per skin, and a maximum of 16 actions, and existing valid files are preserved on failure. Skin lists are shared across other accounts and projects on the same server, but selection preferences remain within the existing browser scope.
