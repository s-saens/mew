## Mobile input focus

Input autofocus when opening dropdowns, windows, or search panels follows the `canAutoFocusInput()` conditions in `@mew/ui`. Allow autofocus only when the width is at least 768px and the primary input device is a hover-capable fine pointer. In mobile/touch environments, the keyboard opens when the user directly taps the input. Apply the same conditions to model search, file/content search, editor find, and name, path, comment, and form inputs.

The shared `DialogFrame` focuses the dialog itself on mobile when the initial focus target is an input element. Preserve button/title focus, Tab navigation, Esc, and back behavior. Distinguish cursor movement during direct input and explicit keyboard navigation from autofocus restrictions.

### Mobile editor and keyboard

- Tapping an editable Hotview, Markdown Plain, or code body immediately uses native focus to open the mobile keyboard. There is no floating keyboard button, delayed activation, persistent `virtualkeyboardpolicy="manual"`, or `inputmode="none"` suppression. Body and auxiliary-key presses do not force blur or call the keyboard API to dismiss input. Other controls retain their native focus behavior. See [0098](../decisions/0098-native-mobile-editor-keyboard.md), which supersedes [0094](../decisions/0094-explicit-mobile-editor-keyboard.md).
- `useEditorTouchSelection` continues to observe native selection and menu timing without owning keyboard policy. Read-only and loading restrictions remain owned by the editor. Isolated browser tests cover native focus during the original tap, repeated cursor taps without blur, selection replacement by typing, unchanged input hints, absent keyboard controls, and viewport/layout changes. Actual OS keyboard appearance and browser-specific selection behavior require physical-device checks.

- The horizontal band during direct access in Android Brave recurred in the user's physical-device testing even after entry-order correction. Until the cause is confirmed, do not add height or spacing adjustments; use the local copy button in the optional `viewport-debug=1` to collect physical-device screen dimensions, keyboard boundaries, and DOM hit tests and compare them with photos. Follow the collection scope, exclusions, and validation limitations in [Mobile viewport diagnostics](viewport-diagnostics.md).
- On top-level touch screens accessed directly, use `requestFullscreenWithKeyboard` to enable `overlaysContent` immediately before requesting native fullscreen. Make the request without a separate frame or asynchronous wait to preserve the user gesture, and keep this policy during viewport updates until the entry Promise settles. Overlapping requests retain the entry state until all finish; if entry fails, restore the previous policy. After success, the existing viewport observer handles restoration on exit or when observation ends. Apply this consistently to native fullscreen entry from the header, shortcuts, Mewpet guidance, remote desktop, and PDF, while preserving PDF target elements, options, and fallback modals. In iframes, mouse environments, or environments without API support, use the existing native request. Follow the [decision on preparing the keyboard policy before entry](../decisions/0038-fullscreen-keyboard-entry-order.md).
- `server/fullscreen-keyboard-entry-ui.test.ts` uses controllable native requests to check advance policy configuration, user activation, option forwarding, resize/frame updates while requests are pending, policy restoration on failure, synchronous exceptions, and overlapping requests, entry with the keyboard open, repeated opening/closing/exiting, input focus, bottom boundaries, and excluded environments. A CDP function breakpoint also confirmed `overlay=true`, 1 pending request, and user activation immediately before the native request. Agent and editor checks in actual fullscreen use the same entry function. Automated checks do not guarantee reproduction of the Android OS black band or its resolution on physical devices.
- The top-level connection page owns the keyboard policy for Mewlink's nested iframes. Chromium ignores iframe `overlaysContent` settings, so the app does not use this property. The top-level page determines the overlay policy from fullscreen and touch-input conditions and sends only keyboard width, height, reference viewport dimensions, and overlay state to the inner launcher and app through the existing connection MessagePort. The inner launcher retains the latest geometry and forwards it to new ports after app readiness or account switching. The app validates received finite, nonnegative numbers, adjusts coordinates by the frame's CSS width ratio, and notifies the existing `geometrychange` observer. The bottom boundary is calculated from the top-level viewport height, so keyboard height is not subtracted again from the already reduced inner frame height. On disconnection, clean up observation and the app's geometry copy and restore the top-level overlay policy. Follow the [nested-frame keyboard decision](../decisions/0034-mewlink-keyboard-host.md).
- `server/mewlink-keyboard-ui.test.ts` opens the top-level page, launcher, and inner app on different origins in actual fullscreen to check keyboard geometry forwarding in 390/980px touch and 1280px mouse environments, input/send button boundaries and hit tests, and restoration after keyboard dismissal and fullscreen exit. `mewlink/test/trusted-browser.browser.test.ts`, excluded from Git, checks the forwarding path through the actual connection parent and inner launcher. This cross-frame forwarding correction requires both applying the local app changes and redeploying the Mewlink frontend. The direct-access entry-order correction requires only applying the local app changes. The user reported that the black band during direct access in Android Brave disappears when the keyboard closes, does not occur in normal mode, and does not recur afterward if fullscreen is entered with the keyboard open. Advance policy preparation was added to match this sequence, but whether the band disappears on physical devices remains unverified.
- `useMobileKeyboard` separately remembers keyboard-free reference heights for normal and fullscreen modes. On fullscreen exit, it restores the normal-mode reference; while typing, it does not overwrite the restored reference with stale viewport values immediately after the transition. It detects keyboard opening from a viewport height reduction adjusted for desktop-site initial scaling and pinch zoom, or from explicit keyboard geometry, and hides the dock; after the keyboard closes, it restores the dock even if input focus remains. Reset the reference cache when the layout width or actual display width calculated with `visualViewport.width * scale` changes. Detect rotation even in desktop-site mode with CSS width fixed at 980px. Compare the 150px height-reduction threshold in screen logical pixels adjusted for initial scaling to avoid mistaking browser toolbar changes for the keyboard. `server/mobile-keyboard-ui.test.ts` checks the fullscreen→keyboard→fullscreen exit sequence, the sequence where the keyboard closes first, timing differences between transition events and viewport changes, overlay, simultaneous shrinking of both viewports, and the keyboard while zoomed.
- Touch-keyboard environments are those narrower than 768px or whose primary pointer is `coarse`. Distinguish the wide CSS layout of desktop-site mode from the actual input device, and preserve the existing desktop panel layout. In fullscreen in these environments, enable `navigator.virtualKeyboard.overlaysContent` in supported browsers and receive OS keyboard geometry through `geometrychange`. Restore the previous policy when returning to normal mode or an environment outside the touch-keyboard criteria, or when observation stops. Because `interactive-widget=resizes-content` alone does not guarantee content resizing in Chromium fullscreen, account for keyboard geometry separately even when viewport APIs and root DOM dimensions remain unchanged. Environments without the API retain existing viewport observation. Follow the [fullscreen keyboard decision](../decisions/0011-fullscreen-keyboard-geometry.md).
- `virtualKeyboardViewportBottom` in `@mew/ui/virtual-keyboard` calculates the occlusion boundary of a bottom-fixed keyboard with positive width and height in overlay mode during fullscreen in touch-keyboard environments. Subtract `boundingRect.height` from the full layout height. Do not use top, because older Android Chromium may report the root's visible origin (0 or the status bar position) instead of top. Apply no additional restriction when the keyboard is closed or outside fullscreen overlay mode in a touch-keyboard environment.
- The workspace height is adjusted by `observeWorkspaceViewport`. `viewportZoomRatio` returns 1 if the rounded visual viewport width is at least the root's `clientWidth`, or `clientWidth / visualViewport.width` otherwise. At the initial fitted size, `visualViewport.height + offsetTop` is used as the visible bottom; during pinch zoom, `visualViewport.height * viewportZoomRatio` is used. The minimum of this value, `innerHeight`, the root's `clientHeight`, `rootBottom`, and `keyboardBottom` is used. The desktop site's initial `scale < 1` is not multiplied into the CSS height again. `useMobileKeyboard` also corrects height using the same width ratio, so focus without a keyboard or zoom alone does not hide the dock. `rootBottom` is the actual root bottom measured with `document.documentElement.getBoundingClientRect().bottom`, and `keyboardBottom` is the keyboard region boundary described above. The root's `clientHeight` returns the layout viewport height, so it may report the same value even when the actual clipping boundary is smaller. Panning offsets during zoom are not added to the height. Bottom occlusion calculations for the agent input also use the same `workspaceViewportBottom`, preventing zoom alone from creating a gap between the panel or input and the fixed dock, while still accounting for an actual reduction in available height when the keyboard opens during zoom. The bottom remains within the visible area both when the keyboard shrinks only the visual viewport and when the two viewports report different heights during fullscreen transitions. Even if the viewport API reports the previous height, it must not exceed the clipping boundary of the root with `overflow: hidden`. If the root's `clientHeight` is 0, `innerHeight` is used; if the measured bottom is 0, that layout height is substituted. The measured root boundary applies even without the visual viewport API. resize, visual viewport scroll, fullscreenchange, keyboard geometrychange, and root `ResizeObserver` notifications are batched per frame for remeasurement. When observation stops, scheduled frames and resize observation are cleaned up, and the CSS height is restored. `server/workspace-viewport-ui.test.ts` enters actual fullscreen, then shrinks only the root through CSS while leaving viewport APIs unchanged to check the bottom boundaries and clickability of the input and Send button, as well as resizing and restoration without resize events. It also checks screen panning, fullscreen transitions, keyboard dismissal, zooming and panning at scales 1.25/1.5/2, keyboard use during zoom, and observation cleanup. `server/agent-history-ui.test.ts` checks the agent input's bottom spacing and position retention under actual Chromium page zoom. `server/fullscreen-keyboard-ui.test.ts` injects an OS keyboard overlay into the agent input and code editor in actual fullscreen while preserving viewport and root dimensions. It checks normal and legacy top coordinates, bottom hit testing of the Send button, actual sending, focus retention, dock hiding and restoration, editor status bar and modifier key boundaries, policy restoration, wide touch layouts, and exclusion of mouse desktops. `server/desktop-site-viewport-ui.test.ts` uses actual Chromium mobile emulation with a 980px viewport and an initial scale of about 0.4 to check the connection between the workspace and fixed dock, focus without a keyboard, scales 0.8/1/1.5/2, keyboard-induced screen shrinking and restoration, rotation, available-height changes corresponding to browser toolbars, and restoration after entering and exiting fullscreen. OS keyboard behavior in actual Android Brave and behavior under different security contexts require verification on actual devices.
- EditorPane also uses the same viewport observer to constrain the combined height of the body and status bar. Keep the selected character count/file size status bar below the auxiliary keys and above the keyboard or Dock. Keep the body viewport extended to the status row behind the keys, and add the measured status height to the fixed keys' bottom inset. Use the measured key height for trailing document padding rather than a margin before the status row. Recalculate space when modifier keys are shown or hidden and when switching views.
- Hotview and CodeMirror use `observeEditorViewport` from `@mew/ui` to constrain their height within the visual viewport and explicit keyboard bounds at the initial fit scale for touch keyboards. The initial `scale < 1` on desktop sites is also treated as the default fit scale. Both browsers that leave the layout viewport unchanged and browsers that shrink both viewports are supported. Height is restored when the keyboard closes; mouse desktops and pinch zoom beyond the default fit scale are excluded from this height constraint.
- Viewport resize and scroll events, the editor ResizeObserver, and focus input are coalesced per frame. Even after keyboard animations, the focused cursor is kept within the intersection of the visible editor and modifier key bar, with a 12px margin. This does not change the document or selection, force focus, or return an unfocused reading view to the cursor position.
- Hotview adjusts only its own scroll position using the current cursor's DOM coordinates. CodeMirror separates coordinate measurement from scroll adjustment through the read/write phases of `requestMeasure`. Frontmatter and document search inputs also remain visible after height changes.
- The fixed mobile modifier key bar adjusts its bottom inset using the smaller of the visual viewport bottom and the explicit keyboard region boundary. It applies the larger of this inset and `--mobile-dock-space`, which includes the safe area, then adds `--editor-status-bar-height`, placing the bar above the status row, which stays above the Dock or keyboard. The editor body extends behind the keys to the status row; the transparent key wrapper does not clip or reserve a separate footer strip. `observeEditorViewport` scopes the measured status height and `--editor-key-bar-height` trailing scroll padding to the editor host, observes both controls for height changes, resets reservations when the bar disappears, and restores original values on cleanup. Reservations remain during pinch zoom even though the editor height constraint is suspended. Cursor visibility uses the key bar's top edge. It subscribes to geometrychange; the terminal's in-flow modifier key bar retains its existing layout.
- `server/editor-keyboard-ui.test.ts` injects viewport size and offset changes into the actual editor to verify position retention after tapping line 28, repeated resizing, modifier key boundaries, status bar visibility and input, dock height and safe-area spacing, placement above the dock after keyboard transitions, keyboard closing and height restoration, simultaneous changes to both viewports, and preservation of desktop and reading scroll positions. ### Mobile auxiliary key bar

Hotview, Markdown Plain, and code editors display auxiliary keys at mobile widths even before editor focus and after focus leaves or the keyboard closes. Embedded hosts can still opt out through `showMobileKeyBar`; desktop editors do not show the keys. The body extends down to the file-size/selection status row. Auxiliary keys float over its lower portion, above status and the Dock or keyboard; they do not occupy a separate layout row.

In fixed editor placement, `MobileKeyBar` has a transparent layout wrapper without a background, border, dividers, or enclosing shadow. Each key floats independently with a 10px corner radius, a 75% opaque themed raised surface, backdrop blur, and a small soft shadow. Buttons are 32px high and at least 24px wide, capped at 40px for the ordinary action row, with 11px text and 14px decorative SVG icons. At 360px and below, use 10px labels, 4px horizontal outer padding, and 2px action gaps so all 13 Hotview keys fit at 320px without horizontal scrolling. The wrapper keeps 6px vertical padding, including the gap above the status row in editor hosts.

Esc, Tab, Ctrl, Shift, host-provided keys, and optional editing actions form one bottom-aligned row. The four arrows sit at the far right in a separate three-column, two-row grid: Up above Down, with Left, Down, and Right on the lower row. The editor keeps rendering behind the full two-row wrapper. Hotview adds the measured wrapper height to trailing body padding so the last line can scroll above Up; Plain/code retain their existing trailing space. Cursor visibility uses the key bar's top edge, resolving the bar within the owning editor body even when it is a sibling of the CodeMirror scroller. Empty wrapper areas pass pointer events through to the document; individual buttons receive input. Terminal in-flow placement retains its single row, original key order, 10px equal-width `stretch` keys, solid background, themed top border, and existing spacing.

Ctrl and Shift retain `aria-pressed` and the theme accent for enabled modifiers. All keys share pressed feedback and an inset keyboard-focus outline. Mouse-down prevention preserves the editor's focus and selection. Optional editing actions appear only when their callbacks are available. Non-arrow keyboard dispatch and swipes starting on ordinary key buttons retain their existing behavior; gestures starting in the transparent gaps belong to the document underneath.

Editor auxiliary actions run against the existing editor state without requesting editing focus, even if the body is already focused. Dismissing a mobile keyboard can leave DOM focus in place, and calling `focus()` again can reopen it. Plain/code key dispatch and Hotview Tab, list indentation, undo/redo, code-block toggling, and table insertion therefore do not call editor focus. Keep existing editing focus when present, leave blurred bodies unfocused, and preserve native keyboard activation through a direct body tap. `server/mobile-editor-keyboard-ui.test.ts` checks both focus states, native focus requests, continued editing, and environments with and without the keyboard API. Physical OS keyboard behavior still requires device verification.

Arrow buttons activate on primary pointer contact rather than release, in both fixed editor and terminal flow placement. Holding repeats after 350ms and every 60ms thereafter. A held pointer entering another arrow activates that direction immediately, including pointers initially pressed outside the arrow area. Hit testing uses pointer coordinates so touch's implicit capture does not keep the original direction active. Gaps pause repetition; reentry starts a new immediate press. Arrow targets disable native touch panning and expose the currently held surface without toggle semantics.

Release, cancellation, loss of pointer capture, multiple pointers, window blur, visibility changes, placement changes, and unmount stop repetition. Pointer-generated clicks following an arrow gesture are consumed to prevent duplicate input or activation of another key after dragging; keyboard and assistive clicks retain normal button activation. Callbacks use the current host state. Arrow gestures are excluded from tab swipes, and a content/key-bar swipe that enters an arrow is cancelled. `server/mobile-arrow-keys-ui.test.ts` checks these interactions with mouse input, real CDP touch input, and a controlled browser clock for fixed and flow layouts.

The bar owns an upward-facing shared `HoverTipLayer`, using accessible labels and `data-tip` instead of native titles. `CodePane` keeps the bar outside its separate search tooltip layer to avoid duplicate tooltips. `server/mobile-key-bar-ui.test.ts` verifies floating surfaces, arrow geometry, touch targets, modifier state, actions, selection preservation, keyboard focus, localization, tooltip placement, narrow layouts, optional actions, and terminal stretch keys. `server/editor-keyboard-ui.test.ts` checks initial and unfocused visibility, the body extending behind keys to status, final-caret visibility, dynamic status height, Dock/keyboard transitions, and restored editor height against the measured initial layout rather than a fixed height threshold. See the [mobile footer work record](../work/editor-mobile-footer.md). The [work record](../work/editor-auxiliary-key-bar-polish.md) records local verification and application limits.

## Editor Body Loading

`Tab.loading` in `useTabs` tracks body requests independently of saves. Set it for new/restored files and cache revalidation; clear it on full-body success, including an empty string, or failure. An anchor-only preview of a large file remains loading. Do not persist the flag or set it for binary media streamed by its own viewer.

When the active tab is loading, `EditorPane` sets `aria-busy` on `DockInlineBody` and covers the body, toolbar, and status bar with a black 50% overlay and a centered spinner. The underlying area is `inert`, and the editor is read-only. The tab bar and other panels remain usable. The loading indicator's `role="status"` uses the existing `common.loading` translation and does not rotate under reduced motion.

Validation: `server/editor-pane-ui.test.ts` uses the actual editor and delayed file responses to verify overlay boundaries, input blocking, cached bodies, reduced motion, consecutive file switches, empty documents, and clearing after failure in dark mode at 1100px and light mode at 390px. Existing collaborative editor error recovery and workspace switching validation are handled by `server/editor-collab-ui.test.ts` and `server/workspace-switch-ui.test.ts`, respectively.

## Editor Tab Visits and Document Navigation

The editor separately manages **tab selection order within an editor pane** and **document visit history within a tab**. It follows the [Per-Tab Document Navigation Decision](../decisions/0044-editor-tab-navigation.md).

**Tab selection.** Closing the active tab selects the most recently active remaining tab in that pane; closing an inactive tab leaves selection unchanged. With tabs 1, 2, 3, opening 4 from 1 and closing it returns to 1. Empty panes follow existing cleanup rules. Each pane tracks recency separately.

| Document action | Visit-history behavior |
| --- | --- |
| Normal internal/subdocument link click | Navigate in the clicked pane's current tab; append after the current position and discard forward history |
| Ctrl/Cmd+click | Open a new tab containing only the target visit, without copying the source history |
| Back/Forward | Move the current history position without recording a new visit |
| Select a tab | Leave its document history unchanged |
| Split or move a tab to another pane | Preserve that tab's document history |

Navigation and Back/Forward retain the originating tab even when another tab already shows the target. `Tab.id` and `Pane.activeTabId` distinguish same-path tabs; shared bodies never merge histories. Other panes' active tabs/histories remain unchanged. Bodies, drafts, saves, and permissions retain per-file-path management.

`Tab.navigation` lasts for the in-memory tab session. Refresh/restoration merges same-document duplicates under existing policy and starts history from the restored current document only.

**Controls.** Pin **Back → Forward** 12px from the editor body's upper-left edges, independently of upper-right file tools. Put Open File Explorer after Forward when visible, without shifting/overlapping navigation. Preserve file-history, view, comment, annotation, and contents tools at their upper-right inset. Reuse floating-button size, surface, spacing, tooltips, and translated accessible names. Disable Back without a previous visit and Forward without a next visit; both start disabled in a new tab.

Document navigation within a tab is separate from viewing historical file contents in Git and does not add document visits to mobile panel visit history or the browser's Back stack. [Links](../features/document-code-media-editing/links-file-references-and-attachments.md) owns link display, path resolution, and click contracts.

## Editor status bar

- Keep the selected-character count and file-size status bar at least 16px high, even when empty. On mobile, place it below [auxiliary keys](#mobile-auxiliary-key-bar), above the Dock or keyboard.
- Calculate UTF-8 text size after initial render. While typing in the same project/file, retain the last value until recalculation finishes. Never show the previous file's size after a project/file change.
- `server/editor-status-bar-ui.test.ts` checks retained size/height during Hotview and Plain typing on desktop/mobile, and the updated UTF-8 size after calculation.

## Text selection

`src/index.css` blocks app-UI text selection and iOS long-press callouts by default, including titles, guidance, tabs, menus, tool buttons, and portal descriptions. Apply this through the `body` default and per-content exceptions, without forcing `user-select: none` on every descendant.

Selection backgrounds in Hotview, Plain, and code editors use the current theme's primary color (`--color-accent`) at 30% opacity, while text and syntax highlighting colors remain `currentColor` ([standard selection highlight color rules](https://www.w3.org/TR/css-pseudo/#highlight-cascade)). The same color applies to Hotview's `.tiptap ::selection` and CodePane's native browser selection and `.cm-selectionBackground`. When CodeMirror draws selections itself, native browser selection remains transparent to prevent overlapping colors; theme colors are also specified for paths that use native browser selection, such as iOS. Changes to the theme's primary color take effect immediately regardless of focus or read-only status. `server/editor-context-menu-ui.test.ts` handles verification, and iOS branch checks use a platform-detection test double in Chromium. Selection handles and toolbars drawn directly by the OS are outside the scope of CSS color settings.

- Inputs, textarea elements, editable content, Hotview (`.tiptap`) and CodeMirror (`.cm-content`), including read-only content, and PDF text layers retain selection and copying. Output and commands in `pre` and `code`, and `role="alert"` errors, are also selectable.
- Apply `select-text` to actual content users may copy, such as agent questions, answers, thoughts, and work content, chats and comments, diagnostic errors, sheets and read-only DB cells, and Git commit bodies. Authentication codes using `select-all` also retain their existing select-all behavior. Notification `ConfirmDialog` messages are selectable, while Confirm and Cancel buttons are not.
- Even within selectable content, regular buttons, label elements, and summary elements block selection. Only the content of collapsible agent bubbles and error buttons re-enables selection with `select-text`, and expanding or opening error details does not run during selection. Explicit `select-none` settings, such as those on line numbers, remain effective.
- For new copyable content, apply `select-text` to the smallest container holding the content. Do not exempt an entire screen or determine selectability solely by color or heading tags. Do not globally block default focus, editing, scrolling, or clipboard behavior with JavaScript.

Verification: `server/text-selection-ui.test.ts` checks non-selectable UI at desktop and mobile widths, nested content and button exceptions, copying read-only content and diagnostics, input selection and editing, portals, actual error buttons, and the shared error dialog. Also run `server/sidebar-touch-ui.test.ts` for mobile file explorer long presses.

## Focus-based tab shortcuts

By default, `Alt+T` toggles the task panel. Open the terminal with `Ctrl+백틱`. The task panel uses existing Markdown, and [DB Gantt](../../../docs/guides/database.md#switching-views) uses rows and date columns from the same DB; they do not automatically sync with each other.

`Ctrl/Cmd+N`, `Ctrl/Cmd+T`, and the existing `Alt+N` (including remapped `newTab`) open a new tab in the focused surface. For agents, this opens that group's `+` selection screen; for regular shells, it creates a new terminal in that group; for the editor and file explorer, it opens the new filename input. In the task panel, it moves to the new-item input in the list or calendar, or adds a new item in Gantt ([task input contract](task-list.md#input-and-panel)). `Ctrl/Cmd+Shift+N` connects to the existing new-folder flow (the document tree follows its existing new-document rules). The file explorer uses the selected location, and the editor uses the active document's folder. Both check file read/write permissions and consume the per-project one-time request in `useSidebarCreate` so it is not replayed on remount or project switch.

`captureAppTabShortcuts` records the last selected area through pointerdown and focusin, retaining that area's new-tab behavior even when clicking an empty part of a panel moves actual focus to body. It does not send creation requests to areas that are hidden, inert, or removed from the DOM. At the capture phase, it first dispatches the action registered with `openFocusedTab`, allowing new agent, terminal, and browser tabs to open independently of file write permissions. Even if a registered surface rejects creation, it does not fall through to creating a new file; file and folder creation runs only in editor and file explorer areas. In other panels and areas outside the app, it consumes creation keys without creating files. Modals, IME composition, and key repeats consume keys without running creation or close actions. Nested shortcut surfaces use the innermost surface that registered the action; surfaces without an action use the ancestor registration. `src/utils/app-tab-shortcuts.test.ts` checks file/folder creation in the editor and file explorer; new agent, terminal, and browser tabs and creation rejection; empty-area selection, hiding, modals, IME, repeated input, and blocked key propagation. [Agent set and tab creation](../features/terminals-agents-automation/agent-sets-and-tab-creation.md) owns the detailed creation flow.

`Ctrl/Cmd+Tab`, `Ctrl/Cmd+PageDown`, and `Alt+E` move to the next tab; `Ctrl/Cmd+Shift+Tab`, `Ctrl/Cmd+PageUp`, and `Alt+Q` move to the previous tab, wrapping at both ends. They use the same focus, split-panel, modal-exclusion, and input-blocking contracts as numbered selection. The existing `Ctrl+Alt+←/→` and custom previous/next tab combinations remain available. CLI switching in agent input, which conflicted with `Ctrl+Tab`, moves to `Ctrl+Alt+M`. When the login video viewer has focus, global tab shortcuts do not run and the input is forwarded to remote Chrome. The tab bar identifies the current tab using `aria-selected`. Since the file explorer has no tabs, tab navigation, numbered selection, and body swipes do not change its search mode. The search-field toggle and `Ctrl+P` and `Ctrl+Shift+F` switch between filename and content search.

`Ctrl/Cmd+1`…`Ctrl/Cmd+9` select the tab at the corresponding display position in the currently focused panel (9 selects the ninth tab). At the window capture phase, `useFocusedWorkspacePanel` identifies the combination with `numberedTabIndex` and invokes the existing tab-click behavior through `activateNumberedPanelTab`. `data-dock-body` connects to the `data-dock-panel` tab bar in the same group, so it does not select tabs in another split panel. If the tab bar has `role="tablist"`, that list is used; otherwise, the `role="tab"` order within `data-dock-tab-bar` is used. The file explorer has no tabs and does not receive `data-numbered-tab`.

- A nonexistent number leaves the current tab unchanged, and a panel without tabs does not forward selection to another panel. Number shortcuts are not forwarded to the editor or PTY. 0, combinations that add Shift or Alt to Ctrl/Cmd, and IME input are not treated as numbered selection.
- Physical keys `Digit1`…`Digit9` and the numeric keypad are supported.
- The last panel selected by keyboard or pointer is remembered, but background tabs are not switched for closed, hidden, or inert panels or during modal input. Ctrl/Cmd number and navigation keys are still consumed in these cases to prevent them from reaching browser tabs. Tasks use the list, calendar, and Gantt view list, excluding the title.
- Regression checks in `src/hooks/use-focused-workspace-panel.test.ts` and `server/desktop-keyboard-ui.test.ts` cover selection in split editors, portal terminals, the file explorer, and tasks; nonexistent numbers; Option and the numeric keypad; modifier and IME exclusions; modals and inert panels; input blocking; and wrapping at both ends. The actual agent panel is verified with `agent-new-tab-ui.test.ts`, login input with `src/components/login-desktop-viewer.browser.test.ts`, and file/folder creation in the actual App with `workspace-switch-ui.test.ts`.


The signed-in user's `Alt+1`…`Alt+9` input is identified by `projectTabIndex`, and the capture listener in `ProjectSwitcher` selects the project in the saved `paths` order. It follows the dropdown list order and uses the existing `onActivate` project-switching path regardless of panel focus. The current project, nonexistent numbers, modals, and key repeats consume the key without switching. For guests, this listener does not consume keys. Shift, combinations with Ctrl/Cmd, IME, and 0 are not treated as numbered combinations. Physical `code` and the numeric keypad are recognized instead of the special `key` produced by macOS Option. Iframes also forward Alt-number input to the app, while the active remote screen receives it through the shared highest-priority capture handler. Follow [Open, select, and switch projects](../features/projects-files-search/opening-projects-tabs-and-groups.md) for the detailed contract.

`Ctrl/Cmd+W`, `Ctrl/Cmd+Shift+W`, and `Alt+W` (including remapped close combinations) close **one tab in the focused surface** through `closeFocusedTab` and `dispatchFocusedShortcut`. Windows that own their tabs, such as terminals, agents, and browsers, register a root ref and `useFocusedShortcutScope(ref, { closeTab, newTab })`.

- When the key reaches the app, `preventDefault()` and `stopImmediatePropagation()` block the browser's default behavior and forwarding to the editor or PTY, regardless of whether a tab can be closed. Repeated keydown events are consumed without closing additional tabs. On the start screen with no tabs, the action does not spill over to tabs in another surface.
- When a confirmation dialog or modal has focus, tab-close keys are consumed without running background tab close actions or the editor fallback. Confirmation and cancellation for an agent tab with work in progress follow the [agent conversation contract](../features/terminals-agents-automation/agent-conversations-queue-and-restoration.md#confirmation-when-closing-a-working-tab).
- A document tab is closed only when no window is registered and the focused editor pane has an active document. Closing a terminal tab terminates its shell session through the same path as the existing `×` button.

`Ctrl/Cmd+Shift+T` blocks forwarding to the browser, editor, and PTY at the capture phase and dispatches to the focused surface's `reopenTab` action. Agents and terminals register this action on the tab bar, body, and empty panel. If there is no closed-tab history, it does nothing and does not fall back to file creation or another panel type. It does not restore tabs during modals, hidden/inert states, repeats, or IME input. History scope and conversation/shell lifetimes follow [Agent tab creation](../features/terminals-agents-automation/agent-sets-and-tab-creation.md) and [tmux terminal](../features/terminals-agents-automation/tmux-shell-terminals.md).

Standard combinations such as `Ctrl/Cmd+W/N/T/숫자` are fixed aliases and remain available even when existing custom shortcuts are changed. In a regular Chrome tab, keydown events for reserved keys may not reach the webpage. Entering JavaScript fullscreen through **mew's fullscreen button or Alt+Enter** causes `captureAppKeyboardLock` to lock the `APP_KEYBOARD_KEYS` needed for creation, closing, selection, navigation, and existing app commands. F11 fullscreen alone does not satisfy this condition. A secure context (HTTPS/localhost) and Keyboard Lock support are required; when unsupported or denied, only delivered events are consumed. Existing Alt combinations are available where locking is unavailable. A Chrome app window (**Install page as app** in the menu) is an optional way to deliver Ctrl+W to the app in windowed mode, without adding a client keyboard helper app. Follow [Keyboard Lock](https://developer.chrome.com/docs/capabilities/web-apis/keyboard-lock) and [Install a Chrome app](https://support.google.com/chrome/answer/9658361?hl=ko).

`APP_KEYBOARD_KEYS` also includes `Escape`. Where Keyboard Lock is supported and permission is granted, a brief Esc press does not exit app fullscreen, while existing Esc handling for closing popups, canceling searches, terminal input, and similar actions remains available. Fullscreen can be exited with the fullscreen button or `Alt+Enter`, and the browser guarantees Chrome's escape behavior of holding Esc for approximately 2 seconds. Where unsupported or permission is denied, the browser's Esc fullscreen exit cannot be blocked. `server/desktop-keyboard-ui.test.ts` checks that the app lock includes Escape and is restored after the remote lock is released.

`@mew/shortcuts` installs a single highest-priority capture listener during module initialization. The active remote screen's `registerKeyboardCapture` handles both keydown and keyup before regular tab shortcuts, numbered selection, and overlays. `keyboard-lock.ts` manages app reserved-key locks and remote all-key locks by priority. If fullscreen remains active after remote focus is lost or the remote screen is closed, it restores the app reserved-key lock; it releases the lock on fullscreen exit, window blur, screen hiding, or unmount. It checks lifetimes so an asynchronous permission result cannot release a new owner's lock. Remote input, OS exceptions, and the clipboard follow the [remote keyboard contract](remote-desktop.md#keyboard-lock-and-clipboard).

The default combination for creating a comment is `Ctrl/Cmd+Shift+C`; explicitly saved custom combinations are retained. When the user is logged in, has collaboration permission, and has focus or a DOM selection in an actual file text editor, `captureCommentShortcut` uses `preventDefault()` and `stopImmediatePropagation()` at the capture phase to block browser developer tools and subsequent forwarding to the editor. Without a selection, it only consumes the key; repeats and IME input also do not create new comments. It neither dispatches comment creation nor consumes keys in agents, terminals, login video, modals, or hidden/inert areas, preserving remote capture priority. [Comments](../features/collaboration-comments-chat/comments-replies-and-member-mentions.md) owns the details of authoring, lists, and permissions.

## Shared editing state for Documents and regular files

For logged-in users, Documents and regular-file tabs are saved in one `.workspace` editing state per root project. The source tree from which a file is opened does not change the `useTabs` project or `DockPanel` ID. Guests retain the existing `docs` scope.

- Regular-file tab identifiers remain their existing relative paths. Other API scopes are distinguished by `mew:file:<인코딩된 프로젝트>/<상대경로>`. This value is a UI identifier and is not sent as a server file path. Filename display, body paths, saving, permission revalidation, collaboration rooms, comments, history, attachments, table widths, and document DBs use the original API scope and relative path. Each editor pane's API object is pinned to its scope so focus in another pane cannot change the target of asynchronous work.
- `mergeEditorTabs` merges the existing `.workspace` and `docs` saved states once. If the regular-file editing state is empty, it uses the Documents panes and layout. If both exist, it uses the regular-file layout and focus, merges tabs into panes with matching IDs, and appends Documents-only panes while preserving their IDs. Old Documents tabs are not merged again into saved state marked `unifiedScopes: true`.
- Documents and regular files with the same name are distinguished, and selecting a restored inactive tab lazy-loads its body using that file's scope. Isolation of saves, caches, and late responses across root projects is maintained.
- Simply selecting a file tab updates the file explorer location. On mobile, only reselecting the active tab switches to the file explorer. Showing the location of, renaming, deleting, creating, and dropping Documents files into editor panes also use the original scope.

Verification: `editor-files.test.ts` checks tab identifiers, same-name files, merging old saved states, and preventing repeated restoration; `unified-editor-ui.test.ts` checks switching between same-name files, saving in each scope, preserving moved dock layouts, and restoration after refresh in the actual editor. `workspace-switch-ui.test.ts` checks shared-tab integration in the actual App and state isolation across roots.

### Editor body context menu

Hotview, Plain, and code bodies display **Add Annotation · Add Comment · Copy · Cut · Paste · Delete · Select All** using the shared `ActionMenu`. The editor opts into the shared horizontal presentation: only icons are visible, and mouse hover shows each translated action name in a tooltip. The same labels remain available to assistive technologies. The 7 default items are always displayed, with unavailable actions disabled. These include annotations in non-Markdown files, body changes in read-only mode, and copy/cut/delete without a selection. Comments require separate feature and file modification permissions, as well as target text.

Long presses and double taps retain native text selection in touch editor bodies. Touch-generated `contextmenu` events, including mouse-compatible events after touch, stop propagation to internal table menus. Cancel the default menu only when a nonempty native selection is already inside the body; otherwise preserve native word-selection initiation. Do not move focus, prepare an editor selection, or cancel touch start/movement.

`useEditorTouchSelection` observes nonempty DOM selections in that body:

- After finger release, open the existing menu below a range stable for 250ms. Mouse or keyboard selection alone does not open it.
- Range-changing input closes the old menu and prepares the new range. Clearing selection through an editing gesture, key input, window-focus loss, or file/workspace/mode/account/permission changes cancels pending display.
- Scrolling and pointer movement retain an open menu and its target. Scrolling also preserves a pending stable-selection timer, whose final placement uses current range geometry. A temporarily collapsed native range during scrolling retains the target; actual range changes hide and rebuild the menu.

A browser can cancel pointer delivery when it takes over native text selection. `pointercancel` and `touchcancel` therefore recheck the current range rather than discard pending menu display. If a native touch is still active, the menu waits for `touchend` or `touchcancel`; once the gesture ends, a valid range opens the menu after the same 250ms stability delay. Cancellation without a selection leaves the menu closed. File and other scope changes still cancel pending display.

Keyboard activation follows [Mobile editor and keyboard](#mobile-editor-and-keyboard). `useEditorTouchSelection` observes selection and menu timing without suppressing, requesting, or restoring keyboard input. Body taps use native editing focus immediately. Native cursor and selection gestures remain uncanceled, and repeated body presses do not force keyboard dismissal.

The automatic selection menu uses `autoFocus={false}` on `ActionMenu` to preserve body focus and native selection handles. In this case, `outsideIgnore` returns the body wrapper so handle adjustments and scrolling touches are not canceled by the shared menu. `useEditorTouchSelection` keeps its existing shown range on pointer start, tracks movement, and dismisses an active selection menu only on a real body click; scrolls and canceled drags leave it visible. Clicks outside the editor wrapper are closed and consumed by `ActionMenu`, after classifying the gesture. The same click mode applies to mouse-opened editor menus. [0095](../decisions/0095-editor-menu-scroll-preservation.md) records this interaction choice. Other menus retain default autofocus, pointerdown dismissal, click consumption, and keyboard navigation. Input that presses a menu item does not close the automatic menu prematurely, and actions such as copy and delete apply to the selection range used to prepare the menu.

Right-clicking within an existing selection preserves it; right-clicking outside moves the cursor to that location. Add Annotation uses the cursor position or the end of the selection. When there is no selection, Add Comment automatically selects the corresponding paragraph in Hotview or line in Plain/code. The existing requirement for a selection when creating comments with a keyboard shortcut remains unchanged. In tables, row/column addition and deletion, DB switching, and Markdown/CSV/image copying are appended to the same horizontal row, preserving each table-specific item's existing permissions and behavior. The row scrolls to reveal overflow. Table-row and table-column deletion use distinct red row/column icons; database conversion and Markdown copying use database and code icons to distinguish them from the body actions.

Copy and paste use each editor's existing serialization and paste paths, and body changes are recorded as editor transactions to preserve undo and collaboration history. Cut deletes the selected content only after the clipboard write succeeds. If a clipboard operation fails, a toast suggests the alternative shortcuts `Ctrl/Cmd+C`, `Ctrl/Cmd+X`, and `Ctrl/Cmd+V`. Changes to the file, workspace, account, view mode, or permissions close the menu, and late results from previous clipboard requests do not modify the body.

`server/editor-context-menu-ui.test.ts` handles validation. It checks native menu cancellation for existing body selections, the unchanged default before selection, range and focus preservation, automatic display after mobile selection, pointer/touch cancellation before or after selection, active-touch waiting, cancellation without a range, scope changes during recovery, selection adjustment, read-only copying, actual touch scrolling inside and outside the editor, mouse wheel scrolling, canceled drags and their compatibility clicks, body/outside click dismissal, copying the original range after scroll, and the existing mouse right-click path. Selection handles and native toolbars on actual Android and iOS devices require physical-device checks.
