## Collaboration rooms (Yjs relay)

- `server/collab.ts` owns rooms, clients, awareness, and `/api/collab` WebSockets. Client room name = `프로젝트:상대경로`; server key = `루트 절대경로` + NUL + client room name. Rooms share edits within one root and separate identically named files across roots. Each connection retains its account root for path and permission checks; another account switching projects does not disconnect it ([per-account path contract](architecture.md#per-account-active-project)).
- `server/syncCodec.ts` owns frame encoding/decoding. **Wire contract:** outer varUint channel (`0` sync · `1` awareness), sync varUint type (`0` step1 · `1` step2 · `2` update), then varUint8Array body. `server/syncCodec.test.ts` checks byte-for-byte y-protocols compatibility; mismatches silently break every open tab at deployment. Untrusted bytes return `null` without throwing.
- `server/roomDoc.ts` supports JS Yjs and Rust yrs through `stateVector()`, `encodeStateAsUpdate(sv?)`, and `applyUpdate(update)`. Broadcast the **newly received update** returned by `applyUpdate` (`null` if none). A state-vector diff can lose deletion-only updates as empty diffs.
- `server/collabAgent.ts` bridges disk changes through an in-process client with its own Y.Doc and awareness, connected through the room's `connect()`. Holding the room's doc would prevent backend switching; a loopback socket would require bypassing `authorizeCollab` guest blocking. Terminal edits to `.md` appear in open rooms with the `agent` cursor, while the `appWrites` echo ledger protects user typing. This bridge is unrelated to the agent window removed on 2026-07-25 and must remain.
- Authentication, `MAX_ROOMS`, awareness, and room lifetime remain in JS for both backends. **Only connected users keep rooms alive.** Counting the bridge client would prevent cleanup and accumulate headless editors and fs watchers.
- `useCollab` allows 10 seconds from socket creation to the first document sync response. A stalled connection or sync discards the socket without awaiting close and retries from 300 ms up to 3 seconds. The first response clears the timeout and resets backoff. Late events from replaced sockets are ignored; Y.Doc, unsent edits, and undo state survive reconnection. `server/collab-reconnect-ui.test.ts` checks stalls, late responses, edit preservation, success timer cleanup, and unmount cleanup.
- After [verified Mewlink recovery](remote-access-recovery.md#reattaching-the-same-rtc-after-a-brief-signaling-interruption), `mew:remote-reconnected` cancels a pending retry and reconnects once immediately. A socket still connecting or awaiting initial sync is retained with a fresh 10-second deadline from verified transport availability, so an overdue pre-sleep timer cannot retire it before its admitted open response. Synchronized sockets are unchanged. Y.Doc, unsent edits, and undo history survive; repeated events cannot duplicate sockets. Room changes and unmount remove listeners and timers. Ordinary `online` events neither bypass backoff nor renew deadlines.

Active file body retrieval and collaboration preparation run in parallel. The server checks collaboration and file-edit permissions independently at socket connection. The client attaches the prepared document only after the file response confirms content and editing permission; until then, it neither seeds cached content nor autosaves. Failure, denial, or tab switching closes the prepared connection without retaining an inactive room. See the [file retrieval contract](file-loading.md) and [ADR 0014](../decisions/0014-parallel-file-collaboration.md).

The Rust backend is optional and disabled by default ([ADR 0035](../history/decisions/0035-mew-collab-rooms-rust-yrs.md)):

```bash
npm run build:native        # native/collab (cargo, napi-rs) → native/collab/mew-collab.node
MEW_COLLAB_RUST=1 npm run serve
```

The platform-specific `.node` artifact is not committed. If `MEW_COLLAB_RUST=1` cannot load it, initialization throws instead of silently selecting JS; the active backend must remain explicit.

The headless editor DOM exposes `self`, `window`, and `document` from the same Window. `server/collabAgent.ts` prepares required globals before loading editor dependencies without overwriting existing globals. RAG and Transformers.js remain outside this contract under the [removal decision](../history/decisions/0176-mew-remove-local-rag.md).

`server/collab-dom.ts` blocks JavaScript execution; script, CSS, image, and iframe loading; file system HTTP requests; and all frame navigation. It rejects asynchronous fetch and synchronous requests before transmission. Externally edited Markdown HTML is document data only. This boundary is explicit rather than a Happy DOM default; `server/collab-dom.test.ts` checks normal content, inline non-execution, and request/navigation blocking.

## Account theme change notifications

On account theme save, `broadcastAccount` sends `{type:'theme'}` only to that account's presence connections after revalidating authentication, excluding other accounts, guests, and revoked connections. The signal contains neither settings nor account ID; the client re-fetches REST with its own session. `usePresence` forwards `mew:theme-changed`. [Account themes](browser-storage.md#account-themes) owns foreground/reconnection re-fetching, save races, and cache boundaries.

## Shared memo

- Opening the panel or switching docks focuses the non-editable `SharedMemo` root. Connection completion and view switching do not focus the body; direct body interaction opens the mobile keyboard. `Ctrl/Cmd+M` from outside an already open memo still explicitly focuses its body.

- The memo body has 16 px of top padding, and the first block's top margin is removed. The standard document editor's horizontal margins, font size, and line height are retained.
- At the user's request on 2026-10-01, the memo popup was converted to a docked panel and the task panel was removed. Popup movement, 8-direction resizing, and viewport position correction are not provided.
- The memo's mobile modifier keys are controlled by passing detection results from `useMobileKeyboard` and the panel's open state to `Editor.showMobileKeyBar`. When the keyboard closes, the keys are hidden and the Ctrl and Shift toggles are cleared.
- App-owned `useSharedMemo` retains CRDT, unsent changes, value, participants, focus, and shortcuts outside per-project DockWorkspace. `toggleMemo` defaults to `Ctrl+M` and also accepts Cmd: closed → open; external focus → bring forward/focus body; internal focus → close. Repeated keydown and IME composition do not retoggle.
- Logged-in users with collaboration permission see `SharedMemo` in `DockPanel(id/kind=memo)`: shared 36 px header, DockGrip, title tab, PresenceDots, and close button. DockInlineBody switches Hotview/CodePane (Plain), with view state in the App session and shortcut focus following the current view. Plain keeps Hotview mounted but hidden; `setRawContent` updates the same Y.XmlFragment without a separate Y.Text, and value synchronization reflects remote edits in source. Movement, split resizing, maximize/restore, mobile stacking, and Esc/back follow shared docking/panel behavior.
- The dock button and shortcut share `memoOpen`. Other dock selections retain memo content and collaboration. Per-project `chrome.memoOpen` stores open state; the dock ledger stores layout. Normalization removes the old `tasks` kind/item but preserves task files.
- The new `tasks` kind and dock item requested by the user on 2026-10-03 are registered again as the [object-based task panel](task-list.md). The removal record above concerns the previous hierarchical tasks and is separate from memo storage and collaborative editing.
- The body reuses `@mew/editor` Hotview and `useCollab`, remains read-only through initial sync/reconnection, and has no character-count bar. Table widths are shared CRDT attributes, not project table-layout data. First opening connects; closing and per-project dock remounts retain the document, undo state, and unsent changes on this page. Closed-window awareness is removed, and remote awareness disappears immediately on disconnect. Title `PresenceDots` deduplicates open awareness colors by account.
- Initial connection and automatic recovery show the shared three-dot indicator beside the title with a translated accessible loading name. The read-only body retains position/content; connection hides the indicator. Recovery neither shows connection-loss copy nor requests refresh. Presentation follows the [shared UI contract](ui-contracts.md); retry lifecycle follows the collaboration rules above.
- `shared/shared-memo.ts` reserves `__mew_shared__:memo` across roots/projects. For this exact key only, `authorizeCollab` checks login and collaboration permission instead of a file path. Existing WebSocket checks still reject guests, temporary-password states, and revoked permission; other rooms retain file checks.
- Regular file rooms retain their in-memory relay and file autosave. Only the reserved room uses the `RoomDoc` adapter in `server/shared-memo.ts`, atomically persisting version and base64 full Yjs update to `DATA_DIR/shared-memo.json`. An empty paragraph is seeded once to prevent duplicate simultaneous initialization. The server replaces and broadcasts state only after saving the candidate. Failure preserves the old room/file and reconnects clients to resend local changes; corruption never overwrites storage with an empty memo. CRDT IDs and deletions survive, so reconnects and server restarts do not reseed text.
- This room has no project file bridge and is excluded from `closeAllRooms` on root switching. The last browser disconnect triggers normal in-memory room cleanup. Workspace file APIs cannot expose its storage file.
- Verification uses `server/shared-memo.test.ts` for concurrent merging, deletion, reloading, save failures, corruption, and authentication boundaries, and `server/shared-memo-ui.test.ts` for actual two-browser collaborative editing with Hotview and WebSocket, focus toggling, participants, closing, shared dock movement/resizing/maximizing, project remounting, keyboard, mobile, themes, and reopening.
- `src/components/shared-memo-startup.browser.test.ts` checks delayed module focus, indicator-only initial connection and recovery, read-only protection, content preservation after recovery, and restoring focus to the current opener on close.
- Mention and slash state callbacks are initialized before calling `useEditor` so that synchronous initialization callbacks do not access undefined functions when a memo editor with an existing CRDT remounts after a project switch.
- The UI test's reopened-body check excludes collaboration cursor names from a cloned DOM. Callbacks executed in the browser specify only structural types for the required DOM members, allowing checks under the server TypeScript configuration without the DOM library.

## Active mew sessions (presence)

- The project header shows active sessions in a 16×16px square outline matching the fullscreen icon. `presence?.sessions.length ?? 1` means 1 when unavailable and 0 for an empty list. Counts of 100 or more display **99+** with the exact count in the accessible name and tooltip. The button opens sessions/history; appearance follows the [shared UI contract](ui-contracts.md).
- `/api/presence`, the header, and the dialog count **browser tabs/windows**, including multiple tabs per account, background tabs, and guests. They exclude the login screen and are independent of login-cookie and agent-execution counts.
- `server/presence.ts` adds `activeSessions: {selfId, sessions}` to `participants`; `shared/active-sessions.ts` owns the types. The public connection UUID is unrelated to an authentication token. Server authentication and profiles supply email/display name; client identity is rejected.
- The list contains the browser and device (inferred from User-Agent), connection time, and client-reported project name, focused file, and background status. Sessions without an open file are retained, grouped by user, and marked to identify the current tab. Closed connections are removed immediately, and a 30-second ping/pong removes unresponsive connections on the next cycle. Reconnection counts as a new connection.
- The list is sent only to logged-in users. Each connection's authentication is revalidated before transmission, and neither the list nor the total count is sent to guests or users required to change their password. Guests' existing per-path participant colors continue to be filtered by viewing permission.
- `usePresence` reports file, project, and visibility changes over the existing socket. Disconnect clears the list, resets the header to 1, and shows connecting state in an open dialog. It retries after 3 seconds without retaining stale counts. The dialog uses the overlay stack for Esc/back and supports outside clicks and its close button.
- `AgentPanel` passes the `busy` state of open, connected agent tabs in the current project (including CLI commands running in those tabs) to `App`. Idle tabs, closed tabs, and ordinary tmux are excluded; merely hiding the panel does not exclude them. Switching projects, removing the panel, or disconnecting clears the previous aggregation. `usePresence` reports `focus.runningAgents` on state changes and every 30 seconds.
- The server accepts only safe integers ≥ 0 in socket `agents: {running, reportedAt}` and assigns the timestamp. Missing/invalid reports and reports older than 90 seconds become `null`. This per-browser observation covers the current project, not server-wide execution; duplicated work across browsers prevents a meaningful total. State changes enter the history DB below. JS heap collection, transmission, and display remain removed unless requested by the user.
- Verification: `server/presence-sessions.test.ts` checks connection counts, navigation, authentication removal, and guest blocking using actual WebSockets. `server/active-sessions-ui.test.ts` checks mobile and desktop popups and reconnection indicators in the browser.
- Previous profile display verification (2026-10-19): 3 checks in `src/utils/active-session-people.test.ts` and 1 check in `server/active-sessions-ui.test.ts` passed. At that time, checks covered excluding my account's multiple devices, deduplicating other accounts, counting guests, profile images and fallback displays, connecting indicators, and the existing sessions and history dialog.

### Connection history, daily queries, and Excel

- Follows [ADR 0183](../history/decisions/0183-mew-presence-history-sqlite.md). `server/presence-history.ts` stores connections (`connections`) and status intervals (`intervals`) in `MEW_DATA_DIR/presence/history.sqlite`. It uses Node's built-in SQLite, WAL, FULL synchronization, transactions, version checks, and indexes; file permissions are 0600 and new directory permissions are 0700. It is independent of external Postgres configuration.
- Identity comes from server authentication, and guests are recorded anonymously. Stored fields include UUID, email, display name, inferred browser/device, connection/observation/end times, project/file, foreground status, and observed agent count. Authentication tokens, cookies, IP addresses, raw User-Agent, and JS heap data are not stored. The hash of the project's actual root is used only to revalidate location information permissions and is not exported in responses or Excel files.
- Initial connections and state changes are saved immediately. Identical state does not create a new interval; it updates at intervals of at least 30 seconds using that connection's own observation time. Reports from other tabs do not extend the connection's observation time. Normal disconnections close at the end time; unresponsive sockets close at the last observation plus at most 60 seconds. After a restart, remaining unclosed connections are closed at their last DB observation time, and new sockets use new UUIDs.
- History accumulates only after this is applied and is not automatically deleted. Corrupted data and unsupported versions are not overwritten. Save failures are logged on the server, and history queries indicate failure with 503. Successful records from other sockets do not clear the failure state.
- `GET /api/presence/history` and `GET /api/presence/history/export` accept `dayFrom`, `dayTo`, `from`, `to` (milliseconds), and optional `person` (email or `guest`). The browser sends local date boundaries, and a day can be at most 25 hours long, including daylight saving time. The time range is `[from,to)` within a single day; connections overlapping that interval are included and returned clipped to its boundaries. If a nonexistent daylight saving time produces an empty range, the UI extends the end time to the next valid time.
- The response contains `records`, `people` for the entire day, `recordedSince`, and `generatedAt`. Intervals contain the connection UUID, interval ID, original connection time, clipped start/end, and end time. Login and password-change status are checked, and the same identity viewing scope as the current session list is applied. Each location is redacted after checking current file viewing permission and whether the actual root matches; the same redaction applies to Excel. The response is `no-store`.
- The history tab provides date, person, and start/end time filters, connection tab counts by time slot, per-person device timelines, foreground/background distinctions, and a detailed list (50 items at a time). Time-slot counts are the number of unique tabs observed during that time, not the peak concurrent connection count. Total observed time double-counts parallel tabs and is not work time. The timeline merges adjacent intervals with the same foreground status and displays up to 100 tabs per person. Details and Excel are not subject to this visualization limit. Today's history is re-fetched every 30 seconds, and stale requests are canceled when filters change or the dialog closes.
- A single query or Excel export supports at most 50,000 state intervals. Exceeding this returns 400 and requires a narrower time/person range rather than silently omitting records. Excel exports are actual OOXML `.xlsx` files generated on the server with the same filters, containing UTC times, observed duration in minutes, locations, and states. They provide frozen headers, filters, and bold headers, and user text is written as inline strings rather than formulas. `server/session-history-xlsx.ts` generates the ZIP package and XML ([Microsoft structure documentation](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document)).
- `server/presence-history.test.ts` checks persistent storage, state separation, deduplication of identical reports, midnight/time/person filters, reload/interruption recovery, preservation of corrupted data, authentication/permission redaction, daylight saving time, and actual XLSX round trips. `server/active-sessions-ui.test.ts` checks mobile/desktop, themes, filters, time graphs, dropdown Esc behavior, matching download scope, empty history, error retries, and focus restoration.
- For backups, treat this as a permanent ledger rather than a cache. Shut down the server and back up the server data directory, including the `presence/` directory, or use SQLite online backup. Copying only `history.sqlite` while the server is running may omit the latest records in the WAL. Do not attempt recovery by deleting the directory.

## Member chat (`DATA_DIR/chat.json`)

Each person has one group chat and 1:1 DMs. Delivery uses **presence signals + REST re-fetching**, without a dedicated socket. `{type:'chat'}` carries no content because presence also reaches guests. See [ADR 0050](../history/decisions/0050-mew-chat-dm-and-read-receipts.md).

**There is no room identifier:** `to` (recipient array) means DM; absence means group chat. `conversationsOf` in `server/chat.ts` and UI `inConversation` compute viewer-relative conversations and **must change together**.

| Request | Action |
| --- | --- |
| `GET /api/chat` | **Only what that person can see** — `{messages, unread, canDeleteHistory}`. Other people's DMs are not included in the response. Each message has `unread` (number of recipients who have not read it yet), and the `unread` map contains the unread count for **me** per conversation. `canDeleteHistory` is true only for the owner |
| `POST /api/chat` `{text, to?}` | Providing `to` makes it a DM. Only existing accounts are accepted as recipients |
| `DELETE /api/chat` `{conversation}` | Both owner status and chat permission are required. Permanently deletes from the ledger messages that appear to the current user as belonging to that conversation and returns `{ok, deleted}`. The group chat is `group`; a DM uses the other person's email. Other conversations and other people's DMs are retained; multi-recipient messages are deleted in full. When a change occurs, a chat signal with no content is broadcast |
| `POST /api/chat/read` `{conversation}` | Records that the conversation has been read. The conversation key is `group` or the other person's email |

- **Read pointers use the conversation's last-message timestamp at read time, not the current time.** Otherwise, a new message in the same millisecond could appear read. Ledger timestamps must be **strictly increasing** (`max(now, 마지막+1)`); these paired rules must change together.
- Deletion preserves read pointers. New timestamps exceed both the ledger's last message and every stored read pointer, including when deletion/resending happen within one millisecond.
- Broadcast read state **only when it changes**; repeatedly writing it while the window is open causes an infinite broadcast loop.
- The 500-line limit is shared by the group chat and DMs

`useChatNotifications` collects incoming notices outside the chat panel while a signed-in account has chat permission. It establishes a silent REST baseline, serializes subsequent reads on chat signals, and reconciles on permission/reconnection and foreground events. Pending signals cause one follow-up read rather than concurrent requests. Cleanup prevents a response from an old identity or permission subscription from publishing notices.

`createChatNoticeTracker` uses the server's strictly increasing message timestamps as a high-water mark that never decreases after deletion or truncation. It excludes the current author and nonrecipient DMs, deduplicates message IDs, and publishes the shared `chat` notice with `target: 'chat'` and a viewer-relative `chatConversation`. The notification stores the sender, never the body. `App` opens that conversation through the existing workspace panel controls, and `ChatPanel.conversationRequest` handles initial and repeated navigation requests. Requirements and limits follow [recipient notifications](../features/collaboration-comments-chat/group-chat-direct-messages-and-read-status.md#recipient-notifications).

## Panel state subscriptions

The Git working tree, commit list, working diff, feature list, debugger state, and browser analysis state share `/api/live/ws`. After the initial HTTP fetch, subscriptions to the same resource are consolidated onto a single browser socket. The server shares reads by account, root, permission, and resource, checking the debugger every 1 second and the others every 2 seconds. It sends no data frame when state is unchanged.

Initial connections and reconnections receive a full `snapshot`; subsequent changes are sent as top-level field `patch` and a list of deleted fields. The client resubscribes on a revision/base mismatch. Permissions are rechecked when projects or permissions change and after queries complete; identical error messages are not repeatedly sent. Hidden pages close the socket and reconnect when visible again. The connection and listeners are cleaned up when the last subscription is removed. P2P transport is also allowed through the same path.

`server/live-socket.test.ts` checks read sharing, omission of unchanged transmissions, field patches, resubscription, and permission revocation while in progress. Git, feature, and debugger UI tests provide fixtures that use this subscription.
