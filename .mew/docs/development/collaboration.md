## Collaboration rooms (Yjs relay)

- `server/collab.ts` — Rooms, clients, awareness, and `/api/collab` WebSockets. Client room name = `프로젝트:상대경로`; internal server key = `루트 절대경로` + NUL + client room name. Collaborative editing is shared within the same root, while identically named files in different roots are separated. Path and permission checks for a connection are fixed to the account's root at connection time, and another account switching projects does not disconnect the room ([per-account path contract](architecture.md#per-account-active-project)).
- `server/syncCodec.ts` — Frame encoding/decoding. **The wire format is the code coupling contract**: outer varUint channel (`0` sync · `1` awareness) + varUint type within sync (`0` step1 · `1` step2 · `2` update) + varUint8Array body. It must match y-protocols byte for byte, and `server/syncCodec.test.ts` checks this — a mismatch silently breaks every open tab at deployment time. For untrusted bytes, it returns `null` without throwing
- `server/roomDoc.ts` — Two CRDT backends (JS Yjs · Rust yrs). Only three interfaces are required: `stateVector()` · `encodeStateAsUpdate(sv?)` · `applyUpdate(update)`. `applyUpdate` returns **the update newly received by the room** (`null` if none) — use this value for broadcasting. Computing it from a state vector diff makes deletion-only updates appear as empty diffs and disappear
- `server/collabAgent.ts` — Disk-to-room bridge. **An in-process client** that holds its own Y.Doc + awareness and **connects through the room's** `connect()` — it does not hold the room's doc (which would prevent switching backends). A loopback socket is not used because it would require opening a bypass around `authorizeCollab` (guest blocking). This is the intended feature that injects `.md` edited in a terminal into an open Yjs room in real time with the `agent` cursor — it is unrelated to the agent window removed on 2026-07-25, so do not confuse the two and remove it. The `appWrites` echo ledger protects normal user typing
- Authentication, `MAX_ROOMS`, awareness, and room lifetime remain in JS regardless of the backend. **Only actual connected users** keep a room alive — counting the bridge's in-process client would prevent rooms from ever closing, causing headless editors and fs watchers to accumulate
- `useCollab` imposes a 10-second limit from socket creation to the first document sync response. If it stalls without a response during or after connection, it discards the socket without waiting for a close event and reconnects at intervals starting at 300 ms and increasing to a maximum of 3 seconds. After the first document response, it clears the timeout timer and resets the retry interval. It ignores late events from previous sockets and preserves Y.Doc, unsent edits, and undo state between reconnections. `server/collab-reconnect-ui.test.ts` verifies connection/sync stalls, late responses, edit preservation, timer cleanup after success, and unmount cleanup.

Active file body retrieval and the collaboration connection are prepared in parallel. The server independently checks collaboration and file editing permissions when the socket connects, and the client attaches the prepared document to the editor only after the file response confirms the body and editing permission. Before confirmation, it neither seeds from cached content nor autosaves. Failure, denied permission, or tab switching closes the prepared connection without retaining an inactive room. Detailed scope follows the [file retrieval contract](file-loading.md) and [ADR 0014](../decisions/0014-parallel-file-collaboration.md).

The Rust backend is optional and disabled by default ([ADR 0035](../history/decisions/0035-mew-collab-rooms-rust-yrs.md)):

```bash
npm run build:native        # native/collab (cargo, napi-rs) → native/collab/mew-collab.node
MEW_COLLAB_RUST=1 npm run serve
```

`.node` is a platform-specific artifact and is not committed. If `MEW_COLLAB_RUST=1` is set but loading fails, **it throws instead of silently falling back to JS** — uncertainty about which implementation is running is the greatest risk in the collaboration path.

The server's headless editor DOM provides `self` pointing to the same Window as `window` and `document`. `server/collabAgent.ts` prepares the required browser globals before loading editor dependencies and does not overwrite existing globals. RAG and Transformers.js execution paths are excluded from the current collaboration contract under the [removal decision](../history/decisions/0176-mew-remove-local-rag.md).

`server/collab-dom.ts` explicitly blocks JavaScript execution, script files, CSS files, images, iframe loading, file system HTTP requests, and all frame navigation in this DOM. Asynchronous fetch and synchronous requests are also rejected before transmission. HTML in externally modified Markdown is parsed only as document data. This boundary does not rely on Happy DOM defaults, and `server/collab-dom.test.ts` checks preservation of normal content, non-execution of inline code, and blocking of requests and navigation.

## Account theme change notifications

When an account theme is saved, `broadcastAccount` sends `{type:'theme'}` only to presence connections for the same account whose current authentication has been revalidated. It does not send it to other accounts, guests, or connections whose authentication has been revoked. The signal contains neither settings content nor the account ID; the client queries REST again using its logged-in session. `usePresence` forwards the `mew:theme-changed` event. [Account themes](browser-storage.md#account-themes) owns re-fetching on return to the screen or reconnection, save races, and cache boundaries.

## Shared memo

- Opening the panel or switching docks focuses the non-editable root of `SharedMemo`. Completing the collaboration connection or switching views does not automatically focus the body; direct interaction with the body opens the mobile keyboard. Explicit body focus by pressing `Ctrl/Cmd+M` while focus is outside an already open memo is retained.

- The memo body has 16 px of top padding, and the first block's top margin is removed. The standard document editor's horizontal margins, font size, and line height are retained.
- At the user's request on 2026-10-01, the memo popup was converted to a docked panel and the task panel was removed. Popup movement, 8-direction resizing, and viewport position correction are not provided.
- The memo's mobile modifier keys are controlled by passing detection results from `useMobileKeyboard` and the panel's open state to `Editor.showMobileKeyBar`. When the keyboard closes, the keys are hidden and the Ctrl and Shift toggles are cleared.
- App-owned `useSharedMemo` maintains the CRDT, unsent changes, memo value, participants, focus, and shortcuts outside the per-project DockWorkspace. The default `toggleMemo` combination is `Ctrl+M`, and Cmd is also accepted. It distinguishes closed → open, external focus → bring to front/focus body, and internal focus → close; repeated keydown events and IME composition do not toggle it again.
- `SharedMemo` renders in `DockPanel(id/kind=memo)` when the user is logged in and has collaboration permission. It uses a shared 36 px header, DockGrip, memo title tab, PresenceDots, and close button. The body provides a toggle between Hotview and the CodePane source view (Plain) in DockInlineBody. View state is maintained in the App-owned session, and shortcut focus follows the current view. Even in Plain, Hotview remains mounted but hidden, and `setRawContent` applies changes to the same Y.XmlFragment. No separate Y.Text is created, and remote edits are reflected in the source through value synchronization. Desktop movement, resizing at split boundaries, maximize/restore, and the mobile front stack and Esc/back behavior follow the shared docking/panel path.
- The dock button and shortcut update the same `memoOpen` state, and switching to another dock item preserves the open memo's content and collaboration connection. Open state is stored in the per-project `chrome.memoOpen`, and layout is stored in the dock ledger. The old `tasks` kind and dock item are removed during normalization, while task storage files are preserved.
- The new `tasks` kind and dock item requested by the user on 2026-10-03 are registered again as the [object-based task panel](task-list.md). The removal record above concerns the previous hierarchical tasks and is separate from memo storage and collaborative editing.
- The body reuses Hotview from `@mew/editor` and `useCollab`. It remains read-only while waiting for initial sync or reconnection, and no character-count status bar is created. Table widths are shared as CRDT attributes and are not saved in the project's table-layout file. It connects only when first opened and preserves the document, undo state, and unsent changes on the current page even after closing. The collaboration document and unsent changes also survive remounting the per-project docking area. Awareness user information for closed windows is removed. `PresenceDots` next to the title displays deduplicated per-account colors from open awareness, and remote awareness is removed immediately upon disconnection.
- A single reserved room `__mew_shared__:memo` in `shared/shared-memo.ts` is used across all roots and projects. Only for this exact key, `authorizeCollab` checks login and collaboration permission instead of checking a file path. Existing WebSocket access checks continue to block guests, temporary-password states, and revoked permissions. File permissions for other rooms remain unchanged.
- The in-memory relay and file autosave for regular file rooms are retained. Only the reserved room uses the `RoomDoc` adapter from `server/shared-memo.ts`, atomically saving the version and a base64 full Yjs update to `DATA_DIR/shared-memo.json`. The server seeds an empty paragraph once to prevent duplication from simultaneous first connections. After saving a candidate change, it replaces and broadcasts the room state; on failure, it preserves the existing room state and file and reconnects clients so they resend local changes. Corrupted stored data is not overwritten with an empty memo. CRDT identifiers and deletion information are also preserved, so text is not reseeded on reconnection or server restart.
- This room does not attach the project file bridge and is also excluded from `closeAllRooms` during root switching. When the last browser connection closes, the in-memory room is cleaned up under the existing lifetime rules. The storage file is not exposed through the workspace file API.
- Verification uses `server/shared-memo.test.ts` for concurrent merging, deletion, reloading, save failures, corruption, and authentication boundaries, and `server/shared-memo-ui.test.ts` for actual two-browser collaborative editing with Hotview and WebSocket, focus toggling, participants, closing, shared dock movement/resizing/maximizing, project remounting, keyboard, mobile, themes, and reopening.
- Mention and slash state callbacks are initialized before calling `useEditor` so that synchronous initialization callbacks do not access undefined functions when a memo editor with an existing CRDT remounts after a project switch.
- The UI test's reopened-body check excludes collaboration cursor names from a cloned DOM. Callbacks executed in the browser specify only structural types for the required DOM members, allowing checks under the server TypeScript configuration without the DOM library.

## Active mew sessions (presence)

- The project header displays the total number of active sessions inside a square outline measuring 16×16px, the same size as the fullscreen icon. The number is `presence?.sessions.length ?? 1`: 1 if the list is unavailable, and 0 if the actual list is empty. Counts of 100 or more are abbreviated as **99+**, with the actual count provided in the accessible name and tooltip. Pressing the button opens the existing sessions and connection history dialog. Appearance follows the [shared UI contract](ui-contracts.md).
- The list sent by `/api/presence`, the header number, and the connection count in the dialog all represent **session counts per browser tab or window**. Multiple tabs for the same account, background tabs, and guests each count separately. These counts are independent of login cookie counts and agent execution counts, and the login screen is not counted.
- `server/presence.ts` adds `activeSessions: {selfId, sessions}` to the existing `participants` message. The canonical source for types is `shared/active-sessions.ts`. The connection UUID is for public display and is unrelated to the authentication session token. Email and display name are determined by server authentication and the user profile; client-supplied identity is not accepted.
- The list contains the browser and device (inferred from User-Agent), connection time, and client-reported project name, focused file, and background status. Sessions without an open file are retained, grouped by user, and marked to identify the current tab. Closed connections are removed immediately, and a 30-second ping/pong removes unresponsive connections on the next cycle. Reconnection counts as a new connection.
- The list is sent only to logged-in users. Each connection's authentication is revalidated before transmission, and neither the list nor the total count is sent to guests or users required to change their password. Guests' existing per-path participant colors continue to be filtered by viewing permission.
- `usePresence` updates state over the same socket when the file, project, or document visibility changes. If the socket disconnects, it clears the list and resets the header number to 1. An open dialog shows a connecting state. It reconnects after 3 seconds without retaining the stale number. The dialog supports Esc/back through the shared overlay stack, outside clicks, and a close button.
- `AgentPanel` passes the `busy` state of open, connected agent tabs in the current project (including CLI commands running in those tabs) to `App`. Idle tabs, closed tabs, and ordinary tmux are excluded; merely hiding the panel does not exclude them. Switching projects, removing the panel, or disconnecting clears the previous aggregation. `usePresence` reports `focus.runningAgents` on state changes and every 30 seconds.
- The server stores only safe integers greater than or equal to 0 as the socket's `agents: {running, reportedAt}` and assigns the timestamp itself. Reports older than 90 seconds, missing reports, and invalid values become `null`. This is an observation of the current project per browser, not a server-wide execution count. The same work may be duplicated across browsers, so no total is provided. Observed state changes are stored in the connection history DB below. JS heap measurement, transmission, and display have been removed and will not be reintroduced until the user requests them.
- Verification: `server/presence-sessions.test.ts` checks connection counts, navigation, authentication removal, and guest blocking using actual WebSockets. `server/active-sessions-ui.test.ts` checks mobile and desktop popups and reconnection indicators in the browser.
- Previous profile display verification (2026-10-19): 3 checks in `src/utils/active-session-people.test.ts` and 1 check in `server/active-sessions-ui.test.ts` passed. At that time, checks covered excluding my account's multiple devices, deduplicating other accounts, counting guests, profile images and fallback displays, connecting indicators, and the existing sessions and history dialog.

### Connection history, daily queries, and Excel

- Follows [ADR 0183](../history/decisions/0183-mew-presence-history-sqlite.md). `server/presence-history.ts` stores connections (`connections`) and status intervals (`intervals`) in `MEW_DATA_DIR/presence/history.sqlite`. It uses Node's built-in SQLite, WAL, FULL synchronization, transactions, version checks, and indexes; file permissions are 0600 and new directory permissions are 0700. It is independent of external Postgres configuration.
- Identity comes from server authentication, and guests are recorded anonymously. Stored fields include UUID, email, display name, inferred browser/device, connection/observation/end times, project/file, foreground status, and observed agent count. Authentication tokens, cookies, IP addresses, raw User-Agent, and JS heap data are not stored. The hash of the project's actual root is used only to revalidate location information permissions and is not exported in responses or Excel files.
- Initial connections and state changes are saved immediately. Identical state does not create a new interval; it updates at intervals of at least 30 seconds using that connection's own observation time. Reports from other tabs do not extend the connection's observation time. Normal disconnections close at the end time; unresponsive sockets close at the last observation plus at most 60 seconds. After a restart, remaining unclosed connections are closed at their last DB observation time, and new sockets use new UUIDs.
- History accumulates only after this is applied and is not automatically deleted. Corrupted data and unsupported versions are not overwritten. Save failures are logged on the server, and history queries indicate failure with 503. Successful records from other sockets do not clear the failure state.
- `GET /api/presence/history` and `GET /api/presence/history/export` accept `dayFrom`, `dayTo`, `from`, `to` (milliseconds), and optional `person` (email or `guest`). The browser sends local date boundaries, and a day can be at most 25 hours long, including daylight saving time. The time range is `[from,to)` within a single day; connections overlapping that interval are included and returned clipped to its boundaries. If a nonexistent daylight saving time produces an empty range, the UI extends the end time to the next valid time.
- The response contains `records`, `people` for the entire day, `recordedSince`, and `generatedAt`. Intervals contain the connection UUID, interval ID, original connection time, clipped start/end, and end time. Login and password-change status are checked, and the same identity viewing scope as the current session list is applied. Each location is redacted after checking current file viewing permission and whether the actual root matches; the same redaction applies to Excel. The response is `no-store`.
- The history tab provides date, person, and start/end time filters, connection tab counts by time slot, per-person device timelines, foreground/background distinctions, and a detailed list (50 items at a time). Time-slot counts are the number of unique tabs observed during that time, not the peak concurrent connection count. Total observed time double-counts parallel tabs and is not work time. The timeline merges adjacent intervals with the same foreground status and displays up to 100 tabs per person. Details and Excel are not subject to this visualization limit. Today's history is re-fetched every 30 seconds, and stale requests are canceled when filters change or the dialog closes.
- A single query or Excel export supports at most 50,000 state intervals. Exceeding this returns 400 and requires a narrower time/person range rather than silently omitting records. Excel exports are actual OOXML `.xlsx` files generated on the server with the same filters, containing UTC times, observed duration in minutes, locations, and states. They provide frozen headers, filters, and bold headers, and user text is written as inline strings rather than formulas. `server/session-history-xlsx.ts` generates the ZIP package and XML ([Microsoft structure documentation](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document)).
- `server/presence-history.test.ts` checks persistent storage, state separation, deduplication of identical reports, midnight/time/person filters, reload/interruption recovery, preservation of corrupted data, authentication/permission redaction, daylight saving time, and actual XLSX round trips. `server/active-sessions-ui.test.ts` checks mobile/desktop, themes, filters, time graphs, dropdown Esc behavior, matching download scope, empty history, error retries, and focus restoration.
- For backups, treat this as a permanent ledger rather than a cache. Shut down the server and back up the server data directory, including the `presence/` directory, or use SQLite online backup. Copying only `history.sqlite` while the server is running may omit the latest records in the WAL. Do not attempt recovery by deleting the directory.

## Member chat (`DATA_DIR/chat.json`)

One group chat + 1:1 DMs for each person. Delivery uses **presence signals + REST re-fetching** without a dedicated socket — the `{type:'chat'}` signal contains no content (that socket also reaches guests). The model is defined in [ADR 0050](../history/decisions/0050-mew-chat-dm-and-read-receipts.md).

**There is no room identifier.** `to` **(recipient array) means a DM; its absence means the group chat.** Conversations are computed from the viewer's perspective (`conversationsOf` in `server/chat.ts`). The UI's `inConversation` uses the same rules, so **both must be changed together.**

| Request | Action |
| --- | --- |
| `GET /api/chat` | **Only what that person can see** — `{messages, unread, canDeleteHistory}`. Other people's DMs are not included in the response. Each message has `unread` (number of recipients who have not read it yet), and the `unread` map contains the unread count for **me** per conversation. `canDeleteHistory` is true only for the owner |
| `POST /api/chat` `{text, to?}` | Providing `to` makes it a DM. Only existing accounts are accepted as recipients |
| `DELETE /api/chat` `{conversation}` | Both owner status and chat permission are required. Permanently deletes from the ledger messages that appear to the current user as belonging to that conversation and returns `{ok, deleted}`. The group chat is `group`; a DM uses the other person's email. Other conversations and other people's DMs are retained; multi-recipient messages are deleted in full. When a change occurs, a chat signal with no content is broadcast |
| `POST /api/chat/read` `{conversation}` | Records that the conversation has been read. The conversation key is `group` or the other person's email |

- **The read pointer is the timestamp of the conversation's last message at the moment it is read, rather than the current time.** Using the current time would bury the next message arriving in the same millisecond as already read. For the same reason, message timestamps in the ledger are made **strictly increasing** (`max(now, 마지막+1)`) — these two rules are paired, so do not change them separately
- Read pointers are preserved after deletion. New message timestamps are generated to be greater than both the ledger's last message timestamp and every stored read pointer, preventing new messages from being treated as already read even when deletion and resending occur in the same millisecond.
- Read state is broadcast **only when it changes**. Continuously recording it while the window is open causes an infinite broadcast loop
- The 500-line limit is shared by the group chat and DMs

## Panel state subscriptions

The Git working tree, commit list, working diff, feature list, debugger state, and browser analysis state share `/api/live/ws`. After the initial HTTP fetch, subscriptions to the same resource are consolidated onto a single browser socket. The server shares reads by account, root, permission, and resource, checking the debugger every 1 second and the others every 2 seconds. It sends no data frame when state is unchanged.

Initial connections and reconnections receive a full `snapshot`; subsequent changes are sent as top-level field `patch` and a list of deleted fields. The client resubscribes on a revision/base mismatch. Permissions are rechecked when projects or permissions change and after queries complete; identical error messages are not repeatedly sent. Hidden pages close the socket and reconnect when visible again. The connection and listeners are cleaned up when the last subscription is removed. P2P transport is also allowed through the same path.

`server/live-socket.test.ts` checks read sharing, omission of unchanged transmissions, field patches, resubscription, and permission revocation while in progress. Git, feature, and debugger UI tests provide fixtures that use this subscription.
