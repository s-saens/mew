## Installable web app and startup guidance

For direct access, `index.html` links to `public/manifest.webmanifest`, PNG icons (192·512px), and an Apple touch icon (180px). In the manifest, `display` is `standalone`, and `display_override` is ordered `fullscreen` → `standalone`. Supported browsers preferentially request the `fullscreen` display mode; unsupported browsers fall back to `standalone`. Launching the installed app is separate from entering `requestFullscreen()` through the Fullscreen API, and installation alone does not guarantee keyboard lock permission or resolve interception of mobile back navigation. Installation requires a secure context over HTTPS or localhost.

The installation assets `public/app-icon-{180,192,512}.png` display a static gradient mixing purple (`#30264c`) and teal (`#123841`) on the default Midnight navy background (`#101827`), with a light inner mark (`#dbe7f5`) and no outer square border. The background uses the default palette from `shared/theme.ts` and the 135° radial gradient from `themeBackgroundImage()`, capturing the same `inset: -8%` area as the app background in a stationary state. Preserve the size, position, and stroke width of the inner path from `public/favicon.svg`, centered within an area spanning 60% of the width and height. The browser favicon and full loading logo retain their existing square borders. The validation and application status of the icon change follows the [work record](../work/app-icon-borderless.md).

Do not add a separate offline cache or service worker to support installation. The app uses the existing host, authentication, and connections, and cannot be used for work when the host is off or the network is unavailable. Retain Mewlink's existing service worker for relaying remote static resources; do not interpret it as offline work functionality.

Because Mewlink runs the installed host app in a nested frame, the top-level public device page needs a manifest, icons, and installation events. The central `/app.webmanifest?device=...` uses the public device path as `id` and `start_url`. The app receives installation availability and launch mode through the existing trusted MessagePort connection channel and forwards user actions on the install button to the parent page. Mobile manual installation instructions direct users to install from the public device page rather than an internal temporary launch URL. Changes to the Git-excluded `mewlink/src/app-manifest.ts`, the central connection parent, and the internal launcher take effect only when the user deploys them to the central frontend separately from the host Mew update.

Display startup guidance in the order installation → fullscreen. Provide an install button when the browser supplies an installation event. On mobile and desktop browsers that support installation, provide the manual installation path through the iOS share menu or browser menu even without an event. In other environments, show installation guidance only when an installation event is available. Hide both prompts when the initial load's installed display mode (`standalone`·`fullscreen`·`minimal-ui`, iOS `navigator.standalone`) or the `appinstalled` event confirms app launch or installation. Do not mistake subsequent Fullscreen API entry for installation, and hide installation guidance during regular web fullscreen.

Immediately save each installation/fullscreen prompt's **Don't show again** setting independently as a scoped browser setting. A prompt dismissed without checking the option stays hidden only for the current app lifetime. Approval request notifications take priority over both startup prompts, and prompts appear even when Mewpet is disabled or has no skin. Preserve remote viewer hide settings, actual fullscreen bindings, and retries after failure. The [Mewpet feature document](../features/appearance-accounts-operations/mewpet-mascot-notifications-and-breaks.md#app-installation-and-fullscreen-guides-at-startup) owns detailed prompt behavior, and the [browser storage contract](browser-storage.md#dont-show-again-for-startup-guidance) owns storage keys. Record the decision rationale in [ADR 0064](../decisions/0064-installable-web-app.md).

Actual Android/iOS installation and fullscreen/back navigation behavior in installed mode require verification on physical devices. Isolated browser checks that mock installation events, display modes, and the Fullscreen API do not replace this verification.

The three dots inherit the current text color. Arrange three equally sized circles in a row and vary each dot's transform scale and opacity over a 1.2-second cycle. Offset their phases by 160ms so they grow and shrink in sequence from the left without changing position. The circular indicator uses a 2px circular border in the current text color with only the top border transparent, rotating at a constant speed over a 0.8-second cycle. The full loading logo uses the square border and inner mark from `public/favicon.svg` as an inline SVG mask with the same coordinates and stroke width. Git-excluded Mewlink uses the same CSS and the `loadingIndicator` DOM helper. ## Shared scrollbars

Global rules in `src/index.css` handle native scrollbars in the editor, file explorer, terminal, and tables. Retain a width/height of 6px, rounded thumbs, and transparent tracks. The thumb is a gradient at 70% opacity mixing the theme background color (`--color-surface-deep`) with the text color (`--color-ink`), brightest at the point corresponding to the current scroll position divided by the maximum scroll distance (content size − viewport size). For vertical scrolling, the thumb is brightest at the top when scrolled to the top, at the center when halfway down, and at the bottom when scrolled to the bottom, becoming darker farther from that point. Horizontal scrolling reflects the left/right position in the same way. `src/utils/scrollbar-gradient.ts` collects each scroll event, including those in nested regions, and updates only that region's CSS variables each frame. By default, both ends mix 82% background color with 18% text color, and the highlighted point mixes 65% background color with 35% text color. On hover, increase the text color ratio to 25% at both ends and 45% at the highlighted point to enhance contrast, while retaining 70% opacity. Both solid and gradient themes follow the selected background and text colors. Manage colors through `--color-scrollbar-*` tokens. In Firefox, which does not support WebKit scrollbars, fall back to a thin solid color using the same theme color as the ends at 70% opacity, and continue hiding `.no-scrollbar` regions.

On touch devices, users can grab and drag an invisible area around the current scrollbar thumb. The touch area is 24px thick. For vertical scrollbars, its length is three times the larger of the thumb length and 44px (at least 132px before clipping); horizontal scrollbars retain the larger of the thumb length and 44px. Center the area on the thumb, shifting it inside the track at either end and capping its length at the track length. Preserve the scrollbar's visual thickness/color, content width, and drag ratio. Grabbing above or below the visible thumb must not jump the scroll position. `src/utils/scrollbar-touch.ts` distinguishes vertical, horizontal, RTL, and nested regions and updates the scroll position for single-finger dragging. Exclude regions without scrolling, `.no-scrollbar`, `overflow: hidden/clip`, and regions whose axes are misaligned by rotation or skew; do not intercept mouse operations, normal content swipes, or multitouch starts. Release dragging on touch end/cancel, and clean up global handlers started in `src/main.tsx` during HMR replacement. The [vertical touch-area work record](../work/scrollbar-touch-area.md) records verification and application status.

Validation on 2026-10-19: the 2 tests `server/scrollbar-touch-ui.test.ts`·`server/sidebar-touch-ui.test.ts` and TypeScript passed. Browser touch input confirmed vertical, horizontal, RTL, and nested operations, exclusion conditions, and preservation of the drag position after adding FileTree rows. Reviewed 390px mobile dark and 1100px PC light captures and checked that 6px scrollbars and content width were preserved.

## Active tab auto-scrolling

All horizontal tab bars use `TabScrollArea` from `@mew/ui`, and `useTabAutoScroll` inside the component handles bringing active/focused tabs into view. Apply the same rules to editor, agent, terminal, existing project, sheet, DB view, task view, account management, and active session window tabs. When the active tab changes through opening a new tab, Ctrl+number, or similar actions, or DOM focus moves into a tab, smoothly scroll only the minimum horizontal distance needed to bring that tab into view. Do not scroll tabs that are already visible.

Regular tabs indicate selection with `role="tab"` and `aria-selected`. For items that indicate an active state without an actual tab, such as `+` in the agent selector, mark the auto-scroll target with `data-tab-scroll-active`. Scrolling changes only the tab bar's horizontal position, without changing its vertical position, outer scrolling, or input focus. With `prefers-reduced-motion: reduce`, move immediately without animation.

Recheck active tab visibility after tab restoration, addition, renaming, and panel size/layout changes. Suppress this auto-scrolling during dragging to avoid conflicts with existing edge auto-scrolling.

For each direction with remaining scroll distance, overlay a chevron button on the last visible tab at that end of the tab bar. Show only the chevron and a dark shadow, without a background or border, and do not reduce the tabs' visible width. Move at a constant speed of 320px per second while the arrow is held, and stop immediately on release, input cancellation, or loss of window focus. Holding Enter or Space also moves the bar. Retain movement from direct manipulation even with reduced motion enabled. Map standard vertical wheel, Shift+wheel, and horizontal trackpad input to horizontal movement; do not convert Ctrl+wheel zoom into horizontal movement. At the ends, do not prevent the wheel's default behavior. Hide the corresponding button when the left/right end is reached, and hide both when there is no horizontal overflow. Recheck the remaining distance in each direction after scrolling, resizing, and tab addition, deletion, or renaming.

Arrows provide translated accessible names and shared tooltips. Activating them does not change the active tab, and pressing them with a pointer does not affect input focus or tab dragging/renaming. Preserve the position set by the user with the arrows until the next tab activation, focus movement, or layout change.

## Drag reordering motion

The agent `+` runtime list uses the vertical axis (`axis: 'y'`) and dedicated handles (`handleOnly: true`) from `useDragReorder`. Register rows as geometry and preview targets, and attach pointer events to the handles. Handles support immediate touch dragging with `touch-action: none`, while the rest of each row retains normal selection and scrolling. Apply the vertical axis to target detection and edge auto-scrolling as well, and preserve the existing default behavior of horizontal tabs.

File and document moves in the file explorer use the same duration and curve. Record positions immediately after a successful move and retain them until the actual tree update, mapping the moved path and descendant paths to new rows so they remain linked even if React recreates the rows. Surrounding rows move together, and scroll changes are excluded from movement distances. Expanding, searching, failing, or canceling alone does not start movement animations. `sidebar-move-ui.test.ts` validates asynchronous updates, intermediate positions, and reduced-motion transitions; `sidebar-touch-ui.test.ts` validates existing touch input and cancellation.

File, project, agent, and terminal tabs, task items, and docks transition between drag-induced layouts over 180ms using `cubic-bezier(0.22, 1, 0.36, 1)`. The shared `useReorderAnimation` records visible positions immediately before reordering and animates only transforms after React changes the layout. Consecutive moves continue from the current animated position to the new destination, and tab/dock target detection uses actual layout coordinates excluding animation to prevent jitter and back-and-forth reordering. A copy of the grabbed item follows the pointer immediately.

Surrounding queue rows and the dashed insertion placeholder move with the same duration and curve. Order persistence, drop, cancellation, and edit-lock contracts follow each feature's existing behavior. Apply keyboard reordering immediately, and omit position animations with `prefers-reduced-motion: reduce`. If the setting changes during dragging, also remove movement animations already in progress.

## Design guidelines: spacing and information density

**Use enough spacing to highlight content and clarify relationships. Create a sense of openness through orderly layouts and consistent spacing rather than the size of empty areas.** Along with readability and ease of operation, Mew's work UI prioritizes the information and workspace users can view and manage on one screen.

- Panels, settings, popups, and toolbars default to compact spacing. In keeping with the existing compact UI, generally start with 8–12px internal padding and 4–8px spacing within groups, increasing only as needed for meaningful separation, readability, and touch operation. Use concise padding and spacing suited to the content. Do not inflate the interface with decorative outer margins, accumulated padding in nested containers, or unnecessary minimum heights.
- Group related items closely, and add only the spacing needed to distinguish groups. Also express hierarchy through alignment, font size and weight, and color; do not rely on large gaps for every distinction.
- Allocate extra space on wide screens to body content, lists, and work areas. On mobile and in narrow panels, prevent excessive spacing from pushing primary actions offscreen or causing unnecessary scrolling.
- Remote desktop prioritizes the visible area of the actual remote screen. Apply the same density principles to connection/settings screens and controls, and prevent large guidance cards or empty areas from encroaching on the workspace. Distinguish letterboxing needed to preserve the video aspect ratio from decorative spacing.
- Even when increasing density, preserve readable text and line spacing, click/touch areas, focus indicators, and device safe areas. Reduce container padding and redundant space first; do not truncate content or make interactive targets excessively small.

Even when using design skills such as `impeccable`, prioritize this project's task-focused density standards. During review, check how well key content and controls remain visible at the same screen size and whether spacing actually helps distinguish sections and improve usability.

## Prefer icon buttons

For familiar actions such as close, refresh, copy, cancel, and disconnect, prefer icon buttons from the existing icon system over text buttons. Display an X icon for closing popups. Provide action names through translated `aria-label` and `data-tip` on the shared `HoverTipLayer`, and preserve keyboard focus, disabled, in-progress, and completed states. Mark the icon itself with `aria-hidden`. Retain short labels for actions such as starting login and authorization flows when an icon alone makes the primary action, target, or result unclear. Do not mechanically convert every button to an icon or excessively shrink interaction areas.

`HoverTipLayer` handles all `data-tip` attributes assigned to HTML elements and SVG lines and points. It immediately displays names on mouse hover, shows no tooltips for touch input, and hides them on click or pointer exit. SVG interaction targets also provide separate accessible names and keyboard behavior.

Panel and file explorer close buttons follow the task header: a 24×24px interaction area, a 14×14px `Xmark`, vertical centering in a 36px-high header, and a 4px right margin. They share icons, sizing, focus, and common tooltips through `PanelCloseButton`, without adding duplicate right padding to the header.

## Popup coordinates inside modals

`getFixedPopupLayout` (`packages/ui/src/fixed-popup-layout.ts`) in `@mew/ui` maps screen coordinates to CSS coordinates for fixed elements. It finds the actual containing element established by `backdrop-filter`, `filter`, transforms, contain, and similar properties, accounting for borders, scrolling, and axis-specific scaling. It calculates placement and dimensions within the intersection of the visual viewport and overflow/paint clipping regions extending from the containing element, preventing menu items from becoming invisible outside the modal. When space is insufficient, the menu scrolls internally.

`SelectField`, `ActionMenu`, file explorer favorites, account popups, mention lists, `FrontmatterPopover`, tag color selectors, compact `ColorPicker`, and `HoverTipLayer` share this calculation. Preserve existing portal targets, focus scopes, and Esc/back dismissal. The compact color picker is displayed with fixed positioning in the same DOM as its trigger to preserve form height and Tab order. Open selection lists and color pickers are repositioned by monitoring the viewport/scroll and observing theme and host changes. Rotated selectors on remote screens retain their existing inverse-matrix local placement, while simple translation and scaling use the shared calculation. Follow [Decision 0069](../decisions/0069-shared-fixed-popup-coordinates.md).

Input autofocus when opening dropdowns, windows, or search panels follows the `canAutoFocusInput()` conditions in `@mew/ui`. ## Theme Colors and Derived Accents

Color inputs use `ColorPicker` (`packages/ui/src/color-picker.tsx`) from `@mew/ui`. `value` and `defaultValue` are opaque 6-digit HEX values, and `onChange` passes only valid lowercase HEX values. The caller owns persistence and theme derivation and supplies translated labels. Instead of opening the OS color dialog, it expands a color area and hue, saturation, and brightness sliders below the field. Its inline placement follows the settings scroll area and mobile width without creating a separate portal or modal.

The color area uses pointer capture for mouse and touch dragging and clamps coordinates outside its bounds. The same values can be adjusted by keyboard through three range sliders with accessible names and current values. The hue and saturation being adjusted are preserved even for black and gray. Incomplete HEX values are not saved and are restored on blur or Esc. `useOverlayDismiss` handles Esc and Back first while the picker or HEX editor is active, keeping the settings dialog open, and returns focus to the color button after closing. Pressing outside also collapses it, and input is blocked when disabled.

Appearance settings select `ThemePalette` from `shared/theme.ts` (`background`, `text`, and `primary`, opaque 6-digit HEX values) as a single unit. The optional `gradient` stores `colors` containing two HEX colors, direction `angle`, and animation flag `animated`. Direction normalizes finite numbers to at least 0 degrees and less than 360 degrees, and the animation flag accepts only booleans. `background` remains the gradient base and solid-color fallback. `ThemeSettings` saves the selected `palette` and `custom` array together in server-side account state without saving derived tokens. `src/utils/theme-color.ts` re-exports the shared model and handles color derivation, browser migration, and initial display. APIs, per-account caches, change signals, and reconnection follow the [Account Theme Storage Contract](browser-storage.md#account-themes). Saved colors are normalized to lowercase, and invalid custom entries, duplicate combinations, and combinations matching presets are excluded. Combination comparisons include gradient presence, both colors, direction, and animation. For entries where only `gradient` is invalid, only the gradient is discarded, preserving the three valid colors. If the current theme is absent from the presets and list, it is included as a custom entry so it can be selected again. If saving fails, it remains usable in the current session.

If `mew:themes` is missing or the selected palette is invalid and there are no previous settings, the Midnight preset is used. The same default is used when storage cannot be read. If previous settings exist, the existing selection is preserved. Migration reads the `mew:theme` mode and `mew:theme-color`. It reads `accent` from the `mew:accent-color` object only when no theme color exists, and restores invalid legacy colors to the default `#4432a8`. It calculates the displayed accent for that mode from the legacy source and migrates it to the new `primary`, preserving the previous screen colors. Legacy settings are retained, and valid new settings take precedence.

When settings are read, if the selected solid-color palette exactly matches the three colors of the old Midnight, Rose, or Ocean preset and the stored custom list contains no identical solid-color palette, it is migrated to the new gradient preset. If the custom list contains the same combination, the user's saved solid colors are preserved. Migration does not occur during normalization or saving, preserving new solid-color custom themes.

`deriveThemePalette` maps `background`, `text`, and `primary` directly to `--color-surface-deep`, `--color-ink`, and `--color-accent`, respectively. It mixes the background and text colors to derive panels, hover states, borders, and secondary text. Component surfaces in light mode without a gradient use lower text-color mixing ratios of 3% for the base, 7.5% for raised, and 14% for hover to appear brighter. The same levels apply to bubbles, neutral buttons, inputs, and popups, while existing solid dark-mode levels are retained. The overall workspace background preserves the existing mix (dark 5.9%, light 4.6%) in a separate `--color-workspace`, and the body background color and gradient are also preserved. Contrast between the base background color and white/black determines `.dark`; status, code syntax highlighting, and inverted tokens follow the existing mode-specific CSS. Custom body text and primary color values are not automatically corrected; drafts with body text contrast below 4.5:1 against the base background or sampled gradient backgrounds display guidance.

For palettes with gradients, `surface`, `surface-raised`, and `surface-hover` are derived as 8-digit HEX values with alpha. Background and text colors are mixed more strongly at 10%, 21%, and 31% in dark mode and 8%, 14%, and 22% in light mode, with respective opacities of 48%, 58%, and 72%, allowing the overall background to show through neutral bubbles, buttons, and components. Three opaque counterpart tokens, `surface-solid`, `surface-raised-solid`, and `surface-hover-solid`, are also provided for all themes. Existing surfaces for themes without gradients, the original palette, overall workspace background, gradient, primary color, body text, borders, and default terminal background are preserved. This change applies only to derived tokens and does not migrate saved entries or draft structures.

Large workspace panel backgrounds are distinguished from the neutral surfaces of buttons and inputs. Git, tasks, debugger, notes, Git diff, SVG, media, spreadsheet and PDF previews, and panel loading backgrounds use `mew-panel-surface`. In gradient themes, these backgrounds, the `[data-dock-tab-bar]` tab bar, and the desktop dock rail are transparent so the full-screen background appears continuous. The Git commit form uses the same background. The large Gantt SVG grid background is transparent, and weekend shading uses the base background color at 32% opacity. ## Editor Tab Visits and Document Navigation

The editor separately manages **tab selection order within an editor pane** and **document visit history within a tab**. It follows the [Per-Tab Document Navigation Decision](../decisions/0044-editor-tab-navigation.md).

- Closing the active tab opens the most recently active remaining tab in the same editor pane. Closing an inactive tab preserves the current tab. For example, if tabs 1, 2, and 3 exist and a new tab 4 is opened from 1 and then closed, focus returns to 1. If no tabs remain, the existing empty-pane cleanup rules apply.
- A normal click on an internal document link, including a subdocument link, changes the document in the current tab of the clicked editor pane and appends it after the current history position. Opening another document after going back removes the existing forward history. Document navigation does not change the active tab or history in another editor pane.
- Ctrl/Cmd+click opens a new tab. The new tab's visit history starts with only the target document and does not duplicate the original tab's history.
- Document navigation and Back/Forward within a tab retain the originating tab even if the target document is open in another tab. `Tab.id` and `Pane.activeTabId` distinguish tabs displaying the same path, and each tab's document visit history remains independent. Sharing file bodies does not merge tab visit histories.
- Back and Forward move only the current tab's history position and do not add the destination document as a new visit. Selecting a tab alone does not change its document visit history. Document bodies, drafts, and save status follow existing per-file-path management and permission checks.
- `Tab.navigation` is an in-memory record for the tab session. Refreshing or restoring saved tabs merges duplicate tabs for the same document according to the existing restoration policy and restarts history with only the restored current document. Splitting a tab or moving it to another editor pane preserves its document visit history. The order for returning to recently active tabs is managed separately for each editor pane.
- At the far left of the floating file history toolbar, controls appear in the order **Back → Forward → Existing File History Tools**. They reuse the existing floating buttons' size, surface, spacing, and shared tooltips and provide translated accessible names. Back is disabled when no previous entry exists, and Forward is disabled when no next entry exists. Both buttons are disabled in a new tab.

Document navigation within a tab is separate from viewing historical file contents in Git and does not add document visits to mobile panel visit history or the browser's Back stack. [Links](../features/document-code-media-editing/links-file-references-and-attachments.md) owns link display, path resolution, and click contracts.

## Overlay dismissal rules (`useOverlayDismiss`)

**Whenever you create a popup, modal, or dropdown, you must** `useOverlayDismiss(onClose)`**call this hook.** It collects open overlays into a single app-wide stack so that Esc and **Android hardware Back** always close *only the most recently opened one*. Pressing Back over an unregistered popup closes the terminal or file explorer behind it, or leaves the page, instead of closing that popup.

- For auxiliary panels whose state App owns (file explorer, chat, terminal, agent panel, browser, Git, Android, and Features), the shared stack in `utils/mobile-panel-stack.ts` owns the front-to-back order and dismissal order of open panels, while mobile navigation history is managed separately. On mobile, selecting an open panel behind another brings it to the front without closing it; only reselecting the frontmost panel closes it. `hooks/use-panel-dismissals.ts` also registers only this frontmost panel as an overlay, keeping Back behavior aligned with z-index. Add new auxiliary panels to `WORKSPACE_PANEL_IDS` and the open/setter registry in `App.tsx`, and use the shared open/close/toggle/layer functions (type checking prevents missing registrations). Modals, popups, and dropdowns register themselves directly in their respective components. On mobile, this device's browser also remembers the **last frontmost window** for each root project, so the last viewed open window returns to the front after a refresh or restart.
- On mobile, opening a file from the file explorer, chat, terminal, or agent panel closes that window and immediately reveals the selected file's editor pane. The side-by-side panel layout on desktop is preserved.
- Mobile navigation history in `useWorkspacePanelDismissals` remembers up to 20 previous visits (including the editor), separately from the open panel stack. A visit consists of a panel ID and optional screen identifier and restoration callback. Registering each panel's current screen `key` and a `restore` that restores lightweight screen state in `navigation.screens` also records screen transitions within the same panel. Reselecting the same screen and screen changes in panels behind the frontmost panel are not recorded. Back restores both the screen and the frontmost panel; restoration creates no new history and preserves other panels' open states and drafts. The Back function returned by the hook consumes the same history from on-screen Back buttons and returns `true` when handled. With no history, existing panel dismissal or navigation to the screen's parent level applies. Transitions to remaining panels or the editor after closing a panel with browser Back are not added as new visits. Modals and menus consume Back first. History and restoration callbacks are kept only in memory and reset on account or root project changes or when switching to desktop. Close buttons retain their existing behavior. Esc does not consume navigation history or close panels.
- Git registers the list, commit hash, diff source, and file path as screen identifiers. Pressing Back twice in `Git 목록 → diff → 에디터` returns through `diff → Git 목록` for the same file, while historical commit diffs return to the list through commit details. Diff content is not duplicated in history; it is fetched again using the restored source and file. Other panels' internal screens can be extended through the same registration contract. `use-panel-dismissals.test.ts` verifies screen restoration, hidden screen changes, identical screens, and history resets; `server/git-panel-ui.test.ts` verifies actual Git, diff, editor, popup, and on-screen Back flows.
- Back handling adds a single dummy History entry (guard). There is only one guard even with overlapping overlays, and after handling Back, it is re-added if any panel, internal screen, or popup stack remains, regardless of whether unregistration occurred. This includes cases where the frontmost panel changes while the shared registration remains active. Even on the first panel → editor transition, the visit to be recorded by the current render is reflected immediately to retain the guard. If registration is removed and `history.back()` is called before the effect saves navigation history, asynchronous Back navigation can consume the new registration and return to the previous panel. Navigation to the browser's previous page occurs only when all internal stacks are empty. When closed through the UI, the guard is removed with `history.back()` to keep the stack aligned.
- `server/overlay-history-ui.test.ts` checks in actual Chromium History that the first transition to the editor retains the selected screen without calling `history.back()`. It also verifies successive Back handling in the order popup → Git diff from before the editor → Git list → remaining panel → editor, and navigation to the page visited before entering the app only after all internal history is exhausted.
- Do not attach a separate keydown listener to each overlay — even calling `stopPropagation` in the capture phase leaves other listeners attached to the same node (window) running, causing overlapping popups to all close with one Esc press.
- `escapePhase: 'bubble'` is for overlays that **only wrap content**, such as file explorer and terminal panels. If an inner component (editor slash menu or file rename) consumes Esc first and calls `stopPropagation`, the panel does not close. The default `'capture'` is for dialogs — it intercepts the event before the editor or terminal underneath can handle it.
- All workspace panels (file explorer, chat, terminal, agent, browser, Git, Android, Features, debugger, notes, and tasks) remain open even after repeated Esc presses. The same applies to standalone browser and agent screens. Esc panel dismissal was removed to prevent accidentally closing work screens; do not reintroduce it without a user request. `useWorkspacePanelDismissals` always returns false from `closeOnEscape` and uses the optional `onEscape` only to cancel file search. The file explorer does not close even when the search is empty. Popup, modal, and dropdown dismissal, drag cancellation, exiting maximized view, and terminal input retain their existing Esc behavior. `src/hooks/use-panel-dismissals.test.ts` checks repeated Esc presses across all panels, search cancellation, and preservation of Back behavior.
- `closeOnEscape` determines whether to consume Esc. Workspace panels always return false. Popups containing a terminal pass `outsideTerminal` (`src/utils/terminalFocus.ts`) to yield Esc to vim and similar programs. This does not affect Back.
- Use `closeOnBack` when content handles mobile Back first. Returning `false` keeps the window open and reinstates the History guard to handle repeated input. No separate popstate listener or second panel registration is added, preserving the priority of modals and menus opened above it. This callback does not apply to Esc, outside clicks, or the close button.
- Providing `outside: () => 요소` also **closes the overlay when the user clicks outside that element** (only the topmost one, following the same rules as Esc). Touchscreens have no Esc key, so **a popup without a close button has no way out unless this is provided**. The decision uses the `contains()` location rather than propagation—even if `stopPropagation` runs inside, capture has already occurred. For overlays that must not close on outside clicks, such as the file explorer, simply omit it.

The editor's mention and slash menus and link/table tooltips are **intentionally not registered.** They appear and disappear frequently during typing and selection; pushing and popping History each time would hit the browser's pushState limit. Their Esc handling is performed directly by ProseMirror's `handleKeyDown` in `Editor.tsx`.

## Focus-based tab shortcuts

By default, `Alt+T` toggles the task panel. Open the terminal with `Ctrl+백틱`. The task panel uses existing Markdown, and [DB Gantt](../../../docs/guides/database.md#switching-views) uses rows and date columns from the same DB; they do not automatically sync with each other.

`Ctrl/Cmd+N`, `Ctrl/Cmd+T`, and the existing `Alt+N` (including remapped `newTab`) open a new tab in the focused surface. For agents, this opens that group's `+` selection screen; for regular shells, it creates a new terminal in that group; for the editor and file explorer, it opens the new filename input. In the task panel, it moves to the new-item input in the list or calendar, or adds a new item in Gantt ([task input contract](task-list.md#input-and-panel)). `Ctrl/Cmd+Shift+N` connects to the existing new-folder flow (the document tree follows its existing new-document rules). The file explorer uses the selected location, and the editor uses the active document's folder. Both check file read/write permissions and consume the per-project one-time request in `useSidebarCreate` so it is not replayed on remount or project switch.

`captureAppTabShortcuts` records the last selected area through pointerdown and focusin, retaining that area's new-tab behavior even when clicking an empty part of a panel moves actual focus to body. It does not send creation requests to areas that are hidden, inert, or removed from the DOM. At the capture phase, it first dispatches the action registered with `openFocusedTab`, allowing new agent, terminal, and browser tabs to open independently of file write permissions. Even if a registered surface rejects creation, it does not fall through to creating a new file; file and folder creation runs only in editor and file explorer areas. In other panels and areas outside the app, it consumes creation keys without creating files. Modals, IME composition, and key repeats consume keys without running creation or close actions. Nested shortcut surfaces use the innermost surface that registered the action; surfaces without an action use the ancestor registration. `src/utils/app-tab-shortcuts.test.ts` checks file/folder creation in the editor and file explorer; new agent, terminal, and browser tabs and creation rejection; empty-area selection, hiding, modals, IME, repeated input, and blocked key propagation. [Agent set and tab creation](../features/terminals-agents-automation/agent-sets-and-tab-creation.md) owns the detailed creation flow.

`Ctrl/Cmd+Tab`, `Ctrl/Cmd+PageDown`, and `Alt+E` move to the next tab; `Ctrl/Cmd+Shift+Tab`, `Ctrl/Cmd+PageUp`, and `Alt+Q` move to the previous tab, wrapping at both ends. They use the same focus, split-panel, modal-exclusion, and input-blocking contracts as numbered selection. The existing `Ctrl+Alt+←/→` and custom previous/next tab combinations remain available. CLI switching in agent input, which conflicted with `Ctrl+Tab`, moves to `Ctrl+Alt+M`. When the login video viewer has focus, global tab shortcuts do not run and the input is forwarded to remote Chrome. The tab bar identifies the current tab using `aria-selected`. Since the file explorer has no tabs, tab navigation, numbered selection, and body swipes do not change its search mode. The search-field toggle and `Ctrl+P` and `Ctrl+Shift+F` switch between filename and content search.

`Ctrl/Cmd+1`…`Ctrl/Cmd+9` select the tab at the corresponding display position in the currently focused panel (9 selects the ninth tab). At the window capture phase, `useFocusedWorkspacePanel` identifies the combination with `numberedTabIndex` and invokes the existing tab-click behavior through `activateNumberedPanelTab`. `data-dock-body` connects to the `data-dock-panel` tab bar in the same group, so it does not select tabs in another split panel. If the tab bar has `role="tablist"`, that list is used; otherwise, the `role="tab"` order within `data-dock-tab-bar` is used. The file explorer has no tabs and does not receive `data-numbered-tab`.

- A nonexistent number leaves the current tab unchanged, and a panel without tabs does not forward selection to another panel. Number shortcuts are not forwarded to the editor or PTY. 0, combinations that add Shift or Alt to Ctrl/Cmd, and IME input are not treated as numbered selection.
- Physical keys `Digit1`…`Digit9` and the numeric keypad are supported.
- The last panel selected by keyboard or pointer is remembered, but background tabs are not switched for closed, hidden, or inert panels or during modal input. Ctrl/Cmd number and navigation keys are still consumed in these cases to prevent them from reaching browser tabs. Tasks use the list, calendar, and Gantt view list, excluding the title.
- Regression checks in `src/hooks/use-focused-workspace-panel.test.ts` and `server/desktop-keyboard-ui.test.ts` cover selection in split editors, portal terminals, the file explorer, and tasks; nonexistent numbers; Option and the numeric keypad; modifier and IME exclusions; modals and inert panels; input blocking; and wrapping at both ends. The actual agent panel is verified with `agent-new-tab-ui.test.ts`, login input with `src/components/login-desktop-viewer.browser.test.ts`, and file/folder creation in the actual App with `workspace-switch-ui.test.ts`.


The owner's `Alt+1`…`Alt+9` input is identified by `projectTabIndex`, and the capture listener in `ProjectSwitcher` selects the project in the saved `paths` order. It follows the dropdown list order and uses the existing `onActivate` project-switching path regardless of panel focus. The current project, nonexistent numbers, modals, and key repeats consume the key without switching. For anyone other than the owner, this listener does not consume keys. Shift, combinations with Ctrl/Cmd, IME, and 0 are not treated as numbered combinations. Physical `code` and the numeric keypad are recognized instead of the special `key` produced by macOS Option. Iframes also forward Alt-number input to the app, while the active remote screen receives it through the shared highest-priority capture handler. Follow [Open, select, and switch projects](../features/projects-files-search/opening-projects-tabs-and-groups.md) for the detailed contract.

`Ctrl/Cmd+W`, `Ctrl/Cmd+Shift+W`, and `Alt+W` (including remapped close combinations) close **one tab in the focused surface** through `closeFocusedTab` and `dispatchFocusedShortcut`. Windows that own their tabs, such as terminals, agents, and browsers, register a root ref and `useFocusedShortcutScope(ref, { closeTab, newTab })`.

- When the key reaches the app, `preventDefault()` and `stopImmediatePropagation()` block the browser's default behavior and forwarding to the editor or PTY, regardless of whether a tab can be closed. Repeated keydown events are consumed without closing additional tabs. On the start screen with no tabs, the action does not spill over to tabs in another surface.
- When a confirmation dialog or modal has focus, tab-close keys are consumed without running background tab close actions or the editor fallback. Confirmation and cancellation for an agent tab with work in progress follow the [agent conversation contract](../features/terminals-agents-automation/agent-conversations-queue-and-restoration.md#confirmation-when-closing-a-working-tab).
- A document tab is closed only when no window is registered and the focused editor pane has an active document. Closing a terminal tab terminates its shell session through the same path as the existing `×` button.

`Ctrl/Cmd+Shift+T` blocks forwarding to the browser, editor, and PTY at the capture phase and dispatches to the focused surface's `reopenTab` action. Agents and terminals register this action on the tab bar, body, and empty panel. If there is no closed-tab history, it does nothing and does not fall back to file creation or another panel type. It does not restore tabs during modals, hidden/inert states, repeats, or IME input. History scope and conversation/shell lifetimes follow [Agent tab creation](../features/terminals-agents-automation/agent-sets-and-tab-creation.md) and [tmux terminal](../features/terminals-agents-automation/tmux-shell-terminals.md).

Standard combinations such as `Ctrl/Cmd+W/N/T/숫자` are fixed aliases and remain available even when existing custom shortcuts are changed. In a regular Chrome tab, keydown events for reserved keys may not reach the webpage. Entering JavaScript fullscreen through **mew's fullscreen button or Alt+Enter** causes `captureAppKeyboardLock` to lock the `APP_KEYBOARD_KEYS` needed for creation, closing, selection, navigation, and existing app commands. F11 fullscreen alone does not satisfy this condition. A secure context (HTTPS/localhost) and Keyboard Lock support are required; when unsupported or denied, only delivered events are consumed. Existing Alt combinations are available where locking is unavailable. A Chrome app window (**Install page as app** in the menu) is an optional way to deliver Ctrl+W to the app in windowed mode, without adding a client keyboard helper app. Follow [Keyboard Lock](https://developer.chrome.com/docs/capabilities/web-apis/keyboard-lock) and [Install a Chrome app](https://support.google.com/chrome/answer/9658361?hl=ko).

`APP_KEYBOARD_KEYS` also includes `Escape`. Where Keyboard Lock is supported and permission is granted, a brief Esc press does not exit app fullscreen, while existing Esc handling for closing popups, canceling searches, terminal input, and similar actions remains available. Fullscreen can be exited with the fullscreen button or `Alt+Enter`, and the browser guarantees Chrome's escape behavior of holding Esc for approximately 2 seconds. Where unsupported or permission is denied, the browser's Esc fullscreen exit cannot be blocked. `server/desktop-keyboard-ui.test.ts` checks that the app lock includes Escape and is restored after the remote lock is released.

`@mew/shortcuts` installs a single highest-priority capture listener during module initialization. The active remote screen's `registerKeyboardCapture` handles both keydown and keyup before regular tab shortcuts, numbered selection, and overlays. `keyboard-lock.ts` manages app reserved-key locks and remote all-key locks by priority. If fullscreen remains active after remote focus is lost or the remote screen is closed, it restores the app reserved-key lock; it releases the lock on fullscreen exit, window blur, screen hiding, or unmount. It checks lifetimes so an asynchronous permission result cannot release a new owner's lock. Remote input, OS exceptions, and the clipboard follow the [remote keyboard contract](remote-desktop.md#keyboard-lock-and-clipboard).

The default combination for creating a comment is `Ctrl/Cmd+Shift+C`; explicitly saved custom combinations are retained. When the user is logged in, has collaboration permission, and has focus or a DOM selection in an actual file text editor, `captureCommentShortcut` uses `preventDefault()` and `stopImmediatePropagation()` at the capture phase to block browser developer tools and subsequent forwarding to the editor. Without a selection, it only consumes the key; repeats and IME input also do not create new comments. It neither dispatches comment creation nor consumes keys in agents, terminals, login video, modals, or hidden/inert areas, preserving remote capture priority. [Comments](../features/collaboration-comments-chat/comments-replies-and-member-mentions.md) owns the details of authoring, lists, and permissions.

## Fast root project switching

Reduce waiting within the contracts for per-account active roots in [ADR 0200](../history/decisions/0200-mew-account-active-workspace.md), SPA switching in [ADR 0086](../history/decisions/0086-mew-root-project-spa-handoff-and-cache.md), and preserving agent work in [ADR 0092](../history/decisions/0092-mew-agent-survives-root-project-switch.md). Do not switch to inactive roots in advance to read actual folders or files.

- While `switchingRootProject` is true, `ProjectLoadingOverlay` displays a central indicator. Root-tab switching and opening subprojects use the same state, which is cleared in the existing `finally`; if session-restoration requests follow, full-screen loading remains active. It does not darken the screen or intercept input, and clicks, touch, and keyboard operations remain available. The indicator disappears automatically when the request completes or fails. It announces a translated loading status to screen readers and does not rotate with reduced motion enabled. The tab-bar text was removed to make the switching status clearer and must not be reintroduced unless the user requests it.
- `App.openRootProject` starts the account UI query with an explicit absolute root and, when agents/terminals are in use, the agent-tab query for that root in parallel with the switch POST. On initial restoration or cache expiration, the UI query reuses an identical request already in flight. `AgentPanel.preparedTabs` accepts only the promise started by that switch to avoid duplicating the initial query; session-occupancy refetches continue to read the server as before. Existing queries are used for switches from another connection on the same account, subproject entry, and the initial screen. Switching by another account does not change the current screen.
- Hovering or focusing an inactive row in the project switcher preloads UI metadata per account and absolute root. At most 2 speculative queries may be in flight; this limit does not apply to actual selection queries. Selection shares the same request, and files, trees, and agent-session occupancy are not prefetched. When permissions change, the cache and restoration generation are refreshed to discard late responses from the previous permissions and refetch with the new permissions.
- Selecting an already registered project preserves the path-list array, skipping unnecessary account-list saves. Project icon bundles are reused within the logged-in App through an LRU cache capped at 4 entries, 1MiB, and 60 seconds, and cleared on permission changes or icon saves. Account/root boundaries and the existing shared icon canonical source are maintained.
- `WorkspaceSnapshotCache` exists only within a logged-in `EditorApp` instance. Screen state is capped at 12 roots and 1MiB; first-level trees are capped at 24 root/scope entries and 1MiB. Each snapshot is usable for 60 seconds after recording, and entries are evicted in LRU order when entry or byte limits are exceeded. Large entries are not cached. No new localStorage ledger or server cache is created. Permission changes clear both caches, and account changes replace the App instance.
- Once the server confirms the switch, the root's cached UI and first-level tree are applied immediately. The first-level tree is always reread in the background, and results read in response to change signals also update the cache. Presence notifications received during a direct switch are coalesced, and the current root is checked once after the POST finishes; older query responses are discarded using sequence numbers. If the POST response and notification query return the same `path`, `projectPath`, and `docsPath`, reinitialization is skipped. If the Documents path changes, the tree cache is cleared and a new query starts. Before the initial root is known, duplicate tree and project-list queries for the authenticated user are not created.
- If the user leaves a root before the 500ms UI-save delay expires, the last snapshot is saved to that **previous root**. Account UI PUTs are serialized, and pending writes are not sent after the account App is gone. If a cache entry overlaps with an in-flight GET, the newer local snapshot is retained.
- `useTabs` creates all saved editor panes and tab shells in a single state update. It does not skip restoration by looking up same-named tabs from the previous root. When switching roots, it also removes tab state from other API scopes, such as the previous Documents scope, so it is not saved under the new root. It preserves the per-account, per-root body memory LRU and reuses the asynchronous IndexedDB cache. Cached bodies appear read-only first, without a loading overlay, and only the active tab in each pane has its permissions and version checked. If they match, body retransmission is skipped; editing, collaboration seeding, and comment operations are blocked until verification completes. Before restoration, bodies from the old root are not displayed under new tabs. The detailed contract follows [File Body Retrieval and Cache Restoration](file-loading.md).
- Tree, body, and document rule responses are applied only when their switch generation matches. Even during rapid A→B→A switching, late responses from an earlier generation do not overwrite the current body or cache. A failed switch preserves the current root and screen.

Validation: `workspace-snapshot-cache.test.ts` checks reuse, in-flight request coalescing, LRU/byte/expiration limits, retries after failure, and permission invalidation. `server/workspace-switch-ui.test.ts` loads the actual App, useTabs, FileTree, project selector, and docking into isolated Chromium and controls network responses to check that metadata requests start before POST completion, warm returns issue 0 additional UI GET requests, caches appear while tree/body refreshes are pending, duplicate notifications are handled, closing the last file tab is saved, Documents scopes are isolated, stale body responses are discarded, and switch failures are handled. Because this test substitutes other panels and editor renderers, its results must not be interpreted as measurements of total latency involving the actual server, large editors, and agent reconnection. `server/agent-command-ui.test.ts` separately checks normal initial queries and reuse of prepared queries in the actual AgentPanel.

On 2026-10-19, 6 cache tests and `server/workspace-switch-ui.test.ts` confirmed that no switch POST, file, tree, or agent occupancy requests occur before selection; prepared requests are reused; warm returns issue 0 additional UI/icon queries; late metadata is discarded after permission changes; and switching and panel restoration work. Total switching latency in production was not measured.


## Switching worktrees within the same project

Following [Decision 0068](../decisions/0068-project-worktree-context.md), the on-screen project identifier is separated from the file operation root. In the `GET/POST /api/workspace` response, `path` is the actual file operation root and `projectPath` is the logical project root. If an existing response lacks `projectPath`, `path` is used. The account ledger stores these values as `activeWorkspace` and `activeProjectPath`, respectively.

- For normal project selection, `POST /api/workspace { path }` changes both roots to the target path and restores that project's saved screen. When moving to an existing worktree through Git branch selection, the request uses `{ path, worktree: true, workspace: <출발 실제 루트> }` and preserves `projectPath`. This operation does not add the worktree to the separate project list.
- The server checks owner/manager permissions, a matching source root, the Git top-level paths of the current and target folders, a shared Git common directory, and the target's registration in `git worktree list`. If the account's actual or logical root changes during asynchronous Git checks, it rejects the request with 409. If target validation fails, it preserves the current project and does not rename or move folders or force a Git switch.
- The project name, account UI ledger, docking and popup storage keys, mobile panel state, editor pane and tab structure, and `AgentPanel` identifier use `projectPath`. Within the same logical project, panels are not remounted and another project's layout is not restored. Files, Git, navigation, search, and body caches use `path` to query the target worktree again.
- When the working root changes within the same logical project, `useTabs` carries over open relative paths and the pane and tab structure, and removes previous bodies. It reloads target content and permissions starting with active tabs; inactive tabs follow the existing lazy-loading rules. Files missing from the target appear as read-only errors so that previous bodies are not saved as new files. External absolute-path files retain their existing external file scope.
- Before creating or switching branches, complete the autosave queue and in-flight saves, and save modified tabs, including external files opened by absolute path. Block new edits and autosaves during preparation, abort the switch if saving fails, and do not immediately retry failed saves automatically. If the optional `workspace` supplied with a file save request differs from the request's actual root, the server rejects it with 409. Late save and body responses from the previous root are not applied to a screen whose switch generation has changed.
- Existing agent and terminal tabs and running sessions retain their original cwd. The default cwd for new tabs is updated to the selected actual working root. Switch notifications for the same account and path isolation between accounts follow the existing contracts.

This switch uses an existing worktree without copying files, checking out, or swapping physical paths. The target tree, bodies, and permissions must be queried again, and total switching latency on the actual server requires separate measurement.

## Search within the file explorer

The top of the explorer has one search field and icons for case sensitivity, regular expressions, and content search. The shared `PanelCloseButton` X is always displayed outside the search field on the right, on the same row, to close the file explorer. Below it, the existing two-button Documents/Files toggle directly selects the scope, with the Create button on the same row. The two buttons retain rounded surfaces, selected backgrounds, `aria-pressed`, and switching by click, touch, left/right arrow keys, and Home/End. They are not replaced with a dropdown, and the owner's right-click settings on the Documents toggle are preserved. Instead of a separate search tab or results list, the corresponding view in the existing `FileTree` is retained, displaying only matches and expanded ancestors. Expansion and scrolling during search are separate from browsing state. Content-match tooltips use a body portal and shared fixed coordinates, showing the matching line, up to 3 lines each above and below it, and approximately 10 words on either side. [Filename and Content Search and Replacement](../features/projects-files-search/filename-content-search-and-replacement.md) owns detailed pattern, search scope, replacement, and compatibility contracts and validation.
