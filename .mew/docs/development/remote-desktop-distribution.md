## Distribution Format

The default video engine is the Rust cdylib in `native/remote-desktop/rust/`. `Cargo.lock` pins `datachannel-sys 0.23.0+0.23.2` and build dependencies including libdatachannel 0.23.2 and OpenSSL. This is distinct from libdatachannel 0.24.5 in the existing `node-datachannel`. The transport implementation's C API follows [upstream](https://github.com/paullouisageneau/libdatachannel/blob/v0.23.2/DOC.md). The installer uses `cargo vendor --locked --versioned-dirs` to preserve dependency sources and original licenses in `rust/vendor/`, then performs an offline release build from those sources. This folder, including MPL corresponding source and transitive dependency notices, must be preserved alongside the binaries. New Rust files follow the Mew license and do not change third-party licenses.

On Windows, a narrowly scoped adjustment changes OpenSSL archive paths in vendored `datachannel-sys` to MSVC `.lib` names. `rust-vendor.mjs` verifies the original file checksums and exact replacement targets, then updates both the vendored sources and file checksums. The modified corresponding source is also preserved as-is. Linux/macOS sources are not modified. Fixture verification of this adjustment does not mean a build on a real Windows machine has succeeded.

The current distribution consists of Mew source and the installer. The receiving environment downloads npm packages from the lockfile and the required OS runtimes. Windows/WSL prepares a dedicated Windows Node at the fixed location `runtime/node.exe` and does not need to download the existing Electron binary. Mac/Linux copies the currently supported Node to a dedicated path and preserves that version's Node LICENSE. The default public STUN performs address discovery only and does not relay video. Lookups can be disabled with `[]`.

`native/remote-desktop/package-lock.json` is separate from the root lockfile, so run `npm audit --package-lock-only --ignore-scripts` in that folder. On 2026-10-21, the installer's `http-cache-semantics` was updated to 4.3.0 within the allowed version range, and only `xml2js` under `dbus-next 0.10.2` was pinned to 0.6.2 to resolve the prototype pollution advisory affecting 0.4.23. The XML results of callback `Parser.parseString` and `Builder({headless:true})` were compared against the previous version for consistency. After that folder's npm dependencies are installed, `node --test native/remote-desktop/dependency-compatibility.test.mjs` uses local XML fixtures to check parsing, regeneration, rejection of malformed XML, and actual dbus-next portal method, property, and signal configuration. This check does not run OS D-Bus, native builds, installation, or remote connections on real machines.

Windows/WSL uses `node-datachannel 0.33.4` and its platform-specific native npm packages (libdatachannel 0.24.5), Koffi 3.2.1, and its own `gpu-windows.cpp`. Installation compiles the DLL using Visual Studio C++ Build Tools and the Windows SDK and links it to D3D11, DXGI, Media Foundation, and Windows OS libraries. It uses vendor hardware H.264 MFTs and does not distribute its own H.264 encoder, FFmpeg commands, or WASM codecs. Generated DLLs, the Windows SDK, and MSVC tools are not committed to the repository. The readiness marker is written only after actually importing the required native npm binding and successfully compiling.

`node-datachannel` and `libdatachannel` use [MPL-2.0](https://github.com/murat-dogan/node-datachannel/blob/v0.33.4/LICENSE). Preserve the package license and the requirements to provide corresponding source for covered files. New distributions of separate Mew files follow the [Mew Source Available License 1.0](../../../LICENSE), which permits internal business use and restricts Mew sales and paid hosting under [Decision 0053](../decisions/0053-source-available-license.md). Existing MIT grants and third-party MPL terms remain in effect. Transport and encryption components within platform binaries are also subject to their respective upstream terms, so do not label the entire binary as MIT. Use of OS H.264 encoders and codec patent requirements in specific markets are separate matters; do not claim that the source license alone satisfies patent permission requirements.

Mac uses VideoToolbox, and Linux uses system GStreamer VA-API/NVENC hardware H.264. The historical Windows choice of Electron/VP8 server transport is preserved in the [previous contract](../history/remote-desktop-electron-transport.md).

Mac/Linux x64/arm64 support and installation requirements follow the [POSIX contract](remote-desktop-posix.md).

The custom Windows virtual display is a separate source distribution of a UMDF 2/IddCx DLL, INF, and catalog. Its DDI and swapchain structure references Microsoft's MIT IndirectDisplay sample, and the package includes the original notice in `virtual-display-origin-license`. It does not redistribute StarDesk or third-party IDD binaries. Production installation requires a trusted release catalog signature, and no signed mew distribution package exists yet. WDK, signing, user SID device ACLs, and installation boundaries follow a [separate contract](remote-desktop-virtual-display.md). Generated binaries, signing keys, and SDK/WDK files are not committed to the repository.

macOS compiles and locally signs its own `gpu-macos.m` during installation and dynamically links host OS frameworks including Metal, ScreenCaptureKit, VideoToolbox, and UserNotifications. Linux dynamically links its own `gpu-linux.cpp` to system GStreamer and X11 libraries. Generated binaries and the Apple SDK are not included in the repository or product. The test-only x264 path is not included in production builds.

Preserve notices for Node, node-datachannel/libdatachannel, Koffi, dbus-next, and transitive dependencies in the lockfile. usocket for Wayland Unix FD passing and the node-gyp build tool also retain their respective upstream notices. If GStreamer and vendor plugins are distributed as a new bundle, their exact licenses, including LGPL where applicable, corresponding source, and replacement rights must be checked against the distribution method. The current installer uses system libraries.

The detailed license review of previous official Electron distributions is preserved in the [historical record](../history/remote-desktop-electron-distribution.md). Do not interpret that review as a completed audit of the entire new native distribution.
