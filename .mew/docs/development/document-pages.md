## Storage Structure

A document without children is stored as `name.md`. Creating or moving in the first child document creates `name/` and moves the existing body to `name/_name.md`. Since `name/child.md` can also have children, the same rules apply recursively. When the last child other than the representative file is deleted or moved elsewhere, it reverts to `name.md`. Attachments and hidden files also count as actual children, so folders with remaining content are not deleted. The Docs root is never converted to a single file.

Renaming a parent document renames both its folder and representative file. `dev/_dev.md` becomes `development/_development.md`. Child documents and body content are preserved. If a single document and a folder have the same name, the operation is rejected as a conflict without overwriting.

Renaming a document in Documents also updates its frontmatter `title` to the new name. If the task's `description` is the automatic default `태스크: 이전 제목`, it is updated too; manually written descriptions, body content, and other properties are preserved. No new properties are added to existing Markdown without frontmatter. Title changes are included in the same recovery scope as path and link changes, and malformed frontmatter is rejected before renaming. Task queries do not revert filenames to previous titles, and existing item IDs are retained.

Existing `MOC.md` and `_MOC.md` files are also read as their folder's representative. Simply opening them does not move files. Creating, renaming, or moving a child document in that folder renames the representative to `_폴더이름.md`. No bulk migration of actual project documents or changes to `archives/` are performed. The existing MOC at the Docs root remains **Document Home**. Clicking the name of an existing folder without a representative expands its children, and creating its first child document creates a representative.

User-visible document names prioritize the representative document's title over the file path. Document file and folder names may use natural language, spaces, uppercase letters, and Korean characters, while reserved entry filenames are retained. The representative document's frontmatter `title` and first heading use natural language, such as `문서 홈` and `개발 계약 홈`. Existing MOCs serve as the opening view of their parent document rather than as files that enumerate lists.

## Navigation and Editing

- Documents without children show a 4px bullet in the chevron position (the existing 20px column). This applies to single documents and folders that, after loading, have no children other than their representative or MOC. Unloaded folders retain the existing chevron for lazy loading. The bullet is an `aria-hidden` decoration, and existing document opening and child addition behavior is retained.
- `FileTree.documentPages` displays the Docs list as parent and child documents. The regular file view retains existing navigation.
- Child list requests from names and arrows share a per-folder cache and Promise and retain existing rows during revalidation. For runs of 200 or more files and closed folders, only rows near the viewport are rendered, while expanded parent document and representative body detection is retained. Detailed criteria follow [File and Folder Navigation](../features/projects-files-search/file-folder-exploration-and-operations.md#implementation-details).
- Clicking a parent document's name opens its representative body. The arrow only expands or collapses its child list. The representative file is hidden from that list. Document names and editor tab names omit `.md` and the representative file's underscore.
- Documents editor tabs prioritize the current body's frontmatter `title` and use the path's display name if no title exists. Title input changes are reflected in the tab immediately. Confirmed task path changes and open body updates follow the [Task Storage Contract](task-list.md#client-lifecycle-and-errors).
- The Documents tree and editor tabs convert storage path slugs to natural-language display names. For example, `document-pages.md` is displayed as `Document Pages`, and `api-reference.md` as `API Reference`. Capitalization and spaces in natural-language names are displayed as written. Actual storage paths and link targets are unchanged.
- A regular click replaces the current tab in the focused editor pane. Ctrl/Cmd+click keeps a new tab open, and an already open document activates its existing tab. Unsaved content in the current body is preserved.
- Each document's **+** prompts for a child document name. The top **New Document** action also uses the selected document as the parent, or creates the document at the Docs root if nothing is selected. The `.md` extension may be omitted from the name. Docs does not have a separate New Folder button.
- For editable Markdown within a project, selecting **Child Page** from Hotview's `/page` first opens a name input. Entering a name and clicking Create creates the child document, inserts its link at the command position, and keeps the parent document open. Open the new document by clicking it in the list or clicking the link. Empty names cannot be submitted, and canceling creates nothing. Navigating to another document while entering a name also creates nothing. If a file or parent document with the same name exists, the first available number starting at 2 is appended to the entered name, and the link uses the finalized name. The same structural change engine as Documents' **+** handles `abc.md` → `abc/_abc.md` conversion, link adjustment, draft saving, and open tab updates. In an existing representative document, it creates a sibling in the same folder, and new child pages can themselves contain nested pages. The `/page` command string is removed from the body before creation, and no link is inserted on cancellation or failure. The command is unavailable to guests, read-only documents, archives, and files outside the project.
- Child documents can be moved by dropping them onto a page or by cut/copy and paste. If the destination is a single document, it is converted to a parent document. When duplicating a folder, the copy's representative name is also matched to the new folder name.
- **View Graph** appears once at the Docs root above Document Home. Graph connections use actual body hyperlinks; folder containment is not substituted for links.

Titles being edited in the editor or tasks appear in the explorer immediately as they are entered. Actual file paths are adjusted after save confirmation; until then, documents open using their original paths. Renaming the same document retains its document identifier in the open editor, preserving title input focus and cursor position, body selection, and scroll position. Task save ordering and validation follow the [Task Contract](task-list.md#client-lifecycle-and-errors).

## Change Handling

`shared/document-pages.ts` shares representative detection, path mapping, and link adjustment. It adjusts relative Markdown, reference-style, and wiki links and image paths to new locations while preserving external URLs, anchors, body labels, code, and frontmatter. Only editable current documents are updated; read-only documents and archives bodies are not modified. Links outside this scope must be checked separately during external document migration.

`server/document-pages.ts` first checks conflicts, path escapes, and permissions. Changes run as a single synchronous batch; failures roll back paths, bodies, and creations. Deletion targets are held in a temporary location on the same filesystem and removed after success. This is not a persistent transaction that provides automatic recovery from process interruption.

`POST /api/docs/pages/{create,rename,delete,move,copy}` checks login, `filesWrite`, and source/destination file permissions. Recursive operations require edit permission for every child. Input is `{path,name?,destination?,project?,unique?}`, and the response is `{path,moves,changed,removed?}`. `project` defaults to `docs`, and Markdown in regular projects uses the same engine. `unique: true` avoids name conflicts during creation by adding numbers; the default `false` retains conflict rejection for the existing **+** action. Structural changes do not create automatic Git commits. Caches, search, and watch lists are updated starting from the surviving parents of changed paths.

`useTabs.prepareDocumentPageMutation` waits for earlier structural changes and in-progress saves and saves drafts for the target project. The default target is Docs. It defers autosaves, manual saves, and closing modified tabs in the target project until the structural change and subsequent body fetches finish. After a successful response, `applyDocumentPageMutation` adjusts the project's paths, body links, and save baselines across all editor panes and waits for bodies to be fetched from their new paths. Body edits made during the change are retained and autosaved to the new paths; older fetches arriving later do not overwrite the latest saved bodies or cache. Other project tabs and split layouts are preserved. `createChildPage` combines this preparation and application flow with the creation API without opening a new tab or changing the active document. If the working folder is switched before the response arrives, the old response is not applied to tabs in the new folder. No separate collaboration protocol was added to broadcast path migrations to other connected users' existing tabs.

Input continues to be reflected in the editing buffer during structural changes. `/page` tracks the command position through transactions and inserts the link in the creation success callback before changing the path or collaboration room. Subsequent path adjustment rewrites both the new and existing links. Reapplying the body preserves the local editor's selection and scroll position. The host communicates the new collaboration room's readiness through `collaborationPending`; cursor, focus, and scroll restoration are deferred in the temporary editor while it is preparing.

Links with natural-language paths URL-encode spaces, Korean characters, parentheses, `#`, and `?`. Shared documentation checks read encoded links and `<공백 있는 경로>` and follow `_폴더이름.md` representative documents in the map chain in addition to `MOC.md` and `_MOC.md`.

## Database Row Subpages

Follows the [Row Page Decision](../decisions/0012-database-row-pages.md) and [Table Database Guide](../../../docs/guides/database.md). Converting the primary column to a page creates `<대표열 값>.md` directly beneath the document containing the DB. The `송상훈` row of a DB in `Books/_Books.md` is stored as `Books/송상훈.md`. If the source is the single document `Books.md`, it is converted to `Books/_Books.md` just like a regular child document. No separate `데이터베이스` document or DB UUID folder is created. A DB without an owning document creates pages at the project root.

Filenames retain Korean characters and spaces, while path separators and OS-reserved characters are replaced with spaces. Prefixes avoid hidden, representative, and reserved names, and long names are shortened. If a file or folder with the same name exists, numbers starting at 2 are appended without overwriting. Row UUIDs and DB UUIDs remain in frontmatter and DB linkage data. Existing paths remain unchanged when titles are edited after creation, while frontmatter `title` and primary DB column values stay synchronized. Paths of manually moved pages are also preserved.

Existing `데이터베이스/<DB UUID>/<행 UUID>.md` files are moved to name-based paths beneath the source document on the next regular DB query or edit. Body content, user properties, and row links are preserved, and document links and DB paths are adjusted together. If the owner path is missing or no longer exists, it is recovered only when exactly one source document contains the same DB. Only empty autogenerated DB representative files and empty folders are cleaned up; those with additional body content or other files are retained. Path migration is deferred during row page autosaves to preserve the save request's original path.

DB REST responses also return `documentPageMutations` when paths change. The host DB API saves project drafts and defers autosaving before the request, applies changes from successful responses to open tabs through `applyDocumentPageMutation`, and then resumes autosaving. If the working folder changes while waiting, the request is not executed, and responses already in progress are not applied to tabs in the new folder. Moving a DB's owning document through regular document operations after document creation also updates `owner_path`.

Frontmatter `title` is shared with the primary column, and other columns use their display names as field names. Numbers, booleans, and multiple selections are stored as YAML numbers, booleans, and string arrays. Selection types and options are passed to the Hotview property editor through existing `mew:field` comments and are not mixed with same-named fields or options in regular documents. `_mew_database` and `_mew_row` are linkage identifiers and are hidden from the property view. `상위파일` points to the DB folder representative. `description` starts with the default title. `created` and `updated` are not forcibly created, and body edits on DB pages do not automatically update an existing `updated` either.

`server/db/rowPages.ts` compares paths, last shared values, and column names in `mew.row_pages` to apply only fields changed in frontmatter to the DB. DB changes write the corresponding fields back to the file while preserving the body and other properties. Renaming a column removes the old frontmatter key. All values to be changed are validated, and if the DB transaction fails, files written earlier are rolled back too. This recovery handles runtime exceptions; it is not a persistent file transaction that recovers from forced process termination.

`server/db/rowPageIntegration.ts` connects file autosaving and external file watching. File saves also require the DB capability and project-wide modification permission. Comparison against the save baseline `expectedContent` prevents an older draft with only body edits from overwriting the latest shared fields, and saves are rejected if the same field was changed to different values. Regular document saves and moves do not depend on Postgres availability. Document moves adjust linked paths; if the recorded file is missing, recovery searches within the project for a document matching both linkage UUIDs. Symlinks, hidden folders, archives, and access-blocked folders are excluded from this recovery search, and no candidate is automatically chosen if multiple candidates exist for the same row.

Converting a page back to text retains its linked path but stops field synchronization. Converting it back to a page reuses the same row's file and body. Deleting a row or DB does not automatically delete the generated page body. Back up Postgres and files together because Markdown alone cannot restore DB definitions, options, or all rows.

Row pages opened in the active editor pane subscribe to their DB row and schema events and reread the file. Tabs without unsaved changes immediately display the latest frontmatter; drafts being edited are preserved, and shared fields are merged on save. Column types use the existing property editors for numbers, selections, multiple selections, and so on; numbers, arrays, and empty values saved in subpage Hotview retain YAML number, array, and `null` types.

On 2026-10-04, display name conversion was added so slug filenames appear as natural language in the Documents tree and tabs. `server/document-pages.test.ts` and `server/document-pages-ui.test.ts` were run directly to verify parent and child document operations and display name regressions. TypeScript, lint, and document link checks passed. The full `npm test -- --runTestsByPath ...` run was stopped because the repository script ran all patterns together, mixing in unrelated agent UI test timeouts and environment failures.

## description-based discovery and new files

AI selects documents by path and description according to the [document rules](../README.md). Existing MOCs are retained for screen representation and link compatibility; creating a new Markdown file does not add an MOC link. Default Documents documents generate a title-based description, which authors refine to match the body’s scope. File-level commits include only the requested files and do not automatically include other modified MOCs.
