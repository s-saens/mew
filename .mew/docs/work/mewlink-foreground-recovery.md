## Purpose and behavior

The previous [quiet background recovery fix](mewlink-background-recovery.md) removed stale warnings but still waited for native RTC disconnection detection. A local native reproduction measured 11,313ms from foreground return to verified replacement in the same app frame: about 6.2 seconds before native detection, another five-second recovery grace, then a short new connection and authentication exchange.

The implementation checks the actual P2P path on foreground return, replaces an unresponsive or expired connection promptly, and accelerates pending agent, presence, and collaboration subscriptions after verified recovery. A fresh probe ID prevents queued pre-sleep traffic from masking a dead path. RTT-aware deadlines avoid applying the shortest timeout to known slow paths. Both clocks bound authorization to request transmission. The app retains its frame, drafts, and eligible input focus without replaying writes. The current contract and rationale belong to [remote access](../development/remote-access-recovery.md#reattaching-the-same-rtc-after-a-brief-signaling-interruption) and [ADR 0105](../decisions/0105-mewlink-foreground-recovery.md).

## Measurements and verification

- The final native fixture recorded 382/363/387ms, with a median of **382ms**, from foreground return to verified reconnection in the same app. It asserts a median at or below 500ms and each sample below one second. Additional cases retained a selected parent control (373ms) and intentionally unfocused app body (360ms). All five retained app/draft nodes, input values and selection where applicable, exactly one replacement authentication check, and one accepted write without replay. A read started 95ms after the return also recovered. A healthy return issued one probe and retained the same peer.
- These measurements use the actual connection client, central launcher, Workers/D1/Durable Objects, native and browser RTC, and local authentication. Only the fixture's own active native helper was paused; the process was resumed and cleaned up. The baseline and final results use a local network and do not establish external or phone-sleep latency.
- A separate read-only production-network check used a fresh anonymous browser with the built central frontend intercepted locally, the actual central service and registered host, and a synthetic drop of only that browser's old channel sends. Foreground-to-verified-bridge recovery measured **1466/1680/1278ms**, median **1466ms**. Dead-path detection took 252–253ms; replacement RTC negotiation took the remaining approximately 1.0–1.4 seconds, followed by 3–4ms of verified handoff. The last two samples also confirmed the installed app's recovery event and the same password-input node. There were no mutation frames or page errors, and the browser and temporary script were cleaned up. This network check did **not** meet the 500ms goal and did not deploy the frontend or simulate physical phone sleep. An initial missing-event observation was a benchmark predicate error, not evidence of an older host build.
- One additional production-network diagnostic measured **1363ms to the installed app's verified event**: dead-path detection/closure 254ms, fresh WSS to challenge 524ms, connect to ticket 266ms, ticket to host answer 252ms, answer to ICE 56ms, then channel/authentication/app handoff 8ms. The host's prepared-peer path was already working. Reusing the current signaling socket for a new RTC would require a new replacement protocol and nonce/generation boundaries; moving an existing signaling object would also require a separately verified authority migration. Neither was introduced as a shortcut in this fix.
- `node --test --test-reporter=dot src/utils/remote-*.test.ts server/mewlink-background-recovery-ui.test.ts` passed. Connection regressions cover fresh-ID proof, unrelated queued frames, 250–1000ms RTT adaptation, missing/late statistics, quota/backpressure, cancellation, event coalescing, and transmission-bound expiry under paused monotonic time. Existing non-replay, body interruption, suspension, bootstrap, and identity checks passed.
- Targeted actual AgentPanel and presence browser checks passed with `node --test --test-reporter=dot --test-name-pattern='verified Mewlink recovery|agent loading and clear' server/agent-connection-ui.test.ts server/active-sessions-ui.test.ts`. They verify immediate pending subscription retries, deduplicated wake events, retained drafts, no prompt or clear replay, exhausted budgets, and cleanup. The broader presence fixture has an unrelated existing 320px tooltip-boundary failure, reproduced using its HEAD source; it was not changed for this task.
- A final subscription review found that collaboration could still wait up to three seconds after transport recovery. `useCollab` now accelerates only a pending retry on the verified event. `node --test --test-reporter=dot server/collab-reconnect-ui.test.ts` passed, including immediate retry at the maximum backoff, deduplicated events, unchanged connecting/open sockets, retained Y.Doc/offline edits/undo-redo, cancellation of the superseded timer, and unmount cleanup. Its owning lifecycle contract remains in [collaboration](../development/collaboration.md#collaboration-rooms-yjs-relay).
- A further ordering check found that a pre-sleep sync deadline could retire an existing connecting socket after the verified event but before its new open response arrived. Recovery now renews only the pending sync deadline, retaining the socket. The same browser regression passed with a paused clock at 9999ms: both connecting and open-but-unsynchronized sockets survived the old deadline, while a genuine stall still expired at the new 10-second deadline. Temporarily compiling the updated fixture against the preceding `40154e2` hook reproduced the failure; the fixed hook passed. Temporary files and browsers were removed. A separate exploratory real-transport harness timed out during fixture initialization and is not counted as verification.
- Central `npm test` passed all 175 tests in 24 files. Existing central startup and recovery browser checks passed 26 tests. The new local `mewlink/test/foreground-recovery.browser.test.ts` passed all five scenarios. Mewlink type checks passed.
- Root `npm run build`, central `npm run build`, root lint, documentation checks, and both repositories' diff checks passed. Root lint retained existing warnings and the root build reported bundle-size warnings. An initial root build encountered a concurrently added undo fixture's type error; its owning work narrowed the fixture output type, and the next required build passed without edits from this task to that file.
- `wrangler deploy --dry-run` passed for the existing central configuration. This packaged the Worker and assets without applying them. The authenticated account, Worker target, and deployment permissions were checked read-only.

## Application and remaining limits

The host build and restart were applied for this task. The initial launcher restart started the server but it exited after the command session ended. Launching the existing `mew start` operation in a separate session retained the process. Post-restart `/` and `/api/auth/me` checks return HTTP 200, and the registered central presence check reports the host online. This task does not change the repository's general server-lifecycle restrictions.

The central launcher imports the root connection client and has its own build and deployment; a host restart alone cannot apply the central copy. Central source changes remain in the independent `mewlink/` repository. The frontend build and dry run are ready; central deployment awaits separate approval and has not been performed as of this record.

The central focus bridge and native regression fixture are recorded in private commit `e3bb0b0` (`fix: retain app focus through fast Mewlink recovery`). Parent and central commits are local; neither repository was pushed.

The native fixture uses real Workers/D1/Durable Objects, browser and host WebRTC, local authentication, and a test-owned paused native helper. The user’s running helper, keys, accounts, and workspaces are not used by that fixture. It measures verified same-frame recovery on a local network, not physical Android Brave sleep or external mobile-network performance. Slow paths, local request saturation, and actual offline hosts retain bounded existing fallback behavior.
