## Purpose and result

Continuous retry alone left agent recovery waiting on sockets that still reported CONNECTING or OPEN, response bodies that never finished, and later retry delays of up to 30 seconds. A command-read fixture reproduced a hung read persisting beyond 60 seconds. The change adds fresh relay liveness checks, bounds safe read completion, caps retry delays at 3 seconds, and starts connection after at most a 25ms transcript-cache gate without waiting for the queue read. Visible RTC disconnection uses the existing fresh P2P check immediately; hidden and congestion paths retain their fallback grace.

The app, conversation, composer, drafts, known command records, and provider session remain in place. These checks do not replay accepted prompts or commands. Fatal events and permanent read failures remain actionable. Current behavior belongs to the [session](../development/agent-sessions.md#messages-reconnection-and-queues), [storage](../development/conversation-storage.md#browser-and-screen), [UI](../development/ui-contracts.md#automatic-recovery-within-panels-and-menus), and [remote access](../development/remote-access.md#reattaching-the-same-rtc-after-a-brief-signaling-interruption) contracts. [ADR 0111](../decisions/0111-fast-agent-recovery.md) records the scope of the change.

## Measurements and verification

- An isolated real supervisor IPC fixture with mock stdio ACP measured seven warm reattachments at 0.77/0.48/0.74/0.41/0.99/0.51/0.67ms from attachment start to session `meta`, with a median of **0.67ms**. Every warm response was an empty incremental `append`; the provider call log across all eight attachments contained only the initial `initialize` and `session/new`. The cold new session took 264.99ms to IPC hello and 347.86ms to metadata. Temporary workspace, data, mock processes, and files were cleaned up. These are local fixture measurements excluding browser transport, real provider startup, and external networks.
- With controlled cache delays of 0/50/5,000ms, first socket creation moved from 0/50/200ms in the preceding revision to **0/25/25ms** after the change. This measures the cache gate in a browser fixture, not real storage or end-to-end session readiness.
- A browser fixture that never delivers a relay response made 21 socket attempts after 60 seconds of virtual time, rather than remaining on the original hung CONNECTING socket. This verifies bounded repeated attempts; it does not establish that a real connection recovers within 3 seconds.
- `node --test server/agent-connection-probe.test.ts server/agentWs.test.ts` passed 2 tests. ## Application boundary

No deployment, launcher execution, or application-server start, stop, or restart is part of this work. Reloading the built host UI applies the client changes; the new relay capability requires the user to apply the server code through their normal server lifecycle. Until then the client retains the legacy-compatible fallback. The shared Mewlink browser client also ships in the separate central frontend; the user must build and apply that copy separately. Host build success does not establish server-code or central application. Physical-device sleep/wake, external-network reconnection latency, and real provider cold-resume time remain unverified.
