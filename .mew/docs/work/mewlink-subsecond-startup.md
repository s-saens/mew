## Purpose and resulting behavior

The target is an actual Mew screen in under one second on a first visit without previously downloaded browser assets, with substantially faster later visits. The [remote access contract](../development/remote-access.md#signed-offer-in-the-first-websocket-upgrade) owns the connection and worker boundaries; [browser startup](../development/browser-startup.md#workspace-initialization) owns module loading and explorer rendering. The rationale is [ADR 0122](../decisions/0122-mewlink-initial-offer.md).

The implementation moves a signed initial offer into the WebSocket Upgrade, prepares public RTC state while controller code downloads, and reuses a compatible active resource worker without waiting for its network update check. It batches non-bootstrap signaling admission and removes the explorer's extra React retry while preserving its module boundary and authentication gates. Plain and Hotview download their engines independently, and closed comments and database UI remain deferred. Ordinary file reads start alongside persistent-cache lookup so an empty or queued disk cache cannot hold up server validation; the [file-loading contract](../development/file-loading.md) owns preview and conflict rules.

Replacement RTC uses a separately advertised, short-lived, browser-key-signed offer with durable one-use consumption and ordinary bootstrap quotas. The first workspace GET can include a bounded account UI snapshot, avoiding a sequential layout read. The active editor prepares its selected language and eligible collaboration session alongside pane loading, while actual editing still requires current file validation and collaboration synchronization. Native mention inputs and closed terminal surfaces no longer download their rich composer or xterm renderer through background agent restoration. The [startup contract](../development/browser-startup.md#workspace-initialization), [composer contract](../features/terminals-agents-automation/agent-input-mentions-skills-and-attachments.md#composer-input), and [terminal contract](../features/terminals-agents-automation/tmux-shell-terminals.md#implementation-details) own these boundaries.

The selected file icon now loads a bounded artwork group, preserving the original SVG and theme mapping instead of fetching the full pack. Foreground public-code preparation begins from accepted initial metadata before pane registration and background agent module fanout. Both use the existing bounded transport rather than increasing stream limits. Closed background agent code uses a bounded 250ms preparation delay; visible or explicitly requested panels and unknown UI state promote the same import immediately. Background agent restoration remains independent of editor download completion.

An index inventory that finds the current host cache empty also avoids repeated CacheStorage lookups before first downloads, while live host responses and background SHA verification remain required. A subsequent diagnostic found document rules waiting 131ms behind resource requests. Both transport routes now reserve two of the existing sixteen request slots for ordinary API admission, with bounded queues and arrival order within each class. No validation, host quota, or response window is bypassed.

## Measurement boundaries

The anonymous fixture uses a fresh Chromium context, actual Workers/D1/DO, native RTC, the current main and login source, and installed CSS. Workspace and port preview are mocked so an anonymous path cannot accidentally enter them. It records navigation start to the next animation-frame opportunity after insertion of the real password input. It asserts whether the signed Upgrade was accepted and whether a later connect message was absent.

The authenticated fixture uses the actual full workspace with a temporary example account. Final samples load the installed Vite artifact and assert its SHA and modification times remain unchanged throughout the run. Each cold sample clears HTTP and CacheStorage, unregisters workers, deletes all host-origin IndexedDB databases, removes app storage, and starts a fresh Chromium process. It retains only the example trusted login and the central non-extractable browser key, asserting that the host databases are empty before navigation. Earlier authenticated rendering comparisons below cleared static caches but retained the file-body database; they are not strict cache-free results.

The fixture measures menu, file tree, and actual editable Plain or Hotview DOM separately. It enters real text, confirms exactly one save through the actual file service, and checks that replacement RTC preserves the saved editor without replaying the write. Recovery records the browser's authenticated reconnection event and its next animation frame separately from later Playwright observations. A fixed-Git App override supports controlled rendering comparisons while retaining the same remaining source graph. Neither fixture reads repository environment files or actual account data.

Optional signaling RTT models delay each browser–central and host–central WebSocket leg, including initial Upgrade requests, by half the configured RTT. HTML downloads, direct P2P, fonts, and CPU remain local unless stated otherwise. These models distinguish protocol savings from actual Internet performance and cannot establish the current production DO location or external-network success.

## Verified intermediate results

A read-only Cloudflare Analytics query on 2026-11-02 matched the current registered Windows device's exact signaling namespace and object name. The one-hour interval 12:19:03–13:19:03 UTC returned a single SJC group with 422 reported requests. This verifies current execution location, not an individual handshake's RTT; an attempted wider query was rate limited. No routing, registration, or authority state was changed. Moving an existing object still requires a separate fenced authority migration and was not attempted.

Before the entry-aware chunk correction, an App-only comparison held the remaining module graph identical. Three cold file-tree displays changed from 1,067/1,022/942ms to 761/665/678ms, with the median decreasing from 1,022ms to 678ms. The corresponding menu median changed from 657ms to 564ms. Same-frame RTC recovery remained 285/286ms in that comparison. These measurements isolate regular-state explorer rendering; they are not the final combined build or production measurements.

The controller-only signed Upgrade passed actual native RTC checks, including explicit acceptance and no second connect. Its initial local anonymous sample was 593ms, followed by 259/257ms visits. A subsequent 180ms signaling model exposed lost overlap before early RTC preparation and one warm worker-registration stall of approximately 1.36 seconds. Those observations motivated the later primer and worker-readiness changes; they are not final timing claims.

Before early collaboration preparation and terminal renderer isolation, the installed artifact's strict cold Plain editor samples were 1,204/1,095/1,131ms; Hotview samples were 1,253/1,135/1,178ms. Menu medians were 801/804ms, and tree medians were 1,003/1,000ms. All six actual editing samples exceeded one second. The fixture received one bounded workspace UI snapshot and made no initial standalone UI-state read in every cold, warm, and direct case.

In the same-artifact Hotview recovery comparison, removing only the new recovery metadata used the ordinary path and produced a verified-online event at 696ms and next-frame opportunity at 705ms. The signed recovery path produced 535/548ms, reducing the next-frame result by 157ms (22%). Both retained the same editor frame and saved content, verified the current identity, and did not replay a write. This comparison isolates recovery signaling; it does not establish production performance.

A later opt-in admission diagnostic found that background agent module requests filled the inner launcher's sixteen-request pool: the pane waited 50ms, Hotview 66ms, and some dependencies 107–110ms. File and document-rule API waits were zero; the outer RTC pool was nearly immediate. Fonts completed before or began after this queue interval. Preparing the pane before background import removed its queue wait, but the engine still waited 51ms, motivating preparation directly from accepted initial UI metadata. These diagnostic samples include instrumentation overhead and are excluded from final timing claims.

## Final installed-build measurements

With the 180ms signaling model, the final artifact produced these strict empty-cache samples. These are navigation to actual editable DOM at its next animation-frame opportunity, not a production guarantee or a pixel-paint measurement.

| Screen | Cold samples (ms) | Median (ms) | Under one second |
| --- | --- | --- | --- |
| Plain editor | 1098 / 1039 / 1049 | 1049 | 0 of 3 |
| Hotview editor | 1175 / 1083 / 1060 | 1083 | 0 of 3 |

The corresponding menu samples were 866/799/813ms for Plain and 859/807/804ms for Hotview. Tree samples were 1118/1039/1049ms and 1080/1002/1060ms. The same final installed artifact's anonymous login appeared at 796ms in a separate fresh-context sample, with later visits at 622/630ms and replacement RTC at 533ms. Warm authenticated editors appeared at 847/868ms. Replacement RTC preserved the same authenticated editor and saved content, producing online events at 499/539ms and next-frame opportunities at 506/548ms. Direct cold editor controls in the preceding artifact were 357/394ms under the fixture's local HTTP conditions.

The first-edit target remains unmet: menus and anonymous login were below one second, while all six cold editing samples exceeded it. Two-slot reservation reduced document-rule API admission wait from 131ms to 48ms in separate instrumented samples; this is not an authorization endpoint and its completion is not required before editing. Before the bounded background delay, ordinary file admission waited 12ms, the pane 49ms, and CodeMirror core 0ms in the final diagnostic. Neither that comparison nor the mixed cold samples establishes an overall scheduling speedup. The cache absence path reduced redundant pre-download cache work, but it also shifted contention; no independent end-to-end gain is claimed for that change.

## Verification and application

Final installed-build timing verification passed the functional assertions but did not meet the cold-editor timing target. Completed checks include 221 transport, resource-worker, snapshot, and client tests; 68 composer and cache browser checks; 226 private central tests across 27 files; 27 launcher startup browser checks; 40 stream-slot, cancellation, reconnect, and admission checks; two empty-cache regressions, including removal of caller conditional headers when no verified body exists; focused deferred editor, collaboration, parser, terminal, and module-boundary checks; parent and private type checks; scoped lint; both required builds, and all three original/sharded icon generator consistency checks. The final combined startup/browser/resource/admission run passed 61 checks. Documentation descriptions pass (655 descriptions, zero errors). The repository-wide link check is blocked by an unrelated absolute API asset link in the existing task document `Image preview and attachment editing.md`; no owning document in this change reports a link error. No deployment, launcher invocation, or running-server lifecycle operation has been performed.

The parent and private central repositories are committed separately. Private commits are `5cf4042` (batched admission), `a773f94` (initial and recovery offers), `72adf11` (isolated timing diagnostics), and `8a05856` (resource-aware diagnostic parity). They require the matching parent shared/client changes. The required parent build refreshes `dist/`, which the running source server serves directly; it does not reload server modules. The user must restart the host to apply the shared cache validator for `~` in entry-aware asset names and the optional workspace UI snapshot API, and separately deploy the central Worker/frontend according to the [central runbook](../operations/remote-central.md). These changes add no D1 migration or device re-registration. Production cold/warm access, physical phones, mobile network switching, and document editing readiness remain separate verification gates.
