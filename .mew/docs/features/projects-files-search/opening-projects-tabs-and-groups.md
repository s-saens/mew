## Requirements

### Projects and My Projects

- The **workspace** is the instance-wide catalog of folders added to Mew. **My Projects** is an ordered set of shortcuts for one signed-in account; it is not a folder or a private copy of a project. The UI uses workspace terminology for this catalog; existing storage and API identifiers remain unchanged.
- A new account starts with an empty My Projects list even when its role or file permissions allow access to existing projects. Browser-cached paths and opening a shared project do not populate the list. Existing projects remain available through **Import project → From this workspace** in the plus popup; adding a shortcut is an explicit account action.
- All signed-in users, including members, can browse registered projects, add them to My Projects, and switch to them. Guests cannot use the catalog, create or link projects, or maintain My Projects. Existing feature and file permissions continue to apply after selection.
- Creating, cloning, or linking a project registers it for the instance and adds it to the initiating account's My Projects. Other accounts can add that same project to their own lists without copying files or affecting the creator's list.
- `DATA_DIR/projects.yaml` owns both the shared catalog and personal shortcuts. Every personal shortcut must reference a registered catalog entry; entries absent from the catalog are excluded from My Projects. Existing per-account lists migrate without moving project folders. The [registry and storage contract](../../development/architecture.md#shared-project-registry-and-my-projects) owns the schema and APIs; [ADR 0118](../../decisions/0118-shared-project-registry.md) supersedes the account-isolated catalog and member restrictions in [ADR 0070](../../decisions/0070-manager-project-access.md).

Project selection prepares fresh account tab metadata alongside the server handoff. Recent tree and body snapshots remain visible while validation continues without extending the workspace loading status; cached bodies remain read-only until verified. The [fast switching contract](../../development/ui-project-navigation.md#fast-root-project-switching) owns request ordering, cancellation, and cache limits.

### Create or link a project

- An empty My Projects list shows only the top bar and the project panel, even when an accessible shared project remains active. Hide the Dock, the top bar's project selector and command button, and project work panels. Center **Add a project** above a plus button that opens the same project-add popup used by the personal list. The server startup folder is not automatically presented as that account's first project.
- If a saved active root is unavailable, restore the first existing My Projects directory; if none exists, show project setup while preserving unavailable entries.
- With personal projects present, the **Projects** panel initially selects **My**, with an **All** scope for the registered workspace catalog. An icon-only **+** button with a translated **Add project** accessible name and tooltip opens a themed popup. The popup offers **New project**, **Git clone**, and **Import project**. **Import project** leads to **From this workspace** and **Browse path** within the popup. The popup retains workspace import alongside direct catalog access from the panel's **All** scope. Creation and clone inputs stay in the popup; ordinary managed creation does not require a filesystem path.
- **New project** shows a visibly labelled name field with a default-on Git icon toggle inside its right edge and a text-labelled primary **Create project** button. Mew creates the directory at `~/.mew/projects/<name>` on the server. Names must be safe single directory names; duplicate names never reuse or overwrite an existing folder.
- Confirming the name creates `.mew/docs/` inside `.mew/` as its initial Documents location, and when Git is selected, initializes `.git/` and writes `.gitignore` with Mew temporary uploads excluded. It registers, pins, and opens the result.
- The secondary **Create with agent** action creates and opens the same managed project, then opens a popup using the existing `AgentPanel` conversation component. The agent asks about the intended project before implementation, incorporates the answers, and documents the project under the applicable Mew default and project guidance. Runtime selection, authentication, permissions, conversation retention, and errors reuse the ordinary agent controls.
- **Import project → From this workspace** browses registered projects. Importing adds a shortcut to the caller's My Projects and opens it without copying files. **Import project → Browse path** opens the server folder browser. Linking preserves the folder's location and contents, registers its canonical path, adds it to My Projects, and opens it. Existing aliases resolve to one catalog entry.
- The linked-folder browser retains keyboard and home/parent navigation for signed-in users. Path suggestions, favorites, and missing-path creation remain conditional on their existing role and feature checks. Creating folders or running Git tools at arbitrary server paths remains limited by the existing manager/owner and feature checks. These tools are separate from managed name-only creation.
- **Git clone** accepts a public GitHub or GitLab HTTPS repository URL without provider login and stores the clone at `~/.mew/projects/<name>`. Private cloning uses the connected GitHub account. That account can select repositories it is authorized to access, including private and organization repositories. Account connection is available before a project is open and reuses the existing per-account GitHub flow. GitHub is the supported connected provider; GitLab supports public URL cloning only. Invalid URLs, unsafe names, and existing destinations are rejected without overwriting a folder. Failed clones do not register a project or retain an incomplete managed destination. [Git connections](../../development/git-connections.md) owns authorization and credential handling.
- `Ctrl/Cmd+O` opens the server file explorer for accounts with the required server file permission. Opening a file keeps the current project. `Ctrl/Cmd+Shift+O` opens the project panel and its project-add popup for a signed-in user. Alt combinations and IME composition do not trigger these actions.

### Select and organize projects

- The plus button follows the current My or All list. Setup opens in a viewport-bounded `DialogFrame` popup with internal scrolling and a fixed title and close control. A separate back arrow returns one step: workspace catalog to import sources, or name, clone, and import setup to the three choices. X, outside press, Esc, and Back close the whole project-add popup from any step; a nested folder browser or menu closes first. Busy operations block dismissal and duplicate submissions. Closing restores focus to the plus trigger, and empty-list onboarding remains visible. The popup traps keyboard focus, follows the active theme, and retains at least 44px action and field heights on mobile. Clone setup has a visible repository URL label and a text-labelled primary **Clone repository** button.

- The desktop sidebar and mobile full-screen panel use the translated title **Projects**. A **My / All** scope toggle sits directly below the header and matches the file explorer's **Documents / Files** appearance and keyboard behavior. **My** shows personal shortcuts in their existing hierarchy and order, with reordering and project commands. **All** lazily loads the registered workspace catalog with search. Selecting a catalog row adds it to My Projects before opening it; an existing shortcut is reused. The initial scope is My, and the selected scope is retained while the component remains mounted. Left/Right switches scope and moves focus, Home selects My, and End selects All. A pending catalog import blocks scope changes.
- The header and project lists show project names and their shared icons; managed creation and catalog browsing do not depend on knowing storage paths. Icons remain owned by each project's `.mew/project-icon.json`, shared by the explorer and selector. Signed-in users can edit shared icons, with members restricted to registered project roots.
- The header project button opens the leftmost project sidebar on desktop (768px or wider) or the full-screen project panel on mobile. The sidebar is outside the Dock and file explorer, opens independently, and remembers its width and open state per browser and account. Desktop selection does not close it. Mobile selection and Close dismiss the panel and restore focus to the invoking control. While the project-add popup or a nested menu is open, Esc and Back dismiss only that top overlay and restore focus to its invoking control; busy setup stays open. Without an inner popup or menu, Esc and Back dismiss the mobile panel. Safe-area padding, focus containment, internal scrolling, and touch-sized rows are retained.
- My Projects supplies the **My** list and its order. **All**, as well as **+ → Import project → From this workspace**, browses registered projects and explicitly imports them into My Projects. Importing an already pinned project reuses it. Duplicate names show a path detail only where needed to distinguish the choices. Removing a shortcut preserves the shared catalog, filesystem, and other accounts' shortcuts; removing an active shortcut switches successfully to another pinned project first when one remains. Removing the last shortcut preserves its saved active root and the shared catalog, then shows the panel for an empty personal list until a project is added.
- Nested Git/Mew projects are discovered beneath registered roots and added to the workspace catalog without being automatically pinned. In My Projects, pinned descendants appear beneath their nearest pinned path ancestor. Hierarchy reflects filesystem ancestry rather than user-created groups. Existing per-account shortcut order and switch permissions remain authoritative.
- Drag the left handle with mouse or touch to reorder My Projects. `Shift+↑/↓` on a row or `↑/↓` on its handle performs the same reorder without switching. Reordering starts from the displayed hierarchy order and refreshes shortcut numbers and targets together. Personal order is persisted in `projects.yaml`; the add action is not sortable. The active row is highlighted across its full width, without a checkmark.
- `Alt+P` opens the project list for signed-in users and focuses its first item. `Alt+1…9` selects the first nine My Projects rows from top to bottom after grouping nested projects beneath their pinned ancestors, with matching numbers displayed on the right. The same order applies while the list is closed; rows after the ninth have no numbered shortcut. Existing IME, repeat, modifier, modal, remote-input, and focus boundaries remain. `Ctrl/Cmd+number` continues to select tabs within the focused panel.
- Each My row's command button targets that project without changing the active root, and remains conditional on command/terminal permission. [Project commands](../terminals-agents-automation/project-command-buttons.md) owns execution, editing, and session isolation.
- The current project button and My rows open a shared context menu with **Edit** and **Delete**. Delete replaces those entries within the same menu with **Remove from My Projects** and, for owners only, **Delete permanently**. Remove from My Projects retains its shortcut-only behavior; it never deletes files or another account's shortcuts. Menu navigation, keyboard invocation, Esc/Back dismissal, focus restoration, and touch long-press remain available. No project tab strip or group UI is restored.
- **Delete permanently** opens an irreversible-deletion confirmation naming the target project and its folder. The dialog initially focuses Cancel. Confirmation recursively deletes the real project folder, including any uncommitted files and nested projects, removes that folder and registered descendants from the shared catalog, and removes their shortcuts from every account. This is owner-only for both managed and linked projects. Protected roots, home, server data, and Mew source locations and their protected ancestors cannot be deleted through this action. The [registry API contract](../../development/architecture.md#shared-project-registry-and-my-projects) and [ADR 0151](../../decisions/0151-permanent-project-deletion.md) own validation and storage boundaries.
- During deletion, block duplicate confirmation and dialog dismissal. Canceling before confirmation closes only the confirmation and preserves the folder. A failed request keeps the target and error available for retry; do not report success or remove the visible entry before the server confirms the operation.

### Switching and boundaries

- Selecting a registered project changes only the requesting account's active project and notifies that account's other connections. Other users' roots, watchers, and collaboration rooms are preserved. Accounts opening the same actual root share its files and permitted collaboration.
- The browser restores each logical project's documents, layout, and scroll state without refreshing. Selecting another project during loading cancels obsolete preparation and applies only the latest selection. Returning to the displayed project while a different switch is pending reasserts that project through the server.
- Running agents and terminals retain their original working paths. New sessions use the selected working root.
- Subproject arrows and Git worktree switching retain their existing manager/owner checks. Switching a registered root does not grant arbitrary OS operations. Within a logical project, switching an existing worktree preserves the project identifier, panels, tabs, and sessions while refreshing files against the actual working root; the worktree is not automatically a separate catalog project.
- A missing catalog directory remains listed so unavailable mounts and migrated entries are not silently removed. Opening it reports the existing path error instead of creating or replacing it.

## Implementation details

The [architecture contract](../../development/architecture.md#shared-project-registry-and-my-projects) owns catalog persistence, migration, and API payloads. The [shared UI contract](../../development/ui-project-navigation.md#shared-ui-for-adding-projects-and-browsing-server-files) owns the project-add popup, catalog controls, and explicit linked-folder browser. [Project usage](../../../../docs/guides/projects.md#프로젝트-탭) explains the flow to users.

`activeWorkspace` in the account UI ledger is the actual file root, and `activeProjectPath` is the logical root used for screen restoration. Ordinary project selection sets both values; an existing-worktree switch preserves the logical root. `hasProject` distinguishes a selected root from the server's internal fallback root; the loaded personal list independently controls the panel for an empty My Projects list. HTTP and project WebSocket requests pin the authenticated account's actual root; switching never changes the startup root or other accounts' contexts.

Project icons use the existing shared read, migration, and validation code. Personal ordering uses the compatible root-project API backed by YAML. Existing browser path copies are recovery/migration data; they do not define the global catalog or make another user's shortcut visible in My Projects.

The agent-assisted popup reuses the project-bound AgentPanel and normal runtime selection rather than introducing a separate chat implementation. Its opening request asks for project discovery first and applies the existing documentation instructions to the resulting work.
