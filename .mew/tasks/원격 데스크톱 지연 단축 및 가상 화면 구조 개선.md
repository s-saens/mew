## 목적과 범위

원격 데스크톱의 입력부터 화면 표시까지 걸리는 체감 지연을 줄이고, 물리 모니터가 60Hz이거나 꺼진 환경에서도 고주사율·맞춤 해상도로 조작할 수 있도록 구조를 개선한다.

현재 계약과 설계는 [원격 데스크톱 기능](../docs/features/browser-android-remote-desktop/remote-desktop-and-touch-input.md), [원격 데스크톱 아키텍처](../docs/development/remote-desktop.md), [Rust 영상 엔진](../docs/development/remote-desktop-rust.md), [가상 디스플레이 드라이버](../docs/development/remote-desktop-virtual-display.md), [StarDesk 격차 조사](../docs/research/remote-desktop-stardesk-gap.md)를 따른다.

## 제안 후보 검토와 우선순위

외부 제안 4가지와 현재 Mew 구현([gpu-windows.cpp](../../native/remote-desktop/gpu-windows.cpp), [virtual-display-driver.cpp](../../native/remote-desktop/virtual-display-driver.cpp), [engine.rs](../../native/remote-desktop/rust/src/engine.rs), [rtp.rs](../../native/remote-desktop/rust/src/rtp.rs), [rust-engine.mjs](../../native/remote-desktop/rust-engine.mjs), [remote-desktop.tsx](../../src/components/remote-desktop.tsx))을 대조한 결과는 다음과 같다.

| 변경 후보 | 현재 Mew 구조와 대조 | 기대 효과 | 비용·한계 및 판단 |
| --- | --- | --- | --- |
| **1. 캡처부터 표시까지 오래된 프레임이 쌓이는 지점 제거** | WGC 프레임 풀(2장)과 인코더 `inFlight < 3` 제한은 이미 적용되어 있다. 그러나 브라우저 수신 지터 버퍼(`playout-delay` 미설정), Rust RTP 페이서의 소형 프레임 분할 대기, 마우스·키보드 입력의 Node.js 4ms 타이머 폴링, `gpu-windows.cpp`의 1~2ms 폴링 및 중간 텍스처 복사에서 매 프레임 지연이 누적된다. | 입력 반응성과 화면 추종성을 가장 크게 개선할 수 있다(전 구간 15~50ms 단축 가능성). | **최우선 추진(1단계).** 드라이버 변경이나 별도 앱 설치 없이 현재 코드 경로 안에서 바로 줄일 수 있다. |
| **2. 가상 화면의 해상도·주사율을 접속 기기에 맞춤** | 자체 UMDF 2 / IddCx 드라이버([virtual-display-driver.cpp](../../native/remote-desktop/virtual-display-driver.cpp))가 이미 있으나 `1920×1080 @ 60Hz` 단일 고정 모드만 노출한다. 물리 모니터가 60Hz이거나 꺼진 상태에서는 120·144fps 설정을 켜도 DWM 합성이 60Hz에 묶인다. | 물리 모니터 제약 없이 120·144·240Hz 고주사율 합성과 기기 화면 비율·해상도 맞춤이 가능해진다. | **핵심 추진(2단계).** 드라이버 모드 테이블·제어 프로토콜 수정과 드라이버 재빌드·서명 설치 검증이 필요하다. GPU·네트워크 대역폭 사용량이 함께 늘어난다. |
| **3. 가상 화면의 GPU 프레임을 인코더로 직접 전달** | 현재 가상 화면도 드라이버 스왑체인 표면을 즉시 해제하고 사용자 세션에서 WGC(`CreateForMonitor`)로 다시 캡처한다. | 별도 WGC 캡처 단계와 동기화 비용을 줄일 가능성이 있다. | **조건부 추진(3단계).** UMDF 드라이버와 사용자 세션 호스트 간 DXGI 공유 핸들·보안·수명·GPU LUID 동기화 복잡도가 높다. 1단계의 `gpu-windows.cpp` 내부 이중 복사 제거와 이벤트 기반 캡처 전환 후에도 캡처 지연이 병목일 때 진행한다. |
| **4. 전용 네이티브 수신 앱 제공** | 현재는 웹·모바일 브라우저의 `<video>`와 WebRTC를 사용한다. | 디코딩·표시 시점과 버퍼를 브라우저보다 세밀하게 제어할 여지가 있다. | **후순위 보류(4단계).** 플랫폼별 개발·설치·배포 부담이 크고 브라우저 즉시 접속이라는 장점이 약해진다. `playout-delay=0` 적용과 브라우저 내 WebCodecs(`VideoDecoder` + `<canvas desynchronized>`) 경로를 먼저 검토한다. |

## 단계별 변경 항목

### 1단계: 송수신·입력·캡처 파이프라인 지연 제거

- [ ] **WebRTC `playout-delay=0` 확장 적용**: SDP 협상과 [rtp.rs](../../native/remote-desktop/rust/src/rtp.rs)의 RTP 헤더에 `http://www.webrtc.org/experiments/rtp-hdrext/playout-delay`(`min=0, max=0`)를 추가해 Chromium `<video>` 수신부의 기본 지터 버퍼 대기를 줄인다.
- [ ] **Rust RTP 페이서 즉시 전송 범위 확대**: [rtp.rs](../../native/remote-desktop/rust/src/rtp.rs)에서 일반 델타(P) 프레임이 `1.15 × bitrate` 페이싱과 `5ms` 버스트 예산 때문에 여러 주기에 걸쳐 쪼개지지 않도록 즉시 전송(버스트 허용) 범위를 넓히고, 대형 키프레임(IDR)이나 혼잡 상황에서만 페이싱을 유지한다.
- [ ] **입력 DataChannel의 Node.js 4ms 폴링 우회**: [rust-engine.mjs](../../native/remote-desktop/rust-engine.mjs)의 4ms 타이머 폴링과 Node 이벤트 루프를 거치지 않고, Rust(`rtc.rs`/`engine.rs`)에서 수신한 마우스·키보드·터치 입력을 네이티브 입력 어댑터(`SendInput`)로 직접 전달한다.
- [ ] **Windows GPU 캡처·인코딩 루프 정리**: [gpu-windows.cpp](../../native/remote-desktop/gpu-windows.cpp)의 `mew_gpu_poll`에서 인코딩 출력 드레인(`METransformHaveOutput`) 직후 함수를 종료하지 않고 같은 호출 안에서 새 프레임 입력(`ProcessInput`)까지 이어서 처리한다. WGC 표면을 `e->latest`로 한 번 더 복사(`CopyResource`)하는 중간 단계를 줄이고, 1~2ms 폴링 대신 프레임 도착·인코더 이벤트 기반 깨우기를 검토한다.
- [ ] **하드웨어 인코더 초저지연 경로 검토**: 범용 Media Foundation MFT에서 드라이버 내부 큐가 남는 경우를 대비해 NVENC 등 벤더 초저지연 옵션(Zero-Reorder, Ultra-Low Latency, Intra-Refresh) 적용 가능성을 확인한다.

### 2단계: 가상 화면 동적 해상도·고주사율 지원

- [ ] **드라이버 다중 해상도·고주사율 모드 노출**: [virtual-display-driver.cpp](../../native/remote-desktop/virtual-display-driver.cpp)의 고정 1080p·60Hz 신호 설정을 확장해 `1920×1080`, `2560×1440`, `3840×2160` 및 60·120·144·240Hz 타깃 모드를 지원한다.
- [ ] **접속 기기 맞춤 모드 선택 연동**: [virtual-display-protocol.h](../../native/remote-desktop/virtual-display-protocol.h)와 [virtual-display-client.h](../../native/remote-desktop/virtual-display-client.h), 호스트 시작 경로에서 클라이언트가 요청한 해상도·FPS에 맞춰 가상 모니터 모드를 활성화한다.

### 3단계: 가상 화면 스왑체인 직접 전달 및 브라우저 디코더 대안 검토

- [ ] **드라이버 스왑체인 → 인코더 직접 전달 측정·검토**: 1·2단계 적용 후 `captureUs`를 측정해 WGC 캡처 비용이 여전히 유의미할 때만, 드라이버 스왑체인 GPU 표면을 호스트 인코더로 안전하게 공유하는 구조를 설계한다.
- [ ] **브라우저 WebCodecs 수신 경로 또는 네이티브 뷰어 판단**: `playout-delay=0` 적용 후에도 브라우저 `<video>` 지터 버퍼(`jitterBufferDelay`)가 병목으로 남는지 측정하고, 필요시 DataChannel/WebRTC 기반 WebCodecs(`VideoDecoder` `optimizeForLatency: true` + `<canvas desynchronized>`)를 전용 네이티브 수신 앱보다 먼저 검토한다.

## 완료 및 검증 기준

- [ ] 변경 전후 동일 환경에서 `captureUs`, `encodeUs`, 패킷 송신 대기 시간, 브라우저 `jitterBufferDelay / jitterBufferEmittedCount`, 입력 왕복 체감 지연을 비교 기록한다.
- [ ] 가상 화면(`gpu:99`)에서 60Hz를 넘는 주사율(120·144Hz)과 변경된 해상도가 실제 캡처 FPS 및 출력 크기에 반영되는지 확인한다.
- [ ] 기존 세션 권한 검증, 화면 공유 종료 시 즉시 회수, 드라이버 임대(lease) 만료 정리, 입력 좌표 변환이 깨지지 않는지 회귀 테스트로 검증한다.
- [ ] 구현 변경 시 소유 계약 문서([remote-desktop.md](../docs/development/remote-desktop.md), [remote-desktop-rust.md](../docs/development/remote-desktop-rust.md), [remote-desktop-virtual-display.md](../docs/development/remote-desktop-virtual-display.md)), 결정 기록, 작업 기록을 함께 갱신하고 `npm run check:docs`와 `npm run build`를 통과시킨다. 서버 실행·재시작과 드라이버 서명·설치는 사용자가 수행한다.
